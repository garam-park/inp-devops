이 문서는 통합플랫폼 저장소(`gis-sass`)의 ADR(`docs/01.개발/ADRs/`) 현황과 대표 결정을 한곳에 정리한 것이다. ADR 원문은 결정 1건당 문서 1개로 저장소에 있으며, 결정이 바뀌면 새 ADR 이 앞 결정을 대체하고 옛 ADR 머리에 대체·변경 사실을 표기하는 것이 관례이다(ADR-2026-08-11.06 이 ADR-2026-08-10.02 의 배치 부분을 대체, 표기는 ADR-2026-08-10.02·ADR-2026-08-11.03 머리). 결정의 뼈대가 같은 경미한 보완은 새 ADR 없이 승인 뒤 원문에 갱신 노트·예외로 덧붙인 사례가 있다(ADR-2026-08-12.01, ADR-2026-09-01.02). 새 ADR 이 뒤를 이은 경우에는 옛 ADR 원문에 그 ADR 을 가리키는 후속 안내만 덧붙였다(ADR-2026-08-18.04 → ADR-2026-09-16.01·.02). 확정 뒤의 수정·대체 절차는 ADR README 에 정해져 있지 않다. ADR 번호는 `ADR-YYYY-MM-DD.NN`(날짜.순번)이며, 저장소 규칙(`ADRs/README.md`)상 날짜는 결정일이다. 다만 ADR-2026-09-26.01·.02 는 초안을 쓴 날(2026-09-26)로 번호를 매겼고 결정일은 둘 다 2026-10-14 이다. 상태는 각 ADR 원문의 상태 줄 기준이다.

**현재 단계**: 제주 지반침하 프로토타입(`Jeju-subsidence-AI`) 분석 및 통합플랫폼과의 결합 방식 검토 중이며 결합 방식은 미결정이다. 이에 대한 ADR 은 아직 발급하지 않았고, 3.3 절에 결정 대기 항목으로 정리했다.

## 3. 대표 결정

### 3.1 서비스 분해 기준과 API 게이트웨이 책임

- ADR 번호: ADR-2026-08-26.01
- 제목: 서비스 분해 기준과 API 게이트웨이 책임
- 상태: 승인
- 일자: 2026-08-26
- 결정자: 개발팀(결정자 개인명 <mark>확인 필요</mark>)

**1. 맥락** — WBS ID 3(고가용성 MSA 기반 백엔드 서버 환경 구축)과 ID 5(마이크로서비스 단위 도출 및 서비스 간 통신(API 게이트웨이) 설계)의 과업 문구와 실제 저장소 구조(customer-api·admin-api 가 `api-core` 를 컴포지트 빌드로 공유하는 모듈러 모놀리식, 운영은 1인 전제) 사이의 거리를 결정으로 메운다. 8월 1주차 보고에 "도메인 8개 도출"이 있었으나 목록이 저장소에 파일로 없어 카탈로그 v1.0 으로 확정해 남긴다.

**2. 결정** — 후보를 장애 격리 > 데이터 소유 > 독립 배포·확장 > 팀 경계 순의 기준으로 판정해 **타일 프록시와 ETL 수신을 분해**하고 나머지는 유지하며, 게이트웨이는 **Ingress 단독**으로 두고 Kafka(3-broker)·Keycloak 은 도입하지 않는다.

| 후보 | 판정 | 근거 |
| --- | --- | --- |
| 인증 | 유지 | 두 제품이 `api-core/auth` 를 공유, 분해 시 두 인증이 따로 노는 비용이 크다 |
| 조직·워크스페이스·멤버십 | 유지 | customer 전용, 자체 권한 도메인이 충분히 격리됨 |
| 지도 소스·레이어 | 유지 | map 도메인 내부. 타일 프록시 분해와 무관 |
| 타일 프록시 | 분해 | 스케일 축이 다르고 외부 호출 도메인이라 장애 격리 가치가 크다 |
| ETL 수신 | 분해 | 배치성 비동기, Kafka 미도입 결정과 정합 |
| admin | 유지(이미 별도) | `apps/admin` 이 이미 별도 배포 단위 |
| 미식별 2개 | 재검토 조건 | 목록이 저장소에 없음, 발견 시 추가 |

게이트웨이 책임 위치: 인증 검증은 서비스(`api-core/auth` 필터), rate limit·요청 크기 제한은 Ingress(환경별 values), `request_id` 채번은 서비스 필터(클라이언트 `X-Request-Id` 보존, 없으면 UUID 발급)다.

**3. 검토한 대안**

| 대안 | 장점 | 단점 | 채택 여부 |
| --- | --- | --- | --- |
| Kong(OSS) 도입 | (원문에 장점 기재 없음) | 운영 대상(DB·realm·업그레이드) 증가, Ingress 와 책임 중복, PoC 비용 대비 이득 작음 | 불채택 |
| Spring Cloud Gateway | (원문에 장점 기재 없음) | api 프로세스 내부에서 동작해 외부 게이트웨이 책임이 줄지 않고 BFF 복잡도만 추가 | 불채택 |
| Kafka 3-broker | (원문에 장점 기재 없음) | ETL 트래픽이 1일 1회~수 회라 컴포넌트 +1 비용이 정당화되지 않음. DB 작업 테이블 + 잡 러너로 같은 비동기 흐름을 구현하기로 했다(기준일 2026-10-16 현재 작업 테이블·잡 러너는 미구현이며, 수신은 customer-api 안의 산출물 메타데이터 등록·조회 API 골격뿐이다) | 불채택 |
| Keycloak | (원문에 장점 기재 없음) | 자체 인증·권한 도메인이 안착, 외부 IdP 요구가 없음 | 불채택(요구 발생 시 재검토) |
| MSA 전면 분해 | (원문에 장점 기재 없음) | 트랜잭션 경계·인증 전파 비용이 1인 운영에 정당화되지 않음 | 불채택 |

**4. 결과**

- 얻는 것: WBS ID 5 의 해석 분쟁을 막는 근거 확정, 장애 격리 가치가 큰 두 도메인의 분리 방향, 운영 대상 최소화.
- 감수하는 것: "MSA 전면 분해"가 아니라 모듈러 모놀리식 + 선택적 분해라는 점. 분리 이미지는 아직 없어 현재 두 기능은 customer-api 안에서 동작하고 chart 의 분리 단위는 비활성이다. Ingress 는 JWT 서명 검증을 지원하지 않아 인증 검증은 서비스 필터가 맡는다.
- 후속 작업: 배포 단위 매니페스트(T072), 타일 프록시 Ingress 경로 분리(`/api/map/tiles`), ETL 수신 API·잡 러너 분리(담당 Task 없음, 분리 이미지 일정 없음), 수신 골격·어댑터 골격(T074, 진행 중 — 현재 customer-api 안의 범용 수신 골격만 구현되고 어댑터는 미구현), `api-core/shared` 의 `request_id` 필터.

- ADR 번호: ADR-2026-09-26.02
- 제목: CSAP 인증 유형·범위 확정과 운영 타깃 재확인
- 상태: 승인(D4 는 공공 콘솔 실측 5건을 승인 조건으로 둔다)
- 일자: 2026-10-14(초안 2026-09-26)
- 결정자: 개발팀(결정자 개인명 <mark>확인 필요</mark>)

**1. 맥락** — ADR-2026-08-11.03 은 운영 타깃을 NCP NKS + Cloud DB for PostgreSQL 로 정하면서 CSAP 요건을 대상으로 보지 않았다. 사업 과업(WBS ID 32~35)으로 CSAP 인증 신청이 들어와 전제가 바뀌었다. CSAP 는 인증받은 IaaS 위에서 운영되는 SaaS 만 인정하므로 인증 유형·등급·범위, 운영 타깃, 망분리 여부, 제3자 진단 필요 여부를 정해야 한다.

**2. 결정** — 하등급 SaaS(조건부)로 customer + admin 을 인증 대상으로 하고, 운영 타깃은 NCP 공공기관용(NKS + Cloud DB for PostgreSQL)으로 한다. 망분리는 대상이 아니다(인터넷망 SaaS 의 영역분리로 갈음).

| 항목 | 결정 | 조건·비고 |
| --- | --- | --- |
| D1 인증 등급 | 하등급 SaaS | 발주처의 하등급 분류 확인, `username` 에 식별 가능한 값을 쓰지 않는 운영 정책 |
| D2 인증 대상 제품 | customer + admin | 관리자 접근통제·접근기록을 같은 증적 체계로 제시 |
| D3 시스템 경계 | 수신 경로는 경계 안, 세세부1·2 전송 측 시스템은 경계 밖 | 외부 연계 인터페이스 통제(인증·전송 암호화·접근기록) 제시 |
| D4 운영 타깃 | NCP 공공기관용 NKS + Cloud DB for PostgreSQL | 공공 콘솔 실측 5건(NKS Multi Zone, PostGIS, Ingress 방식, 외부 레지스트리, 마이그레이션 공지 영향) |
| D5 이미지 레지스트리 | 공공 영역 레지스트리로 전환 | D4 실측 4 이후 |
| D6 제3자 진단 | 자체 사전 점검 + KISA 요건 문의 | 요건이면 별도 안건 |
| D7 기준 문서 판 | KISA 최신판 재확보 후 판·시행일 기록 | 저장소 정리본과 대조 |

**3. 검토한 대안**

| 대안 | 장점 | 단점 | 채택 여부 |
| --- | --- | --- | --- |
| NCP 일반 리전 유지 | 변경 없음 | 인증 범위 밖이라 신청이 성립하지 않음 | 불채택 |
| NCP 공공기관용 | 이미 가입, 같은 사업자·상품군이라 chart 변경 최소 | 공공 영역 NKS Multi Zone·PostGIS·Ingress 방식 미확인 | **채택**(조건부) |
| AWS 서울 리전 | PostGIS·관리형 k8s 성숙 | 하등급 상한, 신규 계정·과금·학습 비용 | 불채택 |
| AWS GovCloud | — | 미국 리전이라 국내 위치 요건 불충족 | 제외 |
| KT 공공 | — | 인증 범위·PostGIS 확인 못 함 | 비교 불가 |

**4. 결과**

- 얻는 것: 인증 범위와 운영 타깃의 확정, 매니페스트 재작성 범위(Ingress 클래스, zone 분산, 관리형 DB 엔드포인트·TLS, 이미지 레지스트리, 로그 수집)의 식별.
- 감수하는 것: 공공 영역 실측 5건이 끝나기 전에는 D4 가 조건부이며, PostGIS 가 불가하면 재검토한다. D1 조건이 깨지면 중등급으로 가야 하고 12-31 기한 안에 흡수하기 어렵다.
- 후속 작업: 공공 콘솔 실측, 발주처 등급 확인, KISA 해설서·고시 재확보, 통제항목 갭 분석(T078), 운영 원칙(공공 고객용 인스턴스를 민간 고객과 공유하지 않는다).

### 3.3 제주 지반침하 프로토타입의 통합플랫폼 결합 방식 (검토 중)

- ADR 번호: 미발급(결정 시 ADR-YYYY-MM-DD.NN)
- 제목: 제주 지반침하 프로토타입 기능의 통합플랫폼 결합 방식
- 상태: 제안(검토 중, 미결정)
- 일자: 2026-10-16(작성 기준일)
- 결정자: <mark>확인 필요</mark>

**1. 맥락** — 프로토타입(`Jeju-subsidence-AI`)은 통합플랫폼에 올릴 기능의 **참조 기준**이다. 지도 레이어 6종(위험등급(CSI)·지반 변위·관로·굴착공사·침하 사고이력·재해위험지구)뿐 아니라 데이터를 보여 주는 모듈(순위·상세·등급 분포·분석 설정·내보내기)과 데이터 표현 방식의 예시를 담고 있다. 이 밖에 관리자 화면(역할별 레이어·내보내기 권한 설정, 사고 이력 관리, 작업 기록)이 있으나 참조 기준으로 다루지 않았고, 모두 브라우저 저장이며 서버 집행이 없다. 통합플랫폼 FR-01~03·FR-09 와의 겹침과 사고 이력 자료의 소유는 결합 방식 결정 때 판단한다(<mark>확인 필요</mark>). 통합플랫폼은 분해를 결정했으나 분리 이미지는 아직 없는 모듈러 모놀리식(ADR-2026-08-26.01)이며, 현재 단계는 프로토타입 분석 및 결합 방식 검토 중이다. M010·WBS 스냅샷은 분석 알고리즘·UI/UX·리포트(ID 9~31)를 개발팀 범위 밖(타 팀 소관)으로 분류하나 WBS 담당 조직 열은 ID 29~31(분석 리포트 자동 구현)을 개발로 적어 어긋나므로, 결합 범위와 담당도 정해야 한다.
