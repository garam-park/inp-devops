## 1. 목적

통합플랫폼의 설계·개발 표준·시험·배포·운영·인증·관리 문서를 어디에 어떤 규칙으로 두는지 정한다. 문서는 별도 위키 도구가 아니라 저장소 안의 파일로 Git 에서 버전 관리하며, 형식은 **마크다운이 기본**이다(예외: WBS 는 Excel `docs/WBS.xlsx`, 주간업무보고 일부는 HWPX, 월간·중간보고 일부는 txt). 변경을 반영하는 방식은 저장소마다 다르며 4절에 적었다. WBS 제출 산출물(`docs/90.관리/산출물/`)은 개발팀 내부 문서(ADR·API·규칙·테스트 문서)와 폴더를 나눠 두어, 제출 시점에 무엇을 내보내도 되는지 판단하지 않도록 한다(`산출물/README.md`). 예외가 둘 있다. `산출물/CSAP/` 에는 제출 문서가 아니라 작성 근거·준비 자료(해설서, 작성 양식)가 함께 있고, 주간보고는 내부용과 외부공유용 파일이 `보고/주간보고/{월}/` 에 같이 있다.

통합플랫폼(제주위성AI) 관련 문서가 있는 저장소는 세 개이고(아래 표), 이 문서가 놓인 워크스페이스 저장소(`inp-devops`)에는 여러 저장소에 걸친 작업의 기록(`docs/history/`)과 현장방문 대비 문서가 따로 있다(2절 끝). 같은 워크스페이스의 `official-website`(회사 홈페이지)는 범위 밖이다.

| 저장소 | 역할 | 문서 |
| --- | --- | --- |
| `gis-sass` | 통합플랫폼 본체(제품 코드·배포·작업 계획 포함) | 아래 2절 |
| `dev0` | 사내 개발·스테이지 클러스터 운영 | `docs/architecture/`(구조), `docs/operations/`(접속·백업·재구축·업그레이드), `docs/reports/`, `docs/history/`(작업 기록) |
| `Jeju-subsidence-AI` | 제주 지반침하 프로토타입(참조 기준 자료) | `README.md`(화면 구성·데이터·위험도 산정), `docs/CSI_산정근거.*` |

## 2. 디렉터리 구조

통합플랫폼 저장소(`gis-sass`)의 주요 문서 위치다. 코드 옆에 둔 README(`dagger/`, `apps/*/database/`)는 생략했다.

```text
gis-sass/
├── AGENTS.md                 저장소 진입점(구조·규칙·작업 절차)
├── RELEASE-NOTES.md          릴리스 노트(원본), VERSION(버전 기준)
├── planning/                 마일스톤·작업·WBS 스냅샷·아카이브(작성 규칙은 `.ai-workflow/docs/planning-guide.md`)
├── deploy/                   배포 문서(README.md)와 Helm chart
├── scripts/                  smoke·CI 스크립트(사용법은 `docs/TESTING.md`)
└── docs/
    ├── 01.개발/
    │   ├── ADRs/             결정 기록(runtime·repository·backend·frontend·auth·authorization·deployment·code-sharing·map·architecture)
    │   └── APIs/customer/    API 계약(auth·organizations·map·ingest)
    ├── 03.운영/
    │   └── dev-stg/          사내 개발·스테이지 클러스터 설계와 운영 보고(kubernetes-관리)
    ├── 90.관리/
    │   ├── 보고/             주간·월간·중간보고
    │   └── 산출물/           WBS 제출 산출물(서버 및 인프라 아키텍처 설계서, CSAP 문서 4종)
    │       └── CSAP/         제출 문서가 아니라 CSAP 작성 자료(KISA 해설서 원본·하등급 SaaS 정리본 각 30건, 작성 양식 188건)
    ├── CSAP/                 CSAP 양식 작성 목록과 작성 팁
    ├── rules/                코딩·Git·워크플로 규칙(coding·git·workflow)
    ├── WBS*.xlsx             WBS(Excel)
    └── TESTING.md            테스트 절차의 단일 진입점
```

현장방문 대비 문서는 워크스페이스 저장소의 `.ai-workflow/work/tasks/현장방문대비/` 에 둔다(`10 원천데이터` 점검표, `20 중간산출` 빈 양식, `30 관리 산출물` 작성본). `10 원천데이터/참고/` 는 외부 참고자료용 폴더이며, 용량이 크고(100MB 초과 파일 포함) 외부 산출물이라 `.gitignore` 로 git 에서 제외한다. 그래서 이 폴더의 내용은 저장소에 올라가지 않는다. 워크스페이스 저장소의 작업 기록은 `docs/history/` 에 남긴다.

## 4. 작성·갱신 규칙

- 문서번호는 `JSA-{시스템}-{분류}-{일련번호}` 를 따른다. 현장방문 점검표의 문서번호와 같으며, 두 점검표(다. 공정관리, 라. 산출물)에 모두 있는 문서는 같은 번호로 한 번만 작성한다.
- 문서 상단에 문서번호·버전·작성자를 적고, 제·개정 이력을 둔다. 양식 파일명은 `{문서번호}_{문서명}` 이며 버전은 파일명이 아니라 표지와 이력에 적는다.
- 변경을 반영하는 방식은 저장소마다 다르다. gis-sass 는 develop·main 으로의 모든 머지를 PR 로 하는 것이 규칙이다(혼자 작업해도 마찬가지). 마크다운 린트와 문서 링크 검사는 gis-sass 의 CI `docs` 잡이 PR 과 develop·main push 마다 실행한다. dev0 와 워크스페이스 저장소(inp-devops)는 PR 없이 커밋하고, 커밋 전 훅(lefthook)이 로컬에서 markdownlint 를 돌린다.
- 제출 문서(`docs/90.관리/산출물/`, `CSAP/` 제외)는 제출본을 정리할 때 한국어로 쓰고, 내부 상대 링크에 의존하지 않으며, 다이어그램은 텍스트 소스(Mermaid)로 관리하고, 비밀과 개인정보를 넣지 않는다. 문서 이력(버전·작성일·작성자)을 넣는다.
- 설계서는 "무엇이 어떻게 되어 있는가", ADR 은 "왜 그렇게 정했는가"를 적는다. ADR 을 제출 문서에 복사하지 않는다.
- ADR·마일스톤·Task 번호는 한 번 쓴 뒤 재사용하지 않는다. 확정한 ADR 은 결정 본문을 다시 쓰지 않는 것을 원칙(관례)으로 하고, 결정이 바뀌면 새 ADR 로 대체하면서 옛 ADR 머리에 변경·대체 표기만 덧붙인다(예: ADR-2026-08-11.06 이 ADR-2026-08-10.02 의 배치 부분을 대체). 결정의 뼈대가 그대로인 경계·예외 보완은 날짜를 적은 '갱신 노트'나 '예외' 항목으로 같은 ADR 안에 남긴다(예: ADR-2026-08-12.01, ADR-2026-09-01.02).
- 작업 기록(`docs/history/`)은 지난 기록을 고치지 않고 새 기록으로 대체하며, 옛 파일 맨 위에 `> 대체됨: <새 파일>` 한 줄만 추가한다(워크스페이스 저장소 `AGENTS.md`).
- 사실이 바뀌면 문서를 고치고, 근거가 없는 항목은 지어내지 않는다.
