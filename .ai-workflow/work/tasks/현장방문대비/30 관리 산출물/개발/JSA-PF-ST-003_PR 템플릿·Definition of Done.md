## 1. Pull Request 템플릿

PR 은 아래 규칙을 따라 작성한다.

- 제목은 커밋 메시지와 같은 Conventional Commits 형식이다(`타입(범위): 제목`, 50자 이내 권장).
- 한 PR 은 한 가지 목적만 갖는다. 기계적 변경(이름 변경·포맷팅·이동)은 별도 PR 로 분리하고, 리팩토링과 기능 변경도 섞지 않는다.
- 본문에는 무엇을·왜 바꿨는지를 적는다. 제목에 내부 작업 번호를 함께 적는 경우가 많다.

아래는 기본 PR 템플릿이다.

```markdown
## 요약
(무엇을, 왜 바꿨는가)

## 변경 내용
-

## 관련 이슈
closes #

## 테스트
- [ ] 단위 테스트 추가·수정
- [ ] 로컬에서 동작 확인

## 스크린샷(화면 변경 시)
```

## 2. Definition of Done

작업은 아래 조건을 모두 만족할 때 완료로 본다. 근거 규칙 문서가 있는 항목은 끝에 적었다.

- [ ] 작업 문서(Task)에 적은 완료 조건과 검증 방법을 충족한다 — `AGENTS.md` §5(플래닝·작업 절차)
- [ ] 테스트를 추가·수정했고 CI 가 통과한다 — `test.md`, `pull-request.md`
- [ ] 버그를 고쳤다면 그 버그를 재현하는 테스트를 남겼다 — `test.md`
- [ ] 셀프 리뷰를 마쳤다(diff 를 처음부터 끝까지 다시 읽었고, 이해하지 못한 줄이 없다) — `pull-request.md`
- [ ] 관련 문서(API 문서·ADR·설계서·`docs/TESTING.md`)를 갱신했다
- [ ] 완료된 Task 문서를 아카이브로 옮기고 현황판(index)의 상태를 갱신했다 — `AGENTS.md` §5
- [ ] 요구사항·이슈의 인수 조건을 만족한다
- [ ] 보안·성능 영향을 확인했다
- [ ] 체인지로그에 반영했다 — `release.md`(태그 사이의 커밋 로그가 체인지로그이므로 PR 제목·커밋을 Conventional Commits 형식으로 쓴다. 별도 CHANGELOG 파일은 두지 않고, 릴리스 때 `RELEASE-NOTES.md` 와 GitHub Release 를 쓴다)

## 3. 리뷰 규칙

- 리뷰어 수: 셀프 리뷰(규칙 문서 기준).
- 리뷰 기한: 셀프 리뷰는 작성 직후보다 하루 묵혀서 보는 것을 권장한다.
- 머지 방식: merge commit(`--no-ff`)만 쓴다. squash merge 와 rebase merge 는 쓰지 않는다(저장소 설정 + `lint-git` 사후 검출).
- 머지 조건: CI 통과(문서·API 단위·통합·web·배포물 검증 잡) + 셀프 리뷰(JSA-PF-ST-002 4절).
- 크기 기준: 줄 수가 아니라 "사람의 리뷰 용량" — 한 번의 셀프 리뷰 세션에서 전부 이해하고 검증할 수 있는 단위.
