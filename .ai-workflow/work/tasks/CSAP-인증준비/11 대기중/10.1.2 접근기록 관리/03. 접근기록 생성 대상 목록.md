> - **api 인증·감사 기록(`audit_events`)·DB 구현** → 2항 No 3·4·5의 행위 기록 위치 확정, 3항 No 3·4·5 기록 항목 충족 표본 확인
> - **NCP 운영 환경 구축(Cloud DB for PostgreSQL, Load Balancer, 배스천·VPN)** → 2항 No 2·3·11의 로그 위치·전송 방식 실측, 3항·4항의 해당 행. NKS 는 2026-10-21 구축했고 감사 로그를 켰으나, 감사 로그의 저장·보존 위치는 미구성이다(2항 No 1 전송 방식, 3항·4항 No 1)
> - **접근기록 저장소 선택·구성(NCP Cloud Log Analytics 또는 Object Storage 별도 버킷, 객체 잠금·백업)** → 1항 저장소·백업 위치, 4항 전 행(전송·삭제 방지·무결성·백업·용량), 5항 권한 부여
> - **NCP Cloud Activity Tracer·NKS 감사 로그 수집 옵션의 제공 범위 확인** → 2항 No 1·6 생성 위치, 3항 No 1·6
> - **GitHub 조직 감사 로그의 플랜별 제공 범위·보존 기간 확인과 월 1회 내보내기 체계** → 2항·3항·4항 No 9
> - **첫 월별 검토(JAS-10.1.2-04)** → 1항 최근 검토 기록, 7항 대조 결과
> - 2026-10-21 인프라 1차 구축(VPC·NAT·NKS) 반영

> [!note] 현 구현과 차이 (2026-10-20)
> 현재 `jeju-ai-saas-be` api 에는 인증·권한·감사 기록·DB 가 없고, Fastify 요청 로그(요청 ID·메서드·URL·원격 주소·상태 코드)를 stdout 으로만 낸다. 접근 주체를 식별할 수 없고, 로그 수집·별도 보관이 없어 파드가 재생성되면 로그가 사라진다. 사내 `dev0` 클러스터(인증 대상 아님)의 접근은 공용 관리자 kubeconfig·Argo CD `admin` 계정으로 이루어져 개인 식별이 되지 않으므로, 운영 환경에서는 이 방식을 쓰지 않는다.

- 신규 시스템 도입·변경·폐기 통보를 받으면 5영업일 이내에 목록을 갱신하고 버전을 올린다.
