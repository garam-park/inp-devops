> [!info] 법령 기준
> 세부 보안 요구사항은 「국가 사이버보안 기본지침」 제24조의4와 「클라우드 컴퓨팅 보안 가이드라인」(국가정보원)을 준수한다. 두 문서는 비공개·수시 개정 문서이므로 문서명 기준으로 인용하며, 국가기관등 이용 기관이 최신 요구사항을 제시하면 그에 따라 본 대책을 갱신한다.

## 1. 목적

㈜이노팸은 클라우드컴퓨팅서비스 지반침하 스마트관리 시스템(이하 "서비스", 하등급 SaaS)이 국가기관등의 보안수준을 만족할 수 있도록 해설서 점검항목 해설의 보안성 강화 방안을 본 문서로 수립하고 운영·점검한다.

## 2. 적용 범위

- 서비스 인증 범위 내 응용 프로그램(web · api · pipeline), 데이터(DB · Object Storage, 백업 포함), 서버(NKS 워커 노드와 파드), 네트워크 설정(LB · Ingress · ACG · NetworkPolicy)
- 국가기관등에 제공하는 서비스에서 처리되는 기관의 중요 데이터 전체 — 데이터셋 번들(위험도 격자·후보지·지표변위), 민감 레이어(관로 · 굴착), 사고 기록, 감사 기록, 내보내기 파일

## 3. 대책별 현황

### 3.1 데이터 처리 과정의 데이터 보호 방안

애플리케이션의 데이터 처리(송·수신, 저장, 연산 등) 과정에서 데이터를 보호한다.

| 처리 과정 | 보호 대책 | 적용 대상·설정 | 확인 방법 |
| --- | --- | --- | --- |
| 송·수신 | TLS 1.2 이상 암호화 통신 채널 적용(취약 프로토콜 비활성, HSTS 1년). 브라우저는 스토리지를 모르고 모든 요청이 Ingress → `/api` 단일 경로를 지난다 | 이용자 ↔ LB/Ingress, api ↔ Cloud DB(`sslmode=require`), api · pipeline ↔ Object Storage(HTTPS), 관리자 접속(VPN) | TLS 스캔 결과, 응답 헤더 시험(`e2e/headers.spec.ts`), DB 연결 설정 |
| 저장 | 저장 데이터 암호화(관리형 DB · Object Storage 서버측 암호화 AES-256, 비밀번호 Argon2id, 비밀값 k8s Secret). 검증필 암호모듈 기준은 14.3.1 산출물을 따름 | Cloud DB for PostgreSQL, Object Storage 버킷(`raw/` · `datasets/` · `exports/` · `incidents/uploads/` · `backups/`) | 암호화 설정 화면 |
| 연산·처리 | 처리 중 데이터 접근통제 — 역할별 권한(`role_permissions`), 세션 관리, 레이어 파일은 api 가 권한 검사 후 중계. pipeline 은 역할별 자격 증명(읽기 `raw/`, 쓰기 `datasets/` · `exports/`)만 쓰고, 지수 로직은 격리 컨테이너(네트워크 없음 · 루트 읽기 전용 · 권한 제거 · nobody · 자원/시간 제한)에서 실행. 작업 디스크는 emptyDir 이라 작업이 끝나면 지워진다 | api 권한 가드, pipeline 워커, `pipeline/run_index.py` | 권한 설정, 처리 로그, 실행기 단위 테스트 |
| 출력·다운로드 | 내보내기는 역할의 `export` 권한(`geojson` · `csv` · `report`)을 가드가 검사하고, 다운로드는 본인 또는 관리자만, 생성·다운로드 모두 감사에 기록(민감 레이어 열람 플래그). 응답은 `private, no-store`. 파일은 30일 뒤 lifecycle 규칙으로 삭제 | `POST /api/exports`, `GET /api/exports/{id}/download` | 권한 설정, 감사 기록(`audit_events`) |

> [!note] 현 구현과 차이
> 2026-10-20 현재 권한 검사·감사·내보내기 API 는 없다(레이어 파일 중계는 권한 없이 조회 전용). 내보내기는 화면이 브라우저 안에서 만든다. 지수 레이어 격리 실행과 송신 헤더(HSTS)는 구현돼 있다.

### 3.2 데이터 무결성 확인 방안

기관의 중요 데이터에 대한 입·출력, 전송 또는 교환 및 저장 과정에서 데이터가 변조되지 않았음을 확인한다.

| 과정 | 무결성 확인 대책 | 적용 대상·설정 | 확인 방법 |
| --- | --- | --- | --- |
| 입·출력 | 입력값 검증(라우트 스키마 · 슬러그 · 경로 검증, 업로드 매직 바이트 · 크기 · zip 경로 검사), 업로드 원본 목록에 파일별 sha256 기록(`raw/{upload_id}/manifest.json`), 지수 실행 결과 검사(JSON 만 · 크기 상한 · 링크 금지) 후 통째 교체, 내보내기 행에 조건·건수·해시 기록 | 파일 업로드, 데이터셋 빌드, 내보내기 | 검증 로직, 단위·통합 테스트, `exports` 표 |
| 전송·교환 | TLS 무결성 보장(AEAD 스위트 MAC), 파일 중계 응답의 ETag(번들은 sha256)로 클라이언트·스토리지 사이 동일성 확인, 스토리지 동기화는 md5(ETag) 비교로 전송 검증 | 레이어·번들 파일 중계, 스토리지 동기화 | TLS 설정, 통합 테스트(pull 사본 md5 일치) |
| 저장 | 데이터셋 번들 · 원본 · 내보내기 · 백업은 불변 키(같은 키에 다시 쓰지 않음), DB 무결성 제약, 사고 기록 변경 이력(`incident_revisions` 전후 값), 감사 표 추가 전용 권한(INSERT · SELECT 만) | Object Storage 접두사, Cloud DB 주요 표 | 스키마, 변경 이력, DB 권한 설정 |
| 백업 | 백업 무결성 검증 — 백업 파일 해시 기록과 반기 1회 복구 시험(RPO 24시간 · RTO 4시간 확인) | DB 자동 백업, `backups/postgres/` | 백업 검증 기록(14.2.2 산출물과 연계) |

### 3.4 서버의 서비스별 분리

인증 범위 내 서버는 각각 최소한의 목적을 유지하도록 서비스별로 분리한다. 서비스는 관리형 k8s(NKS) 위의 컨테이너로 동작하므로 분리 단위는 워크로드(Deployment)·네임스페이스·관리형 서비스다.

| No | 서버(자원명) | 역할·목적 | 실행 서비스 | 분리 방식 | 다목적 사용 여부 |
| --- | --- | --- | --- | --- | --- |
| 1 | NKS {{클러스터명 — 생성 후}} / Deployment `web`(복제 2) | 웹 | nginx(`nginx-unprivileged`) 정적 화면 + `/api/` 프록시 | 컨테이너 분리, 전용 Service, NetworkPolicy | 아님 |
| 2 | NKS / Deployment `api`(복제 2) | 애플리케이션 | Node.js(Fastify) API — 인증·권한·감사·중계 | 컨테이너 분리, 전용 Service, NetworkPolicy(DB · 스토리지 · 브이월드 egress 만) | 아님 |
| 3 | NKS / Deployment `pipeline`(복제 1) | 데이터 처리 | Python 워커(데이터셋 빌드 · 지수 실행) | 컨테이너 분리, 외부 진입 경로 없음, NetworkPolicy(DB · 스토리지 egress 만) | 아님 |
| 4 | Cloud DB for PostgreSQL {{인스턴스명 — 생성 후}} | DB | PostgreSQL + PostGIS | 관리형 서비스, 사설 서브넷 | 아님 |
| 5 | Object Storage {{버킷명 — 생성 후}} | 파일 저장 | 번들 · 원본 · 내보내기 · 백업 | 관리형 서비스, 사설 엔드포인트, 역할별 자격 증명 | 아님 |
| 6 | NCP Cloud Log Analytics 또는 로그 전용 버킷 | 로그·모니터링 | 접근기록 · 감사 · 인프라 로그 보존 | 관리형 서비스, 원본 시스템과 분리 | 아님 |

- 한 서버가 여러 목적을 겸하는 경우: 해당 없음. NKS 워커 노드는 여러 파드를 함께 싣지만 파드마다 PSA `restricted`(비루트 · `readOnlyRootFilesystem` · `drop: [ALL]` · seccomp `RuntimeDefault` · `automountServiceAccountToken: false`)와 자원 제한으로 격리하고, 노드는 서비스 전용 클러스터에만 쓴다(다른 제품·민간 워크로드 미배치).
- 공공용과 민간용 영역의 분리는 14.2.1 물리적 위치 및 영역분리 항목의 산출물을 따른다.

### 3.5 불필요 IP·포트 제거·차단

개발 및 운영에 불필요한 IP·포트 등을 제거·차단한다.

| 통제 | 내용 | 점검 주기 |
| --- | --- | --- |
| 허용 목록 원칙 | ACG · NetworkPolicy 는 필요한 출발지·포트만 허용하고 전체 허용(`0.0.0.0/0` any) 규칙을 금지한다(공개 LB 의 443 · 80→443 리다이렉트 제외). NetworkPolicy 는 인·아웃 기본 거부 후 DNS · DB · 스토리지 · 브이월드 443 만 연다. 사설·루프백·링크로컬 대역 egress 는 차단한다 | 규칙 변경 시, 분기 정기 검토 |
| 서비스 포트 최소화 | 공개 진입은 LB → Ingress 의 443 하나. web(8080) · api(8787)는 클러스터 내부 Service 로만 노출하고 관리 포트·DB · 스토리지 · pipeline 은 공개하지 않는다. 컨테이너 이미지는 앱 프로세스 하나만 실행한다(api 이미지는 npm · corepack 제거) | 분기 포트 점검 |
| 관리용 접근 제한 | NKS API · 배스천 · Cloud DB 관리 접근은 사내 VPN 대역 출발지로 한정한다(ACG · NKS API 허용 CIDR). 노드 SSH 는 열지 않는다 | 규칙 변경 시 |
| 미사용 자원 정리 | 미사용 공인 IP, 미사용 LB · 자원 · 계정(서브 계정 · DB 계정 · 스토리지 키)을 회수한다 | 분기 |
