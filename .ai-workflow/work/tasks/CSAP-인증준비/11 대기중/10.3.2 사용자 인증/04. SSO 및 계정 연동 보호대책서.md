## 1. 목적

싱글사인온 등 여러 클라우드 시스템에 대한 인증을 하나의 인증으로 처리하는 방식은 인증 지점이 병목이 되고, 인증정보·토큰이 도용되면 연동된 모든 시스템으로 피해가 확대될 수 있다. 본 문서는 ㈜이노팸의 SSO·계정 연동 구성을 식별하고, 중요 시스템 재인증·다중 인증, 토큰·세션 보호, 권한 승계 최소화, 인증 로그 모니터링으로 그 위험을 통제하는 별도 보호대책을 정한다.

## 3. 보호대책

### 3.1 IdP 자체 보호

당사는 자체 IdP 를 운영하지 않는다. NCP IAM 은 제공자 기능의 당사 계정 설정을, 발주처 IdP 는 연동 설정과 이용 기관 확인을 대상으로 한다.

| 통제 | 기준 | 적용 |
| --- | --- | --- |
| IdP 로그인 다중 인증 | NCP 메인 계정·모든 Sub Account 에 2차 인증 필수(TOTP 앱 또는 하드웨어 토큰, 문자 단독 금지). 발주처 IdP 는 이용 기관의 다중 인증 적용 여부를 확인서로 확보 | {{○ / X — 계정 개설·연동 후}} |
| IdP 관리자 계정 분리 | NCP IAM 관리 권한(Sub Account·정책 관리)은 일상 운영 계정과 분리하고 2.1.2 주요 직무자로 지정, 관리자 2명 이내. 메인 계정은 봉인 | {{○ / X — 계정 개설 후}} |
| 서명·암호화 키 보호 | NCP 인증키는 개인별·90일 교체, 발주처 OIDC 클라이언트 비밀은 k8s Secret(SealedSecrets 봉인)으로만 주입하고 연 1회·유출 의심 시 즉시 교체 | {{○ / X — 구축 후}} |
| 연동 등록 통제 | OIDC 클라이언트 등록·변경은 JAS-10.3.2-02 12항 검토와 정보보호 관리자 승인 후 수행, 리다이렉트 URI 를 정확히 지정(와일드카드 금지) | {{○ / X — 연동 시}} |
| 가용성·대체 인증 | 발주처 IdP 장애 시 당사 자체 계정 + TOTP 로그인을 유지한다(1차 인증 방식 유지). NCP IAM 장애 시 봉인된 비상 Sub Account(2차 인증 적용, 사용 시 CISO 승인·기록) | {{○ / X — 구축 후}} |
| IdP 설정 변경 기록 | NCP IAM 정책·인증키 변경은 Cloud Activity Tracer 로, OIDC 설정 변경은 PR·배포 기록과 `audit_events` 로 남기고 변경 관리 절차 준수 | {{○ / X — 구축 후}} |

### 3.2 시스템 중요도별 재인증·다중 인증

| 시스템 중요도 | 기준 | 접근 전 추가 인증 | 세션 |
| --- | --- | --- | --- |
| 높음(서비스 관리자 기능, NCP 콘솔, NKS 클러스터, 접근기록 저장소, 사고 기록 처리 기능) | 관리자 권한 또는 개인정보·이용 기관 데이터 접근 | SSO 세션이 있어도 관리 역할 로그인 시 당사 TOTP 를 요구하고, 권한 변경·대량 내보내기·데이터셋 활성화 전 재인증 | 유휴 30분, 최대 12시간 |
| 중간(이용자 `user` 기능) | 지도·위험도 조회, 일반 내보내기 | 최초 SSO 인증, 민감 레이어·대량 내보내기 전 재인증 | 유휴 30분, 최대 12시간 |
| 낮음(일반 협업 도구) | 해당 없음 — SSO 로 연동한 낮음 시스템 없음 | 해당 없음 | 해당 없음 |

- IdP 에서 다중 인증을 한 번 통과했더라도 높음 시스템은 IdP 세션 기간이 아니라 시스템 접근 시점의 다중 인증(OIDC `prompt=login`·`max_age` 또는 당사 TOTP)을 적용한다.
- 이용 기관 서비스 관리자가 기관 SSO 로 로그인하는 경우 관리 기능 접근 전 당사 TOTP 를 기본 적용하고, 이용 기관이 자체 IdP 의 다중 인증을 증명하면 계약으로 조정한다.

### 3.3 토큰·세션 보호

| 통제 | 기준 | 적용 |
| --- | --- | --- |
| 토큰 서명·암호화 | OIDC ID 토큰은 IdP 공개키(JWKS)로 서명 검증하고 승인된 비대칭 알고리즘(RS256·ES256)만 허용(`none`·대칭 키 공유 금지), 전 구간 TLS 1.2 이상. 발주처 SSO 가 SAML 이면 브로커(Keycloak)로 받아 OIDC 로 연동하고, 브로커를 2.1 에 IdP 로 추가해 3.1 기준(관리자 다중 인증·키 보호)을 적용한다(제품 설계 05 §3 리스크 표) | {{○ / X — 연동 시}} |
| 유효기간 제한 | ID 토큰은 로그인 시 1회 검증 후 저장하지 않는다. IdP 액세스·리프레시 토큰은 요청·보관하지 않는다(당사 세션은 서버 세션, 유휴 30분·최대 12시간). NKS 클러스터 토큰은 제공자 단기 토큰을 쓰고 인증키는 90일 교체 | {{○ / X — 구축 후}} |
| 수신자·발급자 검증 | `aud`·`iss`·`nonce`·`state` 검증, 인가 코드 PKCE 적용, 시계 오차 허용 60초 이내 | {{○ / X — 연동 시}} |
| IP·단말 기반 검증 | 세션 발급 시 접속 IP 를 기록하고(`audit_events.ip`) 국가가 바뀌면 재인증 요구. 관리 라우트·운영 콘솔은 허용 목록 외 IP 접근 차단 | {{○ / X — 구현 후}} |
| 세션 고정·하이재킹 방지 | 인증 성공 시 세션 식별자 재발급, 쿠키 `Secure`·`HttpOnly`·`SameSite=Lax`, CSRF 토큰, URL 파라미터로 토큰 전달 금지 | {{○ / X — 구현 후}} |
| 로그아웃·강제 종료 | 당사 로그아웃 시 서버 세션 폐기. 퇴직·권한 회수 시 당사 계정 비활성화로 세션 즉시 폐기, NCP Sub Account·인증키 즉시 삭제 | {{○ / X — 구현 후}} |
| 토큰 저장 | 브라우저 로컬 저장소에 토큰을 두지 않고 HttpOnly 쿠키만 쓴다. OIDC 클라이언트 비밀은 k8s Secret 으로만 주입 | {{○ / X — 구현 후}} |

### 3.4 권한 승계 범위 최소화

| 통제 | 기준 | 적용 |
| --- | --- | --- |
| 속성 전달 최소화 | IdP 가 전달하는 속성은 식별자(`sub`)와 소속만 받는다. 실명·이메일·전화 등 개인정보 속성은 요청하지 않는다(하등급 조건) | {{○ / X — 연동 시}} |
| 기본 권한 최소 | 매핑되지 않은 OIDC 사용자는 접근 거부. 자동 계정 생성(JIT)을 하지 않고 `admin` 이 사전 발급한 계정에 `oidc_sub` 를 연결한다 | {{○ / X — 연동 시}} |
| 관리자 권한 비승계 | IdP 클레임·그룹으로 `admin`·`service` 역할을 자동 부여하지 않는다(역할 출처는 로컬 표). NCP IAM 관리 권한이 클러스터 관리자 권한으로 자동 승계되지 않게 별도 그룹으로 매핑 | {{○ / X — 결정·구축 후}} |
| 매핑 승인·검토 | 역할 부여와 IAM 그룹 → 클러스터 RBAC 매핑 변경은 2.1.2 주요 직무자 지정 절차와 동일하게 신청·승인하고 반기마다 검토 | {{○ / X — 구축 후}} |
| 해지 동기화 | 당사 계정 비활성화는 즉시 반영(세션 폐기). 발주처 IdP 에서의 비활성화는 다음 로그인부터 반영되므로, 이용 기관은 퇴직·전보를 당사에 통보하고 당사는 통보 당일 계정을 비활성화한다 | {{○ / X — 연동 시}} |
| 클라우드 콘솔 연동 | NCP Sub Account 권한은 직무별 최소 권한으로 정의하고 관리자 권한 사용자는 2.1.2 주요 직무자에 한정 | {{○ / X — 계정 개설 후}} |

### 3.5 이용 기관 IdP 연동 절차(제공하는 경우)

1. 이용 기관이 기관 IdP 정보(발급자 `issuer`, 디스커버리 주소, 클라이언트 등록 정보)를 공문으로 제출하고, 당사는 이용 기관 관리자 신원과 도메인 소유를 확인한다.
2. 당사는 서명 알고리즘과 키(JWKS), 토큰 유효 창, 필수 속성(식별자·소속)만 수신하도록 설정하고 시험 계정으로 연동을 검증한다.
3. 서비스 관리자 기능은 3.2항에 따라 당사 TOTP 를 적용하고, 이용 기관의 다중 인증 적용 여부를 계약·확인서로 확보한다.
4. 기관 IdP 서명 키·클라이언트 비밀 만료 30일 전에 이용 기관에 갱신을 안내하고, 만료·유출 시 연동을 즉시 중단할 수 있는 절차와 대체 로그인(당사 계정 + TOTP)을 유지한다.
5. 연동 등록·변경·해지 이력을 기록하고 반기마다 미사용 연동을 정리한다.

## 4. SSO 인증 로그 모니터링 및 이상 탐지

### 4.1 수집 항목

| 항목 | 내용 | 수집 위치 |
| --- | --- | --- |
| 인증 이벤트 | 성공·실패, 실패 사유 코드(내부 기록용), TOTP 성공·실패, 재인증 | `audit_events`(서비스), k8s API 감사 로그(NKS) → 접근기록 저장소 |
| 사용자 정보 | 사용자 식별자(`users.id`·`oidc_sub`), 역할, 대상 시스템 | `audit_events`, k8s 감사 로그 |
| 접속 정보 | 출발지 IP, 국가 | `audit_events.ip`, Ingress 접근 로그 |
| 토큰 이벤트 | 세션 발급·만료·폐기, NCP 인증키 생성·삭제 | `audit_events`, Cloud Activity Tracer |
| 관리 이벤트 | OIDC 클라이언트 설정 변경, NCP IAM 정책·그룹·인증키 변경, 관리자 로그인 | Cloud Activity Tracer, PR·배포 기록 |

- SSO 인증 로그는 일반 서비스 로그와 구분해 접근기록 저장소에 수집하고, 접근기록 보관 기준(10.1.2)에 따라 서비스 인증 로그는 3년, NKS·NCP IAM 로그는 1년 이상 보관한다.
