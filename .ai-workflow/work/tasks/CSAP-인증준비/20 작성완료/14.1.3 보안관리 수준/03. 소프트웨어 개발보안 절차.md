> [!info] 법령 기준
> 행정기관 및 공공기관 정보시스템 구축·운영 지침 제6장 소프트웨어 개발보안 제50조–제53조(행정안전부고시 제2025-1호, 2025. 1. 2. 시행)와 「소프트웨어 개발보안 가이드」(행정안전부, 문서명 기준)를 기준으로 작성했다. 고시가 개정되면 국가법령정보센터에서 조문을 다시 확인한다.

## 1. 목적

㈜이노팸은 국가기관등이 이용하는 클라우드컴퓨팅서비스 지반침하 스마트관리 시스템(이하 "서비스", 하등급 SaaS)을 소프트웨어 개발 단계부터 보안취약점의 원인인 보안약점을 배제하여 개발·변경하도록 본 절차를 수립·운영한다.

## 2. 적용 범위

- 서비스 인증 범위 내 응용 프로그램·API 의 신규 개발과 변경(유지관리)으로 생기는 설계 산출물과 소스코드 전체 — `jeju-ai-saas-be`(api: TypeScript, pipeline: Python), `jeju-ai-saas-fe`(web: TypeScript · React)
- 서비스 동작에 영향을 주는 인프라 코드와 빌드·배포 스크립트 — Dockerfile, nginx 설정, Helm chart · 클러스터 values, GitHub Actions 워크플로, `mise.toml` 작업
- 상용 소프트웨어는 보안약점 진단 대상에서 제외하되, 취약점 패치 관리 대상으로 관리한다(서비스는 상용 소프트웨어를 쓰지 않는다. 관리형 서비스 NKS · Cloud DB · Object Storage 는 제공자 책임). 오픈소스 라이브러리·기본 이미지는 알려진 취약점(CVE) 점검(npm audit · pip-audit · trivy)으로 관리한다.

## 3. 개발 단계별 보안활동

| 단계 | 보안활동 | 기준·도구 | 산출물 |
| --- | --- | --- | --- |
| 요구사항·설계 | 보안 요구사항 정의, 설계 단계 보안설계 기준 적용(입력값 검증, 인증·인가, 암호화, 에러 처리 등) | 「소프트웨어 개발보안 가이드」 설계 단계 기준, 13.1.2 개발 보안 지침(JAS-13.1.2-01) | 보안 요구사항 정의(JAS-13.1.2-01), 설계 반영표(JAS-13.1.2-03), 설계 검토 기록(PR) |
| 구현 | 시큐어 코딩 표준(JAS-13.2.1-01) 준수, 커밋 훅(gitleaks · 린트), 코드 리뷰 시 보안약점 확인 | 「소프트웨어 개발보안 가이드」 구현 단계 기준, 지침 별표 3 소프트웨어 보안약점 | PR 코드 리뷰 기록 |
| 시험 | 보안약점 진단(semgrep 자동 진단 + 수동 확인), 발견 약점 조치·재진단, 보안 요구사항 시험(13.2.1) | 4항의 진단 기준 | 양식 04. 소프트웨어 보안약점 진단 결과서, 13.2.1 보안 시험 결과서 |
| 배포 | 배포 전 진단 결과와 조치 완료 확인, 미조치 약점의 예외 승인 확인. CI 게이트 실패 시 이미지가 만들어지지 않는다 | 5항의 조치·예외 기준 | 배포 승인 기록(운영: `vX.Y.Z` 태그 + 수동 승인) |
| 운영·유지관리 | 변경된 소스코드에 대한 진단(push 마다), 정기 전체 진단, 야간 동적 점검(ZAP) · 이미지 점검(trivy) | 4항의 진단 주기 | 양식 04. 소프트웨어 보안약점 진단 결과서 |

- 분석·설계 과정에서 도출한 보안 요구사항의 시험과 시큐어 코딩 기준의 상세는 13.2.1 구현 및 시험 항목의 산출물(JAS-13.2.1-01 – 05)과 연계한다.

## 4. 보안약점 진단 기준

### 4.1 진단 항목

지침 별표 3의 소프트웨어 보안약점을 필수 진단 항목으로 포함하고, 「소프트웨어 개발보안 가이드」의 다음 유형을 기준으로 진단한다.

| 유형 | 설명 |
| --- | --- |
| 입력데이터 검증 및 표현 | SQL 삽입, 크로스사이트 스크립트, 경로 조작 등 입력값 검증 부재로 인한 약점 |
| 보안기능 | 인증·접근제어·권한 관리·암호화의 부적절한 구현 |
| 시간 및 상태 | 병렬 처리·상태 관리 오류(경쟁 조건 등) |
| 에러처리 | 에러 메시지를 통한 정보 노출, 부적절한 예외 처리 |
| 코드오류 | 자원 해제 누락, 널 포인터 역참조 등 구현 오류 |
| 캡슐화 | 중요 정보·디버그 코드 노출, 잘못된 세션 관리 |
| API 오용 | 보안에 취약한 API 사용 |

### 4.2 진단 도구와 주기

| 항목 | 내용 |
| --- | --- |
| 진단 도구 | semgrep 1.181.0(규칙셋: BE `p/typescript` · `p/javascript` · `p/python`, FE `p/typescript` · `p/javascript` · `p/react`). 보조: typescript-eslint 타입 규칙(코드오류 · API 오용 일부), TypeScript `strict`(널 역참조 등 코드오류), ruff, gitleaks(캡슐화 — 하드코딩된 비밀), OWASP ZAP(동적 — 입력데이터 검증 · 에러처리). semgrep 레지스트리 규칙은 별표 3 보안약점을 전부 다루지 않으므로, 진단 담당이 별표 3 항목별 "도구 규칙 / 수동 확인" 매핑표를 작성·유지하고(첫 운영 배포 전까지 작성, 규칙셋 변경 시 갱신) 미지원 항목은 수동 확인으로 보완한다. |
| 정기 진단 | 분기 1회 전체 소스코드 진단 결과를 양식 04로 작성(진단 자체는 push 마다 저장소 전체를 대상으로 자동 수행) |
| 수시 진단 | 모든 push(CI `checks` 잡, 실패 시 이미지 생성 차단), 주요 기능 신규 개발 완료 시, 운영 배포 전 변경분 진단 |
| 재진단 | 발견 약점 조치 후 조치 확인 진단(조치 커밋의 CI 실행) |
| 수동 확인 | 도구로 진단하기 어려운 항목(설계 결함, 인가 우회, 조직 간 데이터 분리, 경쟁 조건)은 PR 코드 리뷰와 13.2.1 보안 시험(TC-04 · TC-06 등)으로 확인 |

## 5. 조치와 예외 처리

발견된 보안약점은 심각도에 따라 다음 기한 내에 조치한다.

| 심각도 | 기준 | 조치 기한 |
| --- | --- | --- |
| 상 | 원격 코드 실행, 인증 우회, 중요 정보 노출 등 즉시 악용 가능 | 배포 차단, 14일 이내 조치(긴급 취약점은 72시간) |
| 중 | 악용에 조건이 필요하거나 영향이 제한적 | 30일 이내 조치 |
| 하 | 정보성·심층 방어 관련 | 다음 정기 배포까지 조치 |

1. 기한 내 조치가 불가능한 약점은 사유, 보완 통제, 재검토 기한을 양식 04. 소프트웨어 보안약점 진단 결과서 5항에 기록하고 정보보호 최고책임자의 승인을 받는다.
2. 도구의 지적을 오탐으로 판정해 넘길 때(`nosemgrep` · `eslint-disable` · `.trivyignore`)는 그 자리에 이유를 적고 코드 리뷰에서 승인하며, 시큐어 코딩 표준(JAS-13.2.1-01) 6항 예외 목록에 등재한다.
3. 미조치 약점(예외 승인 포함)이 있는 상태로 운영 배포하려면 배포 승인자가 예외 승인 여부를 확인한다.
4. 조치 완료는 재진단으로 확인하고 결과서에 기록한다.

## 7. 역할과 책임

| 역할 | 책임 |
| --- | --- |
| 정보보호 최고책임자 | 본 절차 승인, 예외(미조치 약점) 승인 |
| 정보보호 관리자 | 본 절차 관리, 진단 결과 검토, 조치 이행 확인 |
| 개발 책임자 | 개발 단계별 보안활동 이행, 조치 수행, 교육 대상 관리 |
| 진단 담당(정보보호 담당자) | 진단 수행, 별표 3 매핑표 유지, 결과서 작성, 재진단 |
| 배포 승인자 | 배포 전 진단 결과·조치 완료·예외 승인 확인 |

- 진단 담당은 가능한 범위에서 조치 수행자(개발자)와 분리하고, 분리가 어려우면 정보보호 관리자가 결과를 검토하는 것으로 보완한다.

## 8. 기록 관리

- 진단·조치·재진단 기록은 양식 04. 소프트웨어 보안약점 진단 결과서로 작성하고 3년 이상 보관한다.
- 진단 도구 실행 결과 원본(CI 로그, 야간 검사 아티팩트 — Actions 보존 30일이므로 결과서 작성 시 내려받는다)은 양식 06. 증적 수집 점검표의 보관 위치(`CSAP-인증준비/30 증적/14.1.3/`)에 보관한다.
- 인증평가 시 소프트웨어 보안약점이 확인되지 않도록, 심사 전 최근 정기 진단과 조치 완료 여부를 확인한다.
