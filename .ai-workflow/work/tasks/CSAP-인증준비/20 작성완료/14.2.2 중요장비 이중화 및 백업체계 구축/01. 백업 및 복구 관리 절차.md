> [!info] 법령 기준
> 행정기관 및 공공기관의 클라우드컴퓨팅서비스 이용 기준 및 안전성 확보 등에 관한 고시 제15조(행정안전부고시 제2025-79호, 2025. 12. 29. 시행)는 행정기관등의 장이 재난·재해, 계약 종료, 사업 중단 등으로 클라우드컴퓨팅서비스가 중단되지 않도록 필요한 조치를 하고, 재난·재해 시 서비스 제공자의 재해복구 서비스를 이용할 수 있도록 정하고 있다. 당사는 공공기관 이용 기관이 이 조치를 이행할 수 있도록 본 절차의 백업·복구 체계를 갖춘다. 국가 사이버보안 기본지침 제92조(재해 복구체계)는 비공개 지침으로 문서명만 적는다. 고시가 개정되면 국가법령정보센터에서 조문을 다시 확인한다.

## 1. 목적

㈜이노팸은 클라우드컴퓨팅서비스 지반침하 스마트관리 시스템(제주 GEO-AI 지반침하 SaaS)의 장애·재해·침해사고 발생에 대비하여 가상자원, 데이터, 설정 정보를 백업하고 복구하는 체계를 수립·운영함으로써 공공기관 이용 기관에 제공하는 서비스의 가용성을 보장한다.

## 2. 적용 범위

- 지반침하 스마트관리 시스템(하등급 SaaS) 인증 범위 내 모든 가상자원(NKS 클러스터·워커 노드, web · api · pipeline 컨테이너), 데이터(Cloud DB for PostgreSQL, Object Storage 의 `raw/` · `datasets/` · `exports/` · `incidents/uploads/`), 설정 정보(Helm chart·values, NetworkPolicy, ACG, Ingress, 비밀값 봉인 키), 소스코드·배포 환경
- 백업의 생성, 보관, 모니터링, 복원 시험과 장애·재해 시 복구 활동 전반
- 인프라의 물리 계층(데이터센터, 물리 장비, 하이퍼바이저)은 IaaS 제공자(네이버클라우드 공공기관용)의 책임 범위이며, 5항의 책임 구분에 따라 제공자 인증·계약으로 확인한다.
- 사내 개발 클러스터 `dev0` 와 로컬 환경은 인증 대상이 아니며 운영 데이터를 두지 않으므로 이 절차의 백업 대상이 아니다(양식 02 3항).

## 3. 용어 정의

| 용어 | 정의 |
| --- | --- |
| 백업 | 장애·재해·침해사고로 인한 손상에 대비하여 가상자원, 데이터, 설정 정보의 사본을 별도 위치에 보관하는 활동 |
| 복원 시험 | 백업본으로 시스템·데이터를 실제로 복원하여 백업의 유효성과 복구 절차의 완전성을 검증하는 활동 |
| RTO(복구 목표 시간) | 서비스 중단 시점부터 복구 완료까지 허용되는 최대 시간 |
| RPO(복구 목표 시점) | 복구 시 허용되는 데이터 손실의 최대 범위(시점 기준) |
| 재해복구(DR) | 주 운영 환경 전체를 사용할 수 없는 상황에서 별도 환경으로 서비스를 복구하는 체계 |
| 백업 세대 | 보관 중인 백업본의 개수. 세대 수만큼 과거 시점으로 복원할 수 있다. |
| 데이터셋 번들 | pipeline 이 원본에서 만든 레이어 파일 묶음(`datasets/{버전}/`). 한 번 쓴 키에 다시 쓰지 않는 불변 객체다 |
| 봉인 키 | SealedSecrets 컨트롤러의 개인키. git 에 저장된 봉인 Secret 을 풀 수 있는 유일한 키다 |

## 6. 백업 대상 선정

1. 백업 대상은 양식 02. 정보자산 및 백업 대상 목록에서 자산 단위로 지정하고, 본 항의 기준을 따른다.
2. 아래 표의 유형은 원칙적으로 백업 대상에 포함한다. 제외할 때는 양식 02의 3항에 사유를 기록하고 정보보호 관리자의 확인을 받는다.
3. 신규 자산을 생성하거나 자산 구성을 변경할 때는 변경관리 절차(13항)에서 백업 대상 여부와 백업 방식을 함께 판단하고, 5영업일 이내에 양식 02에 반영한다.

| 유형 | 백업 대상 |
| --- | --- |
| 가상자원 | 컨테이너 이미지(커밋 SHA·`vX.Y.Z` 태그, 레지스트리 보관), NKS 클러스터·노드 그룹 구성 기록, Helm chart(인프라 구성 코드) |
| 데이터 | Cloud DB for PostgreSQL(계정·권한·감사·사고 기록·데이터셋 버전·작업·내보내기 이력), Object Storage `raw/` · `datasets/` · `incidents/uploads/` · `exports/` |
| 인프라·보안 설정 | ACG(보안 그룹) 규칙, NCP 서브 계정·권한 정책, VPC·서브넷·라우팅, LB·Ingress 설정, NetworkPolicy, DNS, TLS 인증서 |
| 응용·배포 환경 | 소스코드 저장소(`jeju-ai-saas-be` · `jeju-ai-saas-fe`), CI 워크플로(`.github/workflows/`), 클러스터 저장소의 운영 values, 응용 설정(환경변수 이름·기본값) |
| 인증정보·암호키 | 봉인 Secret(git), SealedSecrets 봉인 키, TLS 인증서 개인키. 키 관리 서비스(KMS) 도입 시 그 백업 체계를 따른다 |
| 정보보호시스템 설정 | 웹 방화벽 규칙(공공 WAF 적용 시), 로그 수집 설정, NetworkPolicy·PSA 설정, 보안 응답 헤더 설정(`nginx.headers.conf`) |
| 운영 기록 | 접근기록·감사 로그(`audit_events` 3년, 애플리케이션 로그 1년 — 10.1.2 접근기록 관리 기준) |

## 7. 백업 기준

| 항목 | 기준 |
| --- | --- |
| 백업 유형·주기 | DB: 관리형 자동 백업 일 1회 + `pg_dump` 전체 논리 백업 CronJob 일 1회. Object Storage: 원본·번들·업로드는 불변 객체로 보관(같은 키에 다시 쓰지 않음) + 버킷 버전 관리. 설정·chart·코드: git 에 변경 시마다. 자산별 주기는 양식 02를 따른다. |
| 보관 기간·세대 | 일 단위 DB 백업 30일(30세대) 보관. 주·월 단위 별도 세대는 두지 않는다 — 원본·번들은 불변 보관이라 과거 시점 데이터가 남고, 설정은 git 이력으로 과거 시점을 복원한다. 관리형 자동 백업 보관 기간은 제공자 설정 최대값과 30일 중 짧은 값으로 한다. 감사·로그는 10.1.2 기준(3년·1년). |
| 저장 위치 | 원본과 다른 저장 서비스(DB 백업 → Object Storage `backups/postgres/`)에 보관하고, Multi Zone 이 제공되면 원본과 다른 가용영역에 둔다. 공공기관 이용 기관의 데이터와 그 백업은 국내 공공기관용 리전에만 저장하며 국외·민간 영역으로 복제하지 않는다. |
| 암호화 | 백업 데이터는 저장 시 암호화한다(Object Storage·관리형 DB 서버측 암호화 AES-256, 전송 HTTPS). 암호화 방식과 키 관리는 12.3.1 암호 정책을 따른다. |
| 접근 통제 | 백업 전용 스토리지 자격증명은 `backups/` 쓰기만 허용하고 삭제 권한을 주지 않는다. 백업 저장소 접근 권한은 백업 관리자 등 최소 인원으로 제한하고, 삭제·변경은 정보보호 관리자 승인 후 수행한다. |
| 무결성 확보 | 백업본의 임의 삭제·변조를 막기 위해 버킷 버전 관리, 백업 자격증명 분리(삭제 권한 없음), 제공자가 지원하면 객체 잠금(WORM)을 적용한다. `pg_dump` 결과는 SHA-256 해시를 함께 저장한다. |

## 8. 백업 수행 및 모니터링

1. 백업은 Cloud DB 자동 백업과 클러스터 CronJob 으로 자동 실행하는 것을 원칙으로 하고, 수동 백업(변경 작업 전 스냅샷 등)은 수행 기록을 남긴다.
2. 백업 작업의 성공·실패를 모니터링하고, 실패 시 백업 관리자에게 자동 통보되도록 알림을 설정한다(CronJob 실패 이벤트·Cloud DB 백업 이벤트 → 모니터링 도구 알림).
3. 백업 관리자는 백업 결과를 일 1회 확인하고 실패 건은 당일 원인 분석과 재수행을 완료한다. 재수행이 불가하면 정보보호 관리자에게 보고한다.

| 점검 항목 | 주기 | 담당 | 기록 |
| --- | --- | --- | --- |
| 백업 작업 성공 여부 확인, 실패 건 조치 | 일 1회 | 백업 관리자 | CronJob 실행 이력(`kubectl get jobs`), Cloud DB 백업 목록, 조치 기록 |
| 백업 저장소 용량·보관 세대 확인 | 주 1회 | 백업 관리자 | `backups/postgres/` 객체 수·용량 점검 기록(사용률 70 % 경고 · 85 % 조치) |
| 백업 설정과 양식 02 목록의 일치 확인 | 월 1회 | 백업 관리자 | 점검 기록 |

## 9. 복구 목표와 우선순위

시스템별 복구 목표와 우선순위는 다음 표로 정하고, 양식 04. 복구 시스템 상세 복구절차서와 일치하게 유지한다.

| 우선순위 | 시스템·서비스 | RTO | RPO | 근거 |
| --- | --- | --- | --- | --- |
| 1 | 서비스 핵심 기능 — web · api, 운영 DB, Object Storage `datasets/`(활성 번들) | 4시간 | 24시간(관리형 DB 시점 복구 가능 시 1시간) | 공통 기준 §3.5, 가용성 목표 월 99.5 % |
| 2 | pipeline 워커(데이터셋 빌드), 비동기 내보내기(SHP · GeoTIFF) | 24시간 | 24시간 — 원본(`raw/`)이 불변이라 재실행으로 결과 재생성 | 조회 기능과 분리된 배치 기능 |
| 3 | 로그 수집·모니터링 대시보드, 내보내기 파일(`exports/`, 30일 수명) | 3일 | 24시간 — 내보내기 파일은 조건 기록(`exports` 행)으로 재생성 | 내부 운영 도구 |

## 10. 복구 절차

1. 장애·재해·침해사고로 시스템·데이터의 복구가 필요하면 양식 04. 복구 시스템 상세 복구절차서에 따라 복구한다.
2. 복구는 9항의 우선순위 순서로 수행하고, 복구 완료 후 양식 04의 복구 후 확인 체크리스트로 서비스 정상 여부를 확인한다.
3. 주 운영 환경 전체를 사용할 수 없는 재해 상황은 정보보호 최고책임자가 재해 복구를 선언하고, 같은 공공기관용 리전의 다른 가용영역(Multi Zone 제공 시) 또는 새로 생성한 공공 영역 클러스터에 chart·백업본으로 재구축한다. 별도 DR 리전·DR 서비스 계약은 두지 않는다(검토는 양식 05, 비기술).
4. 복구 수행 내역과 결과는 장애 보고서(6.1.2) 또는 침해사고 보고서(5.1.1)에 기록한다.

## 11. 복원 시험

1. 백업본의 유효성과 복구 절차의 완전성을 검증하기 위해 복원 시험을 반기 1회 이상 수행하고, 결과를 양식 06. 백업 및 복구 시험 결과서에 기록한다.
2. 복원 시험은 운영 환경과 분리된 환경(공공 영역의 시험용 DB 인스턴스·네임스페이스)에서 수행하고, 시나리오에 데이터 복원과 시스템(가상자원·설정) 복원을 모두 포함한다. 상반기는 DB·Object Storage 데이터 복원, 하반기는 chart·설정으로 클러스터 전체 재구축을 시험하여 1년 주기로 주요 시스템 전체가 시험되도록 계획한다.
3. 시험에서 발견한 백업 누락, 절차서 오류·누락은 양식 06의 조치 계획에 따라 양식 02, 양식 04와 백업 설정에 반영한다.

## 13. 관련 절차와의 연계

SaaS 환경 운영과 관련된 백업, 비상복구, 변경관리, 침해사고대응 절차는 다음과 같이 연계하여 운영한다.

| 절차 | 연계 내용 |
| --- | --- |
| 비상복구(재해복구) | 재해 선언 시 양식 04에 따라 복구하고, 복구 목표는 9항을 따른다. DR 서비스 계약은 현재 없다(양식 05). |
| 변경관리 | 인프라·응용 변경 시 백업 대상·방식의 변경 필요 여부를 검토하고 양식 02, 양식 03, 양식 04를 갱신한다. 운영 배포(`vX.Y.Z` 태그 + 수동 승인)와 DB 마이그레이션 전에는 수동 DB 백업으로 복구 지점을 확보한다. |
| 침해사고대응 | 랜섬웨어 등으로 데이터가 손상되면 5.1.1 침해사고 대응 절차와 병행하여 오염되지 않은 백업본으로 복구하고, 증거 보전 필요 시 복구 전에 대응 조직과 협의한다. |
| 장애 대응 | 장애 복구에 본 절차와 양식 04를 사용하고, 복구 결과를 6.1.2 장애 보고에 기록한다. 1·2급 장애는 1시간 내 이용 기관에 통지한다(14.1.4). |
