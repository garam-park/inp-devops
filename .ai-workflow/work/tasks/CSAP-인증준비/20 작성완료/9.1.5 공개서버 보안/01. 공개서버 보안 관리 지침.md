> 본 지침은 운영 타깃(NCP 공공기관용 NKS + Cloud DB for PostgreSQL + Object Storage)의 **목표 상태**를 기준으로 한다. 2026-10-20 현재 운영 환경은 구축 전이며, 인증·권한·감사 로그·중앙 로그 수집·웹 방화벽·배스천·VPN 은 아직 없다. 현재 구현 상태와 차이는 02 설정 기준 4항 점검 기록, 03 구성도, 04 운영 현황에 적는다.

## 1. 목적

㈜이노팸은 클라우드컴퓨팅서비스 지반침하 스마트관리 시스템(제주 GEO-AI 지반침하 SaaS, 이하 "서비스")을 제공하기 위해 인터넷에 공개하는 웹서버, API 서버 등 공개서버가 외부 공격의 1차 대상이 되는 점을 고려하여, 공개서버에 대한 물리적·기술적 보호대책과 운영 절차를 정하고, 공개서버가 침해되더라도 내부 네트워크와 이용 기관 데이터로 침입이 확산되지 않도록 한다.

## 2. 적용 범위

- 서비스 인증 범위에서 인터넷을 통해 불특정 이용자 또는 이용 기관이 직접 접근할 수 있는 모든 서버, 컨테이너, 관리형 서비스 엔드포인트. 당사 공개서버는 NCP Load Balancer 와 NKS Ingress 컨트롤러 뒤의 web(nginx 정적 화면)·api(Fastify API) 두 워크로드와 그 진입 구성요소(Load Balancer, Ingress 컨트롤러)이다.
- 공개서버를 운영·개발·보호하는 임직원과 외부인력
- 공개서버를 보호하는 보안시스템(침입차단: ACG·Network ACL·NetworkPolicy, 웹 방화벽, 악성코드 방지, 접근통제솔루션, 로그 수집)과 그 운영 업무
- 사내 개발·스테이지 클러스터(`dev0`)와 로컬 환경은 인증 대상이 아니며 본 지침의 적용 범위에서 제외한다. 다만 운영 데이터를 반입하지 않는다(11.1.5 네트워크 분리 관리 지침 8항).

## 3. 용어 정의

| 용어 | 정의 |
| --- | --- |
| 공개서버 | 인터넷에서 직접 접근 가능한 공인 IP 또는 도메인이 할당된 서버·컨테이너·엔드포인트. 이용자용 웹서버, API 서버, 이용 기관 포털, 앱·응용프로그램·에이전트를 배포하는 배포 서버, 정적 콘텐츠 서버를 포함한다. 당사는 web·api 워크로드와 그 앞단 Load Balancer·Ingress 컨트롤러가 해당한다. |
| DMZ | 인터넷과 내부 네트워크 사이에 두는 완충 영역. 당사 운영 환경에서는 공인 IP 가 붙는 NCP Load Balancer 와 TLS 종단·경로 라우팅을 수행하는 Ingress 컨트롤러로 이루어진 **진입 영역**을 말한다. 공개 워크로드(web·api)는 진입 영역을 거쳐서만 도달할 수 있다. |
| 내부 네트워크 | 인터넷에서 직접 접근할 수 없는 영역. NKS 워커 노드가 있는 Private 서브넷(서비스 영역), Cloud DB for PostgreSQL 이 있는 Private 서브넷(데이터 영역), 관리 시스템이 있는 Private 서브넷(관리 영역)을 말한다. |
| 침입차단시스템 | 출발지·목적지·포트 기준으로 통신을 허용·차단하는 수단. NCP ACG(Access Control Group), Network ACL, 쿠버네티스 NetworkPolicy(CNI 네트워크 정책)를 포함한다. |
| 접근통제솔루션 | 관리자가 공개서버에 접속할 때 경유하도록 강제하여 계정별 인증, 권한 통제, 세션 기록을 수행하는 수단. 당사는 NCP SSL VPN → 배스천(관리 영역) → kubectl·콘솔 경로를 쓰며, 계정 인증은 NCP Sub Account + TOTP 다중 인증으로 한다. |
| 접속이력 | 공개서버에 대한 관리자 접속 기록(접속 계정, 일시, 출발지 IP, 수행 명령·행위)과 이용자 접근 기록(웹 접근 로그, 웹 방화벽 로그, 방화벽 로그) |

## 4. 책임공유모델에 따른 보호대책 책임 구분

| 보호 영역 | IaaS/PaaS 제공자 | 당사(SaaS 제공자) | 확인 방법 |
| --- | --- | --- | --- |
| 물리적 보호(데이터센터 출입통제, 전원·환경, 장비 반출입) | 책임 | 제공자 인증·계약으로 확인 | 제공자 CSAP 인증서, 계약서, 책임공유 안내 문서 |
| 네트워크 기반 인프라, 하이퍼바이저, 호스트 격리 | 책임 | 제공자 인증·계약으로 확인 | 제공자 CSAP 인증서, 계약서 |
| DDoS 기본 방어 | 책임(기본 제공 범위) | 추가 방어 서비스 선택·설정 | 제공자 서비스 설명서, 설정 화면 |
| 네트워크 영역 설계(Public·Private 서브넷, 라우팅) | 기능 제공 | 설계·설정 책임 | 03. 공개서버 네트워크 및 시스템 구성도 |

| 컨테이너 런타임·오케스트레이션 제어 영역 | 관리형 서비스(NKS 제어 영역) 책임 | 워크로드 설정(Pod 보안, 네트워크 정책, 이미지) 책임 | 02. 공개서버 보안 설정 기준 |

## 5. 공개서버 식별 및 등록

1. 정보보호 관리자는 다음 기준에 해당하는 자산을 공개서버로 식별하여 03. 공개서버 네트워크 및 시스템 구성도의 공개서버 목록에 등록한다.
   - 공인 IP 또는 인터넷에서 조회되는 도메인이 할당된 가상 서버, 컨테이너 서비스, 로드밸런서 뒤의 서버 그룹
   - 이용자·이용 기관이 접속하는 웹 서비스, API, 포털
   - 앱·응용프로그램·에이전트·업데이트 파일을 배포하는 서버와 저장소 엔드포인트(당사는 해당 없음 — 설치형 배포물이 없다)
   - 외부 연계 기관이 호출하는 연계 서버(당사는 해당 없음 — 외부에서 호출받는 연계가 없다)
2. 공개서버는 서비스별 전용으로 운영한다. 하나의 공개서버에 인증 범위 밖 서비스, 개발·시험 기능, 내부 업무 시스템을 함께 두지 않는다. 운영 NKS 클러스터에는 본 서비스 워크로드만 배치한다.
3. 공개서버를 신설·변경·폐기할 때는 11항의 변경 절차를 따르고, 구성도·공개서버 목록·보안시스템 운영 현황을 5영업일 이내에 현행화한다.
4. 정보보호 관리자는 분기 1회 NCP 콘솔의 공인 IP·Load Balancer·DNS 레코드 목록을 조회하여 등록되지 않은 공개서버가 없는지 확인한다.

## 6. 공개서버 보호대책

공개서버를 운영하는 경우 다음 보호대책을 모두 적용하고, 상세 설정 기준과 확인 방법은 02. 공개서버 보안 설정 기준을 따른다.

| No | 보호대책 | 요구사항 | 설정 기준(02 양식) |
| --- | --- | --- | --- |
| 1 | 서비스별 전용 운영 | 공개서버 1대(그룹)에 하나의 서비스만 탑재하고 용도 외 기능을 두지 않는다. | A |
| 2 | 암호화 통신 | 웹서버를 통해 개인정보·인증정보를 송·수신하는 구간은 TLS 1.2 이상(1.3 우선)만 허용하고 취약한 프로토콜·암호 스위트(RC4·3DES·EXPORT 등)를 비활성화한다. HSTS 1년을 적용한다. | B |
| 3 | 접근통제와 식별·인증 | ACG·Network ACL, Pod 보안 표준 `restricted`, CNI 네트워크 정책(NetworkPolicy 기본 거부)으로 통신을 최소 허용하고, 관리자 접근은 개인별 계정과 TOTP 다중 인증으로 식별·인증한 뒤 권한을 부여한다. | C |
| 4 | 악성코드 방지와 패치 | 노드에 제공자 또는 당사 도입 악성코드 방지 기능을 적용하고, 컨테이너는 이미지 취약점 스캔(trivy)으로 보완한다. OS·미들웨어·베이스 이미지는 주 1회 재빌드(`--pull`·`apk upgrade`)로 최신 패치를 반영하고, 긴급 취약점은 72시간 안에 반영한다. | D |
| 5 | 불필요 서비스·포트 제거 | 서비스에 필요한 프로세스·포트만 활성화하고 관리 포트·DB·스토리지·pipeline 은 인터넷에 노출하지 않는다. | E |
| 6 | 불필요 소프트웨어 설치 금지 | 컴파일러·개발 도구·패키지 관리자·샘플·실행파일 등 서비스에 불필요한 소프트웨어를 운영 이미지에 넣지 않고, 이미지 구성 변경은 PR 리뷰(승인 절차)를 거친다. | F |
| 7 | 정보 노출 방지 | 테스트·기본·샘플 페이지를 제거하고, 에러 처리에서 서버 버전·스택 트레이스·내부 경로 등 시스템 정보가 노출되지 않게 한다. | G |
| 8 | 접속이력 저장 | 관리자 접속 로그와 웹 접근 로그를 생성하여 중앙 로그 저장소로 전송·보관한다. | H |

## 7. DMZ 배치 및 접근통제

1. 공개서버로 향하는 인터넷 트래픽은 진입 영역(DMZ)의 NCP Load Balancer → Ingress 컨트롤러를 반드시 거친다. 공인 IP 는 Load Balancer 에만 할당하고, NKS 워커 노드·Cloud DB·관리 서버에는 공인 IP 를 할당하지 않는다. 워커 노드·DB·관리 시스템은 인터넷 게이트웨이 경로가 없는 Private 서브넷에 둔다.
2. 인터넷에서 공개서버로 향하는 통신은 Load Balancer(웹 방화벽 도입 후에는 웹 방화벽 경유)를 거치게 하고, 유입되는 통신은 서비스 포트(443)만 허용한다. 80 포트는 443 으로의 리다이렉트에만 사용한다.
3. 공개서버가 침해되더라도 내부 네트워크로 침입할 수 없도록 진입 영역에서 내부 영역으로 향하는 통신은 기본 거부하고, 다음 조건을 모두 충족하는 경우에만 허용한다.
   - 출발지를 Ingress 컨트롤러 파드(NetworkPolicy `ingressControllerFrom`)로, 목적지를 web·api 파드의 서비스 포트로 한정한다.
   - web(정적 화면)은 DB·스토리지에 접속하지 않는다. api 는 응용 계층(WAS 역할)을 겸하므로 DB·Object Storage 에 직접 접속하며, 이 경로의 사유와 보완 통제(NetworkPolicy egress 를 api·pipeline 파드로 한정, DB ACG 는 워커 노드 서브넷만 허용, DB 계정 최소 권한, TLS `require`)를 03 양식의 통신 허용 매트릭스에 기록한다.
   - 허용 규칙마다 업무 목적, 등록일, 승인 근거를 기록한다.
4. 공개서버에서 관리 영역(배스천, 로그 저장소 관리 포트 등)으로 향하는 통신과 공개서버 간 불필요한 통신은 차단한다. 공개서버에서 인터넷으로 나가는 통신은 NAT Gateway 를 경유하고 허용 목적지(브이월드 WMTS 443 등)로 한정하며, 사설·루프백·링크로컬 대역 egress 는 차단한다.
5. 침입차단시스템(ACG, Network ACL, NetworkPolicy)의 정책은 서비스를 위한 최소 서비스만 허용하도록 관리한다. 전체 허용(any) 규칙을 두지 않으며 임시 규칙에는 만료일을 정한다.
6. 정보보호 관리자는 분기 1회 침입차단 정책을 검토하여 불필요한 규칙을 삭제하고, 검토 결과를 04. 공개서버 보안시스템 운영 현황에 기록한다.
7. 공개서버(진입 영역과 web·api 파드)에는 개인정보와 고유식별정보를 저장하지 않는다. 파드는 읽기 전용 루트 파일시스템으로 실행하고 쓰기는 `/tmp` 임시 볼륨만 허용한다. 처리 과정에서 임시 저장이 불가피하면 암호화하고(안전성 확보조치 기준 제7조제3항제1호 참고) 보관 기간을 최소화한다.

## 8. 공개서버 접근권한 관리

1. 공개서버에 대한 관리자 접근(NCP 콘솔, kubectl, 컨테이너 exec, 배스천 SSH 등)은 SSL VPN → 배스천 경로로만 허용하고, 인터넷에서 관리 포트·쿠버네티스 API 로 직접 접속하는 경로를 두지 않는다.
2. 접근권한은 업무상 반드시 필요한 인원에게만 부여한다. 다음 조건을 모두 충족해야 한다.
   - 2.1.2 주요 직무자 목록에 공개서버 운영 관련 직무(클라우드 인프라 운영, 응용 배포 등)로 등재되어 있다.
   - 담당 업무에 해당 공개서버 접근이 필요함을 부서장이 확인하고 정보보호 관리자가 검토했다.
   - 개인별 계정(NCP Sub Account, 개인별 kubeconfig 자격)을 사용하며 공용 계정·공용 키를 사용하지 않는다.
   - TOTP 다중 인증을 적용한다.
3. 접근권한은 클러스터·네임스페이스 단위와 권한 수준(관리자, 운영자, 조회) 단위로 최소 부여하고(쿠버네티스 RBAC, NCP IAM 정책), 부서·그룹 단위 일괄 부여를 하지 않는다.
4. 퇴직, 인사이동, 업무 변경, 외부인력 계약 종료 시 지체 없이(내부 기준: 당일) 권한을 회수한다.
5. 정보보호 관리자는 분기 1회 접근통제솔루션·NCP IAM·쿠버네티스 RBAC 에 등록된 전체 사용자·권한을 04. 공개서버 보안시스템 운영 현황 5항의 접근권한 검토 기록으로 검토하여 업무 필요성이 없는 권한을 회수한다. 검토 시 2.1.2 주요 직무자 목록과 인사 현황과 대조한다. 90일 미사용 계정은 비활성화한다.
6. 긴급 장애 조치 등으로 임시 권한이 필요하면 정보보호 최고책임자 또는 정보보호 관리자의 승인을 받아 만료일이 있는 권한을 부여하고, 종료 후 즉시 회수한다.
7. 웹 응용의 관리자 기능(`admin`·`service` 역할 화면과 API)은 서버가 역할을 검사하고 TOTP 다중 인증을 요구하며, Ingress 에서 사내 VPN 대역만 허용한다.

## 9. 접속이력 저장 및 점검

### 9.1 저장

모든 공개서버는 다음 접속이력을 생성하고 중앙 로그 저장소(NCP Cloud Log Analytics 또는 Object Storage 로그 전용 버킷 — 공공 영역 제공 여부 확인 후 하나로 확정)로 전송하여 보관한다. 공개서버(파드) 로컬에만 로그를 두지 않는다.

| 로그 유형 | 필수 기록 항목 | 생성 위치 |
| --- | --- | --- |
| 관리자 접속 로그 | 계정, 접속·종료 일시, 출발지 IP, 인증 성공·실패, 수행 명령 또는 세션 기록 | SSL VPN·배스천 접속 로그, NKS 감사 로그(kubectl·exec), NCP Cloud Activity Tracer(콘솔 행위) |
| 웹 접근 로그 | 일시, 출발지 IP, 요청 URL·메서드, 응답 코드, User-Agent, request_id | Load Balancer 접근 로그, Ingress 컨트롤러 접근 로그, api 요청 로그 |
| 웹 방화벽 로그 | 일시, 출발지 IP, 탐지 규칙, 차단·탐지 여부 | 웹 방화벽(도입 후) |
| 침입차단 로그 | 허용·차단된 통신의 출발지·목적지·포트 | VPC 흐름 로그, NetworkPolicy 차단 로그(CNI 제공 시) |
| 설정 변경 로그 | ACG·Network ACL·인스턴스·클러스터 설정 변경의 주체·일시·내용 | NCP Cloud Activity Tracer, NKS 감사 로그 |

- 보관 기간은 접속·감사 기록 **3년**, 애플리케이션 일반 로그와 인프라 로그(쿠버네티스 감사, Load Balancer, 클라우드 콘솔 감사) **1년**으로 한다. 이는 공개서버가 개인정보처리시스템에 해당할 경우의 법정 요건(개인정보취급자 접속기록 1년 이상, 5만명 이상 정보주체 또는 고유식별정보·민감정보 처리 시 2년 이상, 안전성 확보조치 기준 제8조제1항)을 모두 충족한다.
- 접속이력이 위·변조·삭제되지 않도록 로그 저장소의 삭제·수정 권한을 정보보호 담당자로 제한하고 삭제는 CISO 승인 절차로만 수행한다. Object Storage 를 쓰는 경우 객체 잠금(WORM)을 적용하고 월 1회 해시를 검증한다(같은 기준 제8조제3항).
- 공개서버는 NTP(클라우드 제공자 시각원)로 시간을 동기화하고 월 1회 확인한다.

### 9.2 점검

- 정보보호 담당자는 공개서버 접속이력의 적정성을 **월 1회 이상** 점검하고 결과를 04. 공개서버 보안시스템 운영 현황 7항의 접속이력 점검 기록에 남긴다. 이 주기는 본 지침이 정한 접근통제 절차상의 점검 주기이며, 위험평가 결과에 따라 단축할 수 있다.
- 점검 항목은 최소 다음을 포함한다.
  - 접근권한이 없는 계정 또는 회수된 계정의 접속
  - 접근통제솔루션(SSL VPN·배스천)을 경유하지 않은 직접 접속
  - 업무 시간 외 접속, 비인가 출발지 IP 접속, 다수 인증 실패 후 성공
  - root 등 관리자 계정 직접 로그인, 클러스터 권한 변경·계정 생성 명령, 컨테이너 exec
  - 웹 방화벽·침입차단 로그의 차단 급증, 스캔·관리 URL 접근 시도
- 이상 접속이 확인되면 담당자 확인으로 정상 사유를 검증하고, 침해가 의심되면 5.1.1 침해사고 대응 절차에 따라 보고·대응한다.
- 점검자와 확인자는 분리한다. 점검은 정보보호 담당자가, 확인은 정보보호 관리자가 수행한다.

## 10. 취약점 점검 및 조치

- 공개서버의 컨테이너 이미지·OS 패키지, 미들웨어, 응용 프로그램, 웹서비스에 대한 취약점 점검을 다음 주기로 수행하고, 공개서버 신설·주요 변경·중대 취약점 공표 시 수시로 수행한다.
  - 자동 점검: 매일(야간 OWASP ZAP API·기준 검사, trivy 이미지·잠금파일 검사), 커밋·push 마다(npm audit·pip-audit·semgrep·gitleaks)
  - 수동 점검: 월 1회(02 설정 기준 점검표)
  - 외부 모의해킹: 연 1회(ADR D6 에 따라 KISA 요건 확인 후 수행 방식 확정)
- 웹서버·API는 OWASP Top 10 등 웹 응용프로그램 취약점 점검을 포함한다.
- 발견된 취약점은 위험도별 조치 기한(05. 공개서버 취약점 점검 및 조치 현황 2항) 안에 조치하고 재점검으로 해소를 확인한다. 기한 내 조치가 불가하면 위험 수용 사유와 보완 통제를 정보보호 최고책임자 승인으로 기록한다.
- 점검 계획, 결과, 조치 이력은 05. 공개서버 취약점 점검 및 조치 현황에 기록한다.
