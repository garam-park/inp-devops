> [!info] 법령 기준
> 개인정보의 안전성 확보조치 기준 제7조(개인정보보호위원회고시 제2026-9호, 2026. 7. 1. 시행)는 비밀번호·생체인식정보 등 인증정보를 정보통신망을 통하여 송·수신하는 경우(제1항)와 개인정보를 정보통신망을 통하여 인터넷망 구간으로 송·수신하는 경우(제4항) 안전한 암호 알고리즘으로 암호화하도록 정한다. 법령·고시가 개정되면 국가법령정보센터에서 조문을 다시 확인한다.

> [!note] 현 구현과 차이
> 본 지침은 운영 타깃(NCP 공공기관용 NKS + Cloud DB for PostgreSQL + Object Storage)의 목표 상태 기준이다. 2026-10-20 현재 운영 환경은 구축 전이고, 서비스 내부 구간(Ingress → web·api 파드)은 평문이다. 구간별 실제 적용과 예외는 JAS-11.1.4-02 현황에 적는다.

## 1. 목적

본 지침은 ㈜이노팸이 제공하는 지반침하 스마트관리 시스템(제주 GEO-AI 지반침하 SaaS, 이하 "서비스")(하등급 SaaS)의 클라우드 시스템에서 중요정보가 이동하는 모든 구간에 암호화된 통신 채널을 적용하기 위하여, 암호화 대상, 요구 암호 강도, 전송 시 암호화 방법, 담당자의 역할과 책임을 정한다. 당사는 하등급 SaaS 인증 범위에서 별도의 정보보호 정책서를 두지 않으므로, 본 지침이 정보보호 정책서의 암호 통제(전송 구간)와 네트워크보안지침 중 네트워크 암호화 절을 갈음한다. 저장 데이터 암호화와 암호키 관리의 상세 절차는 12.3.1 암호 정책 수립 산출물(JAS-12.3.1)을 따른다.

## 2. 적용 범위

| 구분 | 범위 | 책임 |
| --- | --- | --- |
| 당사 책임 구간 | 이용자·이용 기관과 서비스 간 통신, 응용·API 통신, 응용과 DB·스토리지 간 연결, 서버·클라우드 콘솔 원격 관리 접근, 외부 서비스 연계, 이용자 데이터 이관·백업 전송 | 당사가 암호화 설정을 구성·운영하고 본 지침의 기준을 적용한다. |
| 제공자 책임 구간 | 데이터센터 내 물리 네트워크, 하이퍼바이저 내부 통신, 제공자 관리 영역의 전송 보호(NKS 제어 영역 내부, 관리형 DB 복제) | IaaS/PaaS 제공자(네이버클라우드플랫폼 NCP 공공기관용)의 책임이며, 제공자의 CSAP 인증과 이용 계약·공개 문서로 보호 수준을 확인한다. 확인 결과는 JAS-11.1.4-02 암호화 통신 채널 사용 현황 4항에 기록한다. |
| 인원 | 통신 구간을 설계·구성·운영·점검하는 임직원과 외부인력 | 본 지침을 준수한다. |

- 사내 개발·스테이지 클러스터(`dev0`)와 로컬 환경은 인증 대상이 아니며, 운영 데이터와 운영 자격증명을 쓰지 않는 조건에서 본 지침의 적용 범위에서 제외한다.

## 3. 용어 정의

| 용어 | 정의 |
| --- | --- |
| 중요정보 | 개인정보, 인증정보(비밀번호, 세션 쿠키·CSRF 토큰, API 키, DB·스토리지 자격증명, 브이월드 키), 이용 기관 데이터(관로·굴착 민감 레이어, 사고 기록, 위험도 산정 결과), 감사 기록 |
| 암호화 통신 채널 | TLS, SSH, VPN(IPsec·SSL VPN) 등 전송 데이터의 기밀성·무결성을 보장하는 통신 수단 |
| 보안강도 | 암호 알고리즘을 해독하는 데 필요한 계산량. 본 지침의 요구 보안강도는 2^112 이상이다. |
| 취약 프로토콜 | 알려진 취약점으로 사용이 금지된 프로토콜·버전(SSL 2.0/3.0, TLS 1.0, TLS 1.1, SSH-1, Telnet 등) |

## 5. 암호화 대상 구간

다음 구간에서 중요정보를 송·수신하는 경우 암호화 통신 채널을 필수로 적용한다. 구간별 실제 적용 내역은 JAS-11.1.4-02 암호화 통신 채널 사용 현황으로 관리한다.

| No | 구간 | 예시 | 적용 채널 | 적용 |
| --- | --- | --- | --- | --- |
| 1 | 이용자·이용 기관 ↔ 서비스 | 웹 접속, 로그인, 사고 기록 화면, `/api` 호출, 내보내기 다운로드 | HTTPS(TLS) | 필수 |
| 2 | 관리자 원격 접근 | NCP 콘솔, SSL VPN·배스천 접속, kubectl(NKS API), DB 관리 접속 | SSL VPN, SSH, HTTPS | 필수 |
| 3 | 서비스 내부 구간 | api·pipeline ↔ Cloud DB, api·pipeline ↔ Object Storage, TLS 종단 지점 ↔ web·api 파드 | TLS | 필수(중요정보 이동 시). 클러스터 내부 파드 구간은 10항 예외로 관리 |
| 4 | 외부 서비스 연계 | api → 브이월드 WMTS, CI → 컨테이너 레지스트리 | HTTPS(TLS) | 필수 |
| 5 | 데이터 이관·백업 전송 | 원본 자료 업로드, DB 백업(`pg_dump` → Object Storage `backups/`), 이용 기관 데이터 반환 | TLS(HTTPS), SSL VPN | 필수 |

- 인증정보는 중요정보 취급 여부와 관계없이 모든 구간에서 암호화하여 송·수신한다(안전성 확보조치 기준 제7조제1항).
- DaaS 형태로 가상 데스크톱을 제공하는 경우 내부망(업무환경)에서 가상PC 접근 시 VPN 또는 전용회선을 필수 적용한다. 당사는 DaaS 를 제공하지 않으므로 이 항은 적용하지 않는다.

## 6. 통신 프로토콜 기준

| 구분 | 허용 | 사용 금지 |
| --- | --- | --- |
| 웹·API(TLS) | TLS 1.2 이상(TLS 1.3 우선) | SSL 2.0, SSL 3.0, TLS 1.0, TLS 1.1 |
| 원격 셸·파일 전송 | SSH-2(OpenSSH 등), SFTP, SCP, FTPS, HTTPS | SSH-1, Telnet, FTP, TFTP |
| VPN | IPsec(IKEv2), SSL VPN(TLS 1.2 이상) | PPTP |

- 신규 시스템·구간은 오픈 전에 허용 프로토콜만 활성화되어 있는지 확인한다.
- 운영 중 취약 프로토콜이 발견되면 72시간 이내에 비활성화하고(긴급 취약점 조치 기한과 같다), 즉시 조치가 어려우면 10항의 예외 절차를 따른다.
- Load Balancer·Ingress 컨트롤러의 TLS 정책은 취약 버전을 포함하지 않는 정책(NCP Load Balancer 의 TLS 1.2 이상 보안 정책, Ingress 컨트롤러 `ssl_protocols TLSv1.2 TLSv1.3`)으로 지정하고, 정책 이름을 JAS-11.1.4-02 현황에 기록한다. HSTS(`max-age=31536000`)를 적용한다.

## 7. 암호 알고리즘·보안강도 기준

암호화 통신 채널이 지원하는 암호의 보안강도는 2^112 이상이어야 한다. KISA 암호이용 안내서의 권고를 참고하여 다음 기준을 적용한다.

| 구분 | 허용(예) | 사용 금지(예) |
| --- | --- | --- |
| 블록 암호 | SEED, ARIA, AES 등 키 길이 128bit 이상(AES-256-GCM 우선) | DES, 3DES, RC4 |
| 공개키 암호 | RSA 키 길이 2048bit 이상, ECDSA P-256 이상 | RSA 1024bit 이하 |
| 해시 | SHA-256 이상 | MD5, SHA-1(인증서 서명·무결성 용도) |
| 키 교환 | ECDHE, DHE(2048bit 이상) | 익명(anonymous) 키 교환, EXPORT 급 암호 스위트 |

- 공공기관에 검증필 암호화 기술을 제공해야 하는 경우 국가정보원 검증필 암호모듈·검증 대상 알고리즘 기준을 함께 적용한다. 현재 스택(nginx·Node.js 의 OpenSSL, PostgreSQL)은 검증필 암호모듈(KCMVP)이 아니므로, NCP 공공 영역이 제공하는 검증필 기반(Load Balancer TLS·KMS)을 활용하고 자체 구간의 적용 방안은 14.3.1 검증필 암호화 기술 제공 산출물(JAS-14.3.1)에서 결정한다.

## 8. 구간별 적용 방법

| 구간 | 적용 방법 |
| --- | --- |
| 웹 서비스·공개 API | Load Balancer 또는 Ingress 컨트롤러에 TLS 인증서를 설치하고 6항의 TLS 정책을 적용한다. HTTP 접속은 HTTPS로 리다이렉트하고 HSTS 를 적용한다. 세션 쿠키는 `Secure; HttpOnly; SameSite=Lax` 로 발급한다. |
| 클라우드 콘솔·관리 포털 | HTTPS로만 접속하고 TOTP 다중 인증을 적용한다(10.3.3 강화된 인증 수단 제공). 웹 응용의 관리자 기능은 사내 VPN 대역에서만 HTTPS 로 접근한다. |
| 운영 서버 원격 접근 | SSL VPN 접속 후 배스천에 SSH-2로 접근하고, kubectl 은 NKS API 의 HTTPS 로만 접근한다. SSH는 키 기반 인증을 원칙으로 하고, sshd 설정에서 취약 알고리즘을 제거한다. |
| 응용 ↔ DB·스토리지 | DB 연결은 `sslmode=require` 이상으로 하고 `require` 미만이면 기동하지 않게 한다(`verify-full` 전환 여부는 CSAP 판정 후 결정). Cloud DB 서버 측 SSL 접속 강제를 켠다. Object Storage 는 `https://` 엔드포인트(사설 엔드포인트 우선)만 쓴다. |
| 외부 서비스 연계 | HTTPS를 사용하고 상대 인증서 검증을 활성화한다. 개발·시험 편의를 위한 인증서 검증 생략 설정(`NODE_TLS_REJECT_UNAUTHORIZED=0` 등)을 운영 환경에 반영하지 않는다. |
| 데이터 이관·백업 전송 | TLS 기반 전송(HTTPS 업로드·Object Storage)을 사용하고, 사내망에서 직접 옮기는 경우 SSL VPN 을 경유한다. 이관 작업 기록에 사용 채널을 남긴다. |

## 9. 인증서 관리

1. TLS 인증서는 신뢰된 인증기관(CA)에서 발급받는다. 내부 시스템 간 통신에 사설 인증서를 쓰는 경우 내부 CA 운영 기준을 따르고 신뢰 저장소를 관리한다.
2. 인증서 만료 30일 전에 갱신을 완료하도록 만료 알림을 설정하고, 만료일은 JAS-11.1.4-02 현황에서 관리한다.
3. 개인키와 비밀정보는 암호키·인증정보 관리자만 접근할 수 있는 저장소(NCP Certificate Manager, k8s Secret — SealedSecrets 로 봉인)에 보관하고, 소스코드·이미지·문서·로그에 평문으로 저장하지 않는다(gitleaks 로 커밋 차단).
4. 암호키 생성·배포·교체·폐기의 상세 절차는 12.3.1 암호 정책 수립 산출물을 따른다. 정기 회전은 연 1회, 유출 의심 시 즉시 회전한다.

## 10. 예외 관리

1. 기술적 제약(레거시 연동, 상대 시스템 미지원, 클러스터 내부 파드 구간 등)으로 본 지침의 기준을 적용할 수 없는 구간은 담당 부서장이 예외를 신청하고, 정보보호 관리자 검토를 거쳐 정보보호 최고책임자가 승인한다.
2. 예외 승인 시 보완 통제(망 분리, 접근 IP 제한, NetworkPolicy 출발지 한정, 파일 단위 암호화, 모니터링 강화 등)와 적용 기한(최대 6개월, 재승인 가능)을 함께 정한다.
3. 예외 구간은 JAS-11.1.4-02 암호화 통신 채널 사용 현황 3항에 기록하고, 기한 도래 시 재검토한다.

## 11. 점검 및 현행화

1. 신규 통신 구간 오픈, 구성 변경, 인증서 교체 시 담당자는 6–8항의 기준 충족을 확인하고 JAS-11.1.4-02 현황을 갱신한다.
2. 정보보호 관리자는 반기 1회 이상 JAS-11.1.4-03 암호화 통신 채널 점검 결과서로 전 구간의 프로토콜·알고리즘·인증서를 점검한다. 외부 공개 구간의 TLS 스캔은 분기 1회 공개서버 네트워크 노출 점검(JAS-9.1.5-05)과 함께 수행한다.
3. 프로토콜·알고리즘의 신규 취약점이 공개되면 수시 점검을 수행하고 필요 시 본 지침의 허용·금지 기준을 개정한다.
4. 심사 대비 증적은 JAS-11.1.4-04 증적 수집 점검표에 따라 수집·보관한다.
