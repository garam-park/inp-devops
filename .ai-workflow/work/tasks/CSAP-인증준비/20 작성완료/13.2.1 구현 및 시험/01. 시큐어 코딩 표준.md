> [!info] 법령 기준
> 개인정보를 처리하는 기능의 접근통제·암호화 요구는 개인정보의 안전성 확보조치 기준 제6조·제7조(개인정보보호위원회고시 제2026-9호, 2026. 7. 1. 시행)를 기준으로 식별했다. 법령·고시가 개정되면 국가법령정보센터에서 조문을 다시 확인한다.

## 1. 목적

㈜이노팸은 클라우드컴퓨팅서비스 지반침하 스마트관리 시스템(이하 "서비스")을 안전하게 구현하기 위하여 개발 전 과정에 적용하는 시큐어 코딩 표준을 정하고, 모든 개발자가 이 표준에 따라 구현하도록 한다.

## 2. 적용 범위

- 서비스(하등급 SaaS) 인증 범위의 응용 프로그램: 웹 화면(web, React 19 + TypeScript), API(api, Node.js 24 + TypeScript · Fastify), 관리자 기능, 데이터 처리 워커(pipeline, Python 3.12), 배포 구성(Dockerfile, Helm chart · values, GitHub Actions 워크플로)
- 저장소: `jeju-ai-saas-be`, `jeju-ai-saas-fe`, 그리고 서비스를 배포하는 클러스터 저장소의 서비스 설정
- 당사 임직원과 개발 업무를 수행하는 외부인력이 작성하는 모든 소스코드
- 책임공유모델에 따라 물리 시설, 하이퍼바이저, 관리형 플랫폼(NKS, Cloud DB, Object Storage) 등 제공자 책임 영역의 소프트웨어는 제공자 인증·계약으로 확인하고, 당사는 그 위에서 당사가 개발·운영하는 애플리케이션 계층에 본 표준을 적용한다.

## 3. 참조 표준 및 외부 환경 분석

### 3.1 참조 표준

## 4. 코딩표준

각 규칙의 준수 여부는 코드 리뷰와 정적 분석 도구로 확인하며, 확인 방법은 5항을 따른다. 저장소별 실행 규칙(서식·린트 예외 처리)은 각 저장소 `AGENTS.md` 에 있고 본 표준과 어긋나면 본 표준을 따른다.

### 4.1 입력 데이터 검증

| No | 규칙 |
| --- | --- |
| 1 | 사용자·외부 시스템이 입력한 모든 데이터는 서버(api) 측에서 검증한다. 화면(web)의 검증은 편의 목적으로만 사용하고 신뢰하지 않는다. |
| 2 | 보안 기능(인증, 권한, 조직·레이어 식별자, 내보내기 조건 등)을 결정하는 입력값은 반드시 서버 측에서 재검증한다. |
| 3 | 입력값은 허용 목록(형식, 길이, 범위, 허용 문자) 방식으로 검증하고, 검증에 실패하면 요청을 거부(400)한다. api 는 모든 라우트에 Fastify JSON 스키마(params · querystring · body)를 둔다. 식별자는 슬러그 패턴(`^[a-z0-9][a-z0-9-]{0,62}$`)을 쓴다. |
| 4 | 파일 업로드는 확장자·매직 바이트·크기(원본 묶음 `UPLOAD_MAX_BYTES`, 엑셀 5MB)를 서버 측에서 검증하고, zip 안 경로의 `..`·절대 경로를 거부하며 풀린 크기 상한을 둔다. 업로드 파일은 실행 권한이 없는 Object Storage(`raw/`, `incidents/uploads/`)에 저장한다. 엑셀 파서는 수식·외부 링크 해석을 끈다. |
| 5 | 파일 경로는 manifest 조회 또는 검증 함수(`safeFilePath`)로만 해석하고, 사용자 입력 문자열로 스토리지 키나 파일 경로를 바로 만들지 않는다. |

### 4.2 SQL 삽입 방지

| No | 규칙 |
| --- | --- |
| 1 | 데이터베이스 질의는 Prepared Statement(파라미터 바인딩) 또는 검증된 쿼리 빌더·ORM 으로 작성한다. |
| 2 | 사용자 입력값을 문자열 연결·템플릿 리터럴로 SQL 쿼리에 직접 결합하지 않는다. |
| 3 | 동적으로 구성할 수밖에 없는 식별자(테이블·컬럼명, 정렬 기준)는 허용 목록과 대조하여 사용한다. |
| 4 | 애플리케이션의 DB 계정은 업무에 필요한 최소 권한만 가지며 DDL·관리자 권한을 부여하지 않는다. 감사 표(`audit_events`)에는 INSERT · SELECT 만 준다. 스키마 변경은 별도 마이그레이션 계정으로 한다. |

### 4.3 출력값 처리(XSS 방지)

| No | 규칙 |
| --- | --- |
| 1 | 사용자 입력값을 화면에 출력할 때는 출력 위치(HTML, 속성, 스크립트, URL)에 맞게 이스케이프 처리한다. |
| 2 | React 의 자동 이스케이프를 사용하고, 이를 우회하는 기능(`dangerouslySetInnerHTML`, `innerHTML`, `eval`, 지도 팝업의 HTML 문자열 결합)은 검토 승인 없이 사용하지 않는다. |
| 3 | 화면 응답에는 CSP(`default-src 'self'`, `script-src 'self'`, 인라인 스크립트 없음)를 적용하고, CSP 를 완화(`'unsafe-inline'` · `'unsafe-eval'` · 외부 출처 추가)하려면 검토 승인과 `e2e/headers.spec.ts` 갱신을 함께 한다. |
| 4 | api 는 JSON · GeoJSON 만 응답하고 `Content-Type` 을 서버가 정하며 `nosniff` 를 붙인다. 외부 콘텐츠(배경지도 중계)의 `Content-Type` 을 그대로 통과시키지 않는다. |

### 4.4 URL 리다이렉션

| No | 규칙 |
| --- | --- |
| 1 | 사용자 입력값을 리다이렉션 대상 URL 로 직접 사용하지 않는다. |
| 2 | 리다이렉션이 필요한 경우(로그인 후 복귀, OIDC 콜백) 내부 경로 식별자 또는 허용된 URL 목록과 대조한 뒤 이동시킨다. 외부 호출(브이월드)은 고정 호스트로만 나간다(SSRF 방지). |

### 4.5 세션 관리

| No | 규칙 |
| --- | --- |
| 1 | 세션 ID 는 프레임워크가 제공하는 안전한 난수 기반 값을 사용하고 URL·로그에 노출하지 않는다. |
| 2 | 로그인 성공 시 세션 ID 를 재발급하고, 로그아웃·권한 변경 시 기존 세션을 서버에서 무효화한다. |
| 3 | 세션 쿠키에 `Secure`, `HttpOnly` 속성을 설정하고, `SameSite` 속성을 `Lax` 이상으로 설정한다. 상태 변경 요청에는 CSRF 토큰(`X-CSRF-Token`)을 검증한다. |
| 4 | 30분간 활동이 없으면 세션을 만료하고, 관리자 기능은 더 짧은 타임아웃(15분)을 적용한다. 절대 만료는 12시간이다. |

### 4.6 오류 처리

| No | 규칙 |
| --- | --- |
| 1 | 오류 발생 시 스택 트레이스, 내부 경로, DB · 스토리지 오류 메시지 등 내부 정보를 이용자에게 노출하지 않고, 정의된 응답 코드와 일반 메시지(`{ error: "…" }`)를 반환한다. nginx 는 `server_tokens off` 로 버전을 숨긴다. |
| 2 | 오류 처리 후 시스템은 안전한 상태(거부 기본값)로 동작한다. 오류를 무시하고 처리를 계속하지 않는다. 설정이 안전 기준 미만이면 기동을 실패시킨다(예: DB `sslmode` 가 `require` 미만). |
| 3 | 상세 오류 내용은 서버 로그(요청 ID 포함)에만 기록하고, 로그에 개인정보·인증정보(비밀번호, 토큰, 쿠키, 접속 문자열, 인증키가 붙은 URL)를 남기지 않는다. |

### 4.7 인증·접근권한

| No | 규칙 |
| --- | --- |
| 1 | 모든 보호 대상 기능·API 는 서버 측에서 인증과 권한을 검증한다. 예외는 `POST /api/auth/login`, `GET /api/health`, `GET /api/ready` 뿐이다. 화면 숨김만으로 접근을 통제하지 않는다. |
| 2 | 데이터 조회·변경 시 요청자가 해당 데이터(조직 `orgs/{org}`, 레이어, 사고 기록, 내보내기 파일)에 권한이 있는지 서버 측에서 확인하여 다른 이용 기관의 데이터와 권한 없는 민감 레이어에 접근할 수 없게 한다. 권한 없는 자원은 존재 여부를 드러내지 않도록 404 로 답한다. |
| 3 | 관리자 기능은 일반 이용자 기능과 분리된 경로·권한으로 구현한다. 인증·패스워드·추가 인증 구현 기준은 10.3.2, 10.3.3, 10.3.4를 따른다. |
| 4 | 로그인 연속 실패 제한(5회 잠금), 인증 요청 rate limit(분당 20회) 등 인증 보호 기능은 13.1.2 에서 정의한 보안 요구사항대로 구현한다. 클라이언트 IP 는 신뢰 프록시(Ingress) 대역에서 온 `X-Forwarded-For` 만 쓴다. |

### 4.8 암호화

| No | 규칙 |
| --- | --- |
| 1 | 중요정보·개인정보·인증정보의 저장·전송 암호화는 12.3.1 암호 정책에서 정한 안전성이 입증된 알고리즘과 키 길이(AES-256-GCM, RSA-2048 이상 또는 ECDSA P-256, SHA-256 이상)를 사용한다. MD5 · SHA-1 · DES 를 보안 목적으로 쓰지 않는다(무결성 비교용 ETag 등 비보안 용도는 주석으로 표시). |
| 2 | 자체 구현한 암호 알고리즘을 사용하지 않고, 검증된 라이브러리(Node.js `crypto`, 검증된 Argon2id 구현체)를 사용한다. 난수는 암호학적 난수 생성기(`crypto.randomBytes` · `secrets`)만 쓴다. |
| 3 | 패스워드는 일방향 암호화(Argon2id)로 저장한다. |
| 4 | 중요정보 전송 구간에는 TLS 1.2 이상을 적용하고, 취약한 프로토콜(SSL v3, TLS 1.0·1.1)을 허용하지 않는다(11.1.4 참조). 서버 간 호출에서 인증서 검증을 끄지 않는다. |

### 4.9 비밀정보·설정 관리

| No | 규칙 |
| --- | --- |
| 1 | 패스워드, API 키, 인증서, 접속 문자열 등 비밀정보를 소스코드·형상관리 저장소·이미지·화면 번들에 하드코딩하지 않는다. 커밋 훅과 CI 의 gitleaks(`.gitleaks.toml`, 이력 전체)가 차단한다. |
| 2 | 비밀정보는 k8s Secret(SealedSecrets 로 봉인해 저장소 보관)으로 관리하고 환경변수로만 주입한다. 로컬은 `.env`(커밋 금지)만 쓴다. |
| 3 | 주석·테스트 코드·로그에 비밀정보와 개인정보를 남기지 않는다. 테스트의 가짜 자격 증명은 누가 봐도 가짜인 값(`…-0000`)을 쓴다. 운영 반영 전에 디버그 코드를 제거한다. |

### 4.10 외부 구성요소

| No | 규칙 |
| --- | --- |
