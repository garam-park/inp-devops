> [!info] 법령 기준
> 개인정보의 안전성 확보조치 기준 제6조제2항(개인정보보호위원회고시 제2026-9호, 2026. 7. 1. 시행)에 따라 개인정보취급자가 정보통신망을 통해 외부에서 개인정보처리시스템에 접속하려는 경우 인증서, 보안토큰, 일회용 비밀번호 등 안전한 인증수단을 적용한다. 법령·고시가 개정되면 국가법령정보센터에서 조문을 다시 확인한다.

본 문서는 ㈜이노팸 접근통제관리지침 중 강화된 인증 수단에 관한 절(사용자 인증)을 인증 심사 제출용으로 발췌·정리한 것이다. 접근통제관리지침 본문과 내용이 다르면 지침을 우선하고 본 문서를 갱신한다.

## 1. 목적

이용자와 당사 운영자가 지반침하 스마트관리 시스템에 접속할 때 아이디·비밀번호 외에 다중 요소 인증 등 강화된 인증 수단을 적용하고, 이용자가 요청하는 인증 수단과 추가 통제 방안을 제공하기 위한 기준과 절차를 정한다.

## 2. 적용 범위

- 지반침하 스마트관리 시스템(하등급 SaaS) 인증 범위 내 모든 인증 접점과 그 접점에 로그인하는 모든 계정
- 당사 임직원·외부인력의 관리시스템(NCP 콘솔, VPN·배스천, 운영 NKS 클러스터, Cloud DB, GitHub 조직 `innopam`, NCP Container Registry, 관리형 로그·모니터링 콘솔) 접속과 이용 기관 관리자·이용자의 서비스 화면 접속
- NCP 공공기관용 콘솔·API에 대한 당사 계정의 접속. 제공자 내부 관리시스템은 제공자 인증·계약으로 확인하며 본 절차의 대상이 아니다.
- 개발·스테이지 `dev0` 클러스터와 로컬 환경은 인증 범위 밖이다.

## 3. 용어 정의

| 용어 | 정의 |
| --- | --- |
| 인증 접점 | 이용자 또는 운영자가 자격증명을 제시하여 로그인하는 시스템·화면·프로토콜 종단. 03. 인증 수단 적용 현황표에 목록화한다. |
| 관리시스템 | 당사 운영자가 서비스와 인프라를 운영·관리하기 위해 접속하는 시스템. 관리자 기능(web 관리자 화면·관리자 API), NCP 콘솔·API, VPN·배스천, 운영 NKS 클러스터·Cloud DB, GitHub 조직(형상관리·CI/CD·self-hosted runner), 이미지 레지스트리, 관리형 로그·모니터링 콘솔 |
| 이용자 포털 | 이용 기관 관리자(`service` 역할)와 이용자(`user` 역할)가 서비스를 이용하기 위해 로그인하는 web 화면과 인증 API(`/api/auth/*`) |
| 인증 요소 | 지식 요소(아는 것), 소유 요소(가진 것), 생체 요소(본인의 신체·행동 특성) |
| 다중 요소 인증(MFA) | 서로 다른 두 가지 이상의 인증 요소를 조합하는 인증 |
| 강화된 인증 수단 | 아이디·비밀번호에 더하여 적용하는 소유·생체 요소 기반 인증 수단(OTP, 인증서(PKI), 보안토큰, FIDO2·패스키 등) |
| 추가 통제 방안 | 인증 요소 외에 접속 조건을 제한하는 수단(IP·국가 제한, MAC 제한, 브라우저·기기 제한, 접속 시간 제한 등) |
| 안전한 접속 수단 | 외부에서 관리시스템에 접속할 때 통신 구간과 접속 주체를 제한하는 수단(VPN, 배스천 호스트 등) |

## 4. 인증 요소 유형과 인정 기준

### 4.1 인증 요소 유형

| 요소 유형 | 정의 | 예시 | 비고 |
| --- | --- | --- | --- |
| 지식 | 이용자만 아는 정보 | 비밀번호, PIN, 보안 질문 답 | 1차 인증에 사용한다. 2차 인증으로 단독 사용할 수 없다. |
| 소유 | 이용자만 가진 물리·논리 매체 | OTP 앱(TOTP), 하드웨어 보안토큰(FIDO2), 인증서(GPKI)·보안토큰, 등록된 휴대폰(문자 인증코드), 등록된 이메일(인증코드) | 이메일·문자 인증코드는 매체 탈취 위험이 있어 관리시스템의 2차 요소로는 비허용한다. 당사 서비스는 이메일·휴대폰 번호를 수집하지 않으므로 이용자 포털에서도 제공하지 않는다. |
| 생체 | 이용자 신체·행동 특성 | 지문, 얼굴, 홍채 | 기기 내 생체 인증(FIDO2·패스키)으로 제공한다(요청 시 제공 계획). |

### 4.2 인정·불인정 조합

| 조합 | 판정 | 사유 |
| --- | --- | --- |
| 비밀번호 + OTP | 인정 | 지식 + 소유 |
| 비밀번호 + 인증서(PKI)·보안토큰 | 인정 | 지식 + 소유 |
| 비밀번호 + 이메일 또는 문자 인증코드 | 인정(이용자 포털), 관리시스템은 4.1의 비고에 따라 비허용 | 지식 + 소유 |
| 비밀번호 + 지문·얼굴(기기 생체 인증) | 인정 | 지식 + 생체 |
| 패스키(기기 소유 + 생체 또는 PIN) | 인정 | 소유 + 생체 또는 소유 + 지식 |
| 아이디·비밀번호 인증 후 다시 아이디·비밀번호 입력 | 불인정 | 같은 지식 요소의 반복 |
| 비밀번호 + 2차 비밀번호·PIN·보안 질문 | 불인정 | 지식 + 지식 |
| 비밀번호 + IP·국가 제한 | 불인정(추가 통제로만 취급) | IP 제한은 인증 요소가 아님 |
| 이용 기관 SSO(IdP) 연동 | 이용 기관 IdP에서 다중 요소 인증을 수행하는 경우에 한해 인정 | IdP의 인증 정책을 계약·설정으로 확인 |

## 5. 제공 인증 수단 카탈로그

| No | 인증 수단 | 요소 유형 | 제공 상태 | 적용 가능 접점 | 구현 방식 | 등록·사용 방법 요약 | 비고 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | OTP(앱 기반 TOTP) | 소유 | 계획(1차 인증 구현과 함께 개발. 2026-10-20 미구현) | 관리자 기능, 이용자 포털, NCP 콘솔, VPN | api 자체 구현(RFC 6238 TOTP, 30초·6자리). 시드는 서버측 암호화 저장, 라이브러리는 구현 시 선정 | 설정 화면에서 QR 코드로 등록하고 로그인 시 6자리 코드 입력. 등록 시 1회용 백업 코드 발급 | 기본 권장 수단. `admin` · `service` 역할 필수 |

| 3 | 패스키(기기 생체 인증) | 소유 + 생체 | 계획(요청 시 유형 C 로 검토) | 이용자 포털, 관리자 기능 | WebAuthn | 기기에 패스키 등록 후 지문·얼굴로 인증 | 지문 등 생체 인증 요청에 대응하는 수단 |
| 4 | 이메일 인증코드 | 소유 | 미제공 — 이메일을 수집하지 않음(하등급 조건: 로그인 식별자에 이메일 미사용) | 해당 없음 | 해당 없음 | 해당 없음 | 유효시간 해당 없음 — 미제공 |
| 5 | 휴대폰 문자 인증코드 | 소유 | 미제공 — 휴대폰 번호를 수집하지 않음 | 해당 없음 | 해당 없음 | 해당 없음 | 유효시간 해당 없음 — 미제공 |
| 6 | 인증서(PKI) 기반 인증 | 소유 | 계획(이용 기관 요청 시 유형 C 로 검토) | 이용자 포털(공공기관 이용자), 관리자 기능 | 기관 인증서(GPKI) 연동 모듈 — 도입 여부는 요청 시 검토 | 인증서 선택 후 인증서 비밀번호 입력 | 공공기관 이용 기관 요청에 대응하는 수단 |
| 7 | 이용 기관 SSO 연동(SAML·OIDC) | 이용 기관 IdP에 위임 | 계획(제품 설계안 2차 인증 단계, 05 §4-4 열린 결정) | 이용자 포털 | OIDC(`openid-client`). SAML 이면 Keycloak 을 중간에 둔다 | 이용 기관 IdP에서 인증 후 서비스 접속 | IdP의 다중 요소 인증 정책 확인 필요 |
| 8 | IaaS/PaaS 제공자 콘솔 다중 요소 인증 | 소유 | 제공(NCP 기능) | NCP 공공기관용 콘솔·API | 제공자 기능(메인 계정 로그인 2차 인증, Sub Account MFA — 공공 콘솔 메뉴명은 운영 계정 개설 시 실측) | 제공자 콘솔 보안 설정에서 OTP 앱 등록 | 당사가 전체 계정에 활성화·강제 |
| 9 | GitHub 2단계 인증 | 소유 | 제공(GitHub 기능). 조직 단위 필수 설정은 2026-10-20 꺼져 있음 — 03 현황표 조치 | GitHub 조직 `innopam`(소스·Actions·GHCR) | GitHub 조직 설정 "Require two-factor authentication" | 개인 계정에 TOTP 앱·보안키·패스키 등록 | SMS 2단계 인증은 비허용(4.1) |

- 제공 상태가 "계획"인 수단은 04. 강화된 인증 수단 요청 처리 대장 3항의 제공 계획에 따라 개발하고, 제공을 시작하면 본 표와 03. 인증 수단 적용 현황표를 갱신한다.

## 6. 접점별 적용 기준

| 접점 구분 | 적용 방식 | 허용 인증 수단 | 안전한 접속 수단 | 추가 통제 | 비고 |
| --- | --- | --- | --- | --- | --- |
| 관리자 기능(당사 운영자, `admin` 역할) | 필수(전 계정, 해제 불가) | OTP, FIDO2, 패스키 | VPN 경유 필수(`admin` 전용 API 경로 — `/api/roles`, `/api/audit` 등 — 는 Ingress 허용 IP 목록으로 사내 VPN 대역만 허용. web 관리자 화면은 해시 라우트(`#admin`)라 서버 경로로 막을 수 없으므로 API 에서 통제한다) | 허용 IP 대역, 국가 제한(WAF 도입 후), 세션 비활동 30분·절대 12시간 | 아이디·비밀번호만으로 로그인되는 화면·API를 두지 않는다 |
| NCP 공공기관용 콘솔·API | 필수(메인 계정·Sub Account 전 계정) | 제공자 MFA(OTP 앱) | 콘솔 접속 허용 IP 조건 적용(사내 VPN 대역) | Sub Account 정책으로 최소 권한, API 인증키는 용도별 발급 | 메인 계정은 평시 미사용, 봉인 관리(10.3.4 02 관리대장) |
| VPN·배스천(운영 NKS 클러스터·Cloud DB 원격 접속) | 필수 | OTP, 인증서 | VPN 자체가 안전한 접속 수단. 배스천은 VPN 경유만 허용, kubectl·DB 관리 접속은 배스천에서만 | 국가 제한, 접속 시간 제한, 세션 기록 | 외부에서 관리시스템 접속 시 안전한 접속 + 추가 인증 |
| 형상관리·CI/CD(GitHub 조직 `innopam`)·이미지 레지스트리·로그·모니터링 콘솔 | 필수 | GitHub 2단계 인증(TOTP·보안키·패스키), NCP 콘솔 MFA | 해당 없음 — GitHub 는 외부 SaaS 이고 조직 IP 허용 목록은 상위 요금제 기능이라 미적용. 운영 배포는 사설망의 self-hosted runner 가 수행 | 브랜치 보호, 운영 배포 수동 승인 | NCP Container Registry·Cloud Log Analytics·Cloud Insight 는 NCP 콘솔 MFA 를 따른다 |
| 이용자 포털: 이용 기관 관리자 계정(`service` 역할) | 필수(관리자 역할로 분류) | OTP | 해당 없음 | 기관 허용 IP 대역(요청 시) | 공통 기준 3.1: `admin` · `service` 역할 TOTP 필수 |
| 이용자 포털: 일반 이용자(`user` 역할) | 기본 제공, 이용자 선택. 기관 요청 시 기관 단위 강제 | OTP(SSO 연동 시 IdP MFA) | 해당 없음 | 기관 허용 IP 대역(요청 시) | 불특정 다수 이용 특성 반영 |
| 이용 기관 시스템 연동 API(비대화형) | 해당 없음 — 2026-10-20 현재 연동 API 없음. 생기면 다중 요소 인증 대신 대체 통제 적용 | API 키·토큰 + 상호 TLS | 해당 없음 | 허용 IP 제한, 키 연 1회 교체, 권한 최소화 | 예외가 아닌 별도 통제 기준 |

- 신규 접점(새 관리 화면, 새 도메인, 새 로그인 API)을 배포할 때는 변경 관리 절차(PR 리뷰)에서 본 기준 적합 여부를 검토하고, 배포 후 03. 인증 수단 적용 현황표에 등재한다.
- `admin` · `service` 역할 계정은 최초 로그인 시 인증 수단 등록을 강제하고, 등록 전에는 등록 화면 외 기능에 접근할 수 없게 한다.

## 8. 이용자 요청 처리 절차

### 8.1 안내

당사는 다음 채널에 강화된 인증 수단의 종류, 사용 방법, 요청 방법을 안내하고 연 1회 이상, 제공 수단이 바뀌면 즉시 현행화한다.

| 채널 | 안내 내용 | 위치 | 담당 |
| --- | --- | --- | --- |
| 서비스 이용 가이드 | 제공 인증 수단, 등록·사용 방법, 기관 단위 강제 설정 방법, 추가 통제·신규 수단 요청 방법 | 운영 도메인의 이용 가이드 페이지(위치는 04 대장 1항에 기록) | 고객지원 담당 |
| 이용자 포털 설정 화면 | 인증 수단 등록·해제 메뉴와 도움말 | 내 정보 → 보안 설정(구현 시 04 대장 1항에 경로 기록) | 개발 책임자 |
| 이용 계약·보안서비스 수준 협약 | 제공 인증 수단, 요청 절차, 처리 기한 | 계약서 부속 문서 | 영업·고객지원 담당 |
| 고객지원 채널 | 요청 접수 창구(헬프데스크·이메일·전화) | {{고객지원 연락처}} | 고객지원 담당 |

### 8.2 처리 단계

| 단계 | 담당 | 내용 | 처리 기한 | 기록 |
| --- | --- | --- | --- | --- |
| 1. 접수 | 고객지원 담당 | 이용 기관, 요청자, 요청 유형, 요청 수단·조건, 사유를 확인하고 요청자가 이용 기관의 권한 있는 담당자인지 확인 | 접수 즉시 | 04. 요청 처리 대장 2항 |
| 2. 분류 | 정보보호 담당자 | 유형 A: 제공 중인 수단의 사용·기관 단위 강제 설정, 유형 B: 추가 통제(IP·국가·브라우저 제한) 설정, 유형 C: 제공하지 않는 수단(인증서·생체 등)의 신규 제공, 유형 D: 해제·초기화·재등록 | 접수 후 1영업일 | 04 대장 2항 |
| 3. 검토 | 정보보호 관리자 | 유형 A·B: 설정 가능 여부와 영향 확인. 유형 C: 기술 검토(구현 방식·비용·일정)와 대안 수단 검토. 유형 D: 9항의 본인·기관 확인 절차 적용 | 유형 A·B·D 3영업일, 유형 C 10영업일 | 04 대장 2항 검토 결과 |
| 4. 적용 | 개발 책임자, 운영(인프라) 담당자 | 설정 변경 또는 기능 개발·배포. 유형 C는 정보보호 최고책임자 승인 후 제공 계획 수립 | 유형 A·B 5영업일, 유형 C 제공 계획에 따름 | 변경 이력(PR·배포 기록), 04 대장 3항 |
| 5. 확인·회신 | 정보보호 담당자, 고객지원 담당 | 적용 결과를 화면·감사 로그로 확인한 뒤 이용 기관에 회신. 유형 C를 제공할 수 없으면 대안과 계획을 회신 | 적용 후 1영업일 | 04 대장 2항 회신일 |
| 6. 기록·점검 | 정보보호 관리자 | 대장 현행화, 분기별 처리 기한 준수 점검 | 분기 | 04 대장 5항 |

- 이용자가 설정 화면에서 스스로 인증 수단을 등록·사용하는 경우는 요청 처리 대장에 기록하지 않고 시스템 기록(`audit_events`)으로 갈음한다.
- 공공기관 이용 기관이 기관 인증서(GPKI) 연동, 국내 IP 한정 등을 요청하면 유형 B·C로 처리하고 보안서비스 수준 협약과 연계한다.

## 9. 인증 수단 등록·변경·분실·재등록

| 상황 | 절차 | 본인 확인 방법 | 기록 |
| --- | --- | --- | --- |
| 최초 등록 | 로그인 후 설정 화면에서 등록. `admin` · `service` 역할은 최초 로그인 시 강제 | 1차 인증 성공 상태 | 시스템 기록(`audit_events`) |
| 수단 변경·추가 | 기존 수단으로 재인증 후 변경 | 기존 강화된 인증 통과 | 시스템 기록 |
| 분실·기기 교체(이용자) | 1회용 백업 코드 사용 또는 이용 기관 관리자(`service`)를 통한 초기화 요청 | 백업 코드 인증 또는 이용 기관 관리자 확인(공문·기관 관리자 계정 요청) | 04 대장 4항 |
| 분실·기기 교체(당사 운영자) | 정보보호 담당자에게 신고, 부서장 확인 후 초기화 | 대면·영상 확인 | 04 대장 4항 |
| 임시 해제 | 허용하지 않는다. 불가피하면 10항의 예외 절차를 따른다 | 해당 없음 | 예외 승인 기록 |

- 초기화 시 아이디·비밀번호만으로 새 인증 수단을 등록하도록 허용하지 않는다. 초기화 후 첫 로그인은 임시 패스워드(유효 24시간)와 함께 등록 화면으로만 진입한다.
- 백업 코드는 1회용으로 발급하고, 사용하면 감사 이벤트를 남기고 화면에 알린다(이메일·문자 알림은 연락처 미수집으로 쓰지 않는다).
