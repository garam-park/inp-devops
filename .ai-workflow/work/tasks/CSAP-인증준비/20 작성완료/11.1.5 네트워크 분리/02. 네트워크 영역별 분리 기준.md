# 네트워크 영역별 분리 기준

> [!note] 현 구현과 차이
> 본 기준은 운영 타깃(NCP 공공기관용)의 목표 구조다. 서브넷 대역(CIDR)은 운영 VPC 생성 시 정해 JAS-11.1.5-03 구성도에 적는다. 2026-10-20 현재 서비스 Helm chart 와 NetworkPolicy 는 아직 없고(gis-sass chart 구조를 따를 예정), 응용의 권한 검사도 구현 전이다.

## 1. 개요

- 목적: JAS-11.1.5-01 네트워크 분리 관리 지침이 정한 분리 원칙을 영역별 배치·구현 기준으로 구체화하여, 네트워크를 신설·변경할 때 일관되게 적용한다. 본 문서는 당사 네트워크보안지침 중 네트워크 분리에 해당하는 기준이다.
- 적용 범위: 지반침하 스마트관리 시스템(제주 GEO-AI 지반침하 SaaS) 인증 범위 내 모든 네트워크 영역과 그 구성 자원
- 해설서의 영역별 네트워크 분리 예시와 당사 영역의 대응은 다음과 같다. 영역 명칭은 JAS-9.1.5-03 공개서버 네트워크 및 시스템 구성도와 동일하게 사용한다.

| 해설서 예시 영역 | 당사 영역 | 구현 방식 |
| --- | --- | --- |
| DMZ망 | DMZ(진입 영역) | 운영 VPC 의 Load Balancer 전용 서브넷 + NKS Ingress 컨트롤러(TLS 종단·경로 라우팅) |
| (해당 예시 없음, 당사 세분화) | 내부 - 앱(서비스 영역) | 운영 VPC 의 NKS 워커 노드 Private 서브넷, 서비스 네임스페이스 + NetworkPolicy |
| DB망 | 내부 - DB(데이터 영역) | 운영 VPC 의 Cloud DB for PostgreSQL 전용 Private 서브넷, Object Storage 사설 엔드포인트 |
| 관리망 | 관리망 | 운영 VPC 의 관리 Private 서브넷 + NCP SSL VPN 진입 |
| 개발망 | 개발·시험 | 운영 VPC·계정 밖 — 사내 `dev0` 클러스터(Talos·Cilium)와 개발자 로컬(물리 분리) |
| 이용자망 | 이용자(이용 기관) 간 분리 | 이용 기관별 전용 배포(5항) |
| 기타(업무망) | 사무 업무망 | 서비스 네트워크 외부(사무실 네트워크), SSL VPN 접점만 허용 |

## 2. 영역 정의 및 배치 기준

| 영역 | 정의 | 배치하는 자산 | 배치 금지 | 인터넷 노출 | 분리·보호 수단 |
| --- | --- | --- | --- | --- | --- |
| DMZ(진입 영역) | 인터넷 이용자가 접근하는 완충 영역(Load Balancer 서브넷과 Ingress 계층) | Load Balancer, 웹 방화벽(도입 예정), Ingress 컨트롤러 | DB·DBMS, 스토리지 자격증명, 백업, 운영자용 관리 기능의 무제한 노출, 개인정보·고유식별정보 저장 | 인바운드는 Load Balancer 경유 443 만 | ACG, Network ACL, 웹 방화벽, Ingress IP 허용 목록(관리자 경로) |
| 내부 - 앱(서비스 영역) | NKS 워커 노드 Private 서브넷 | web·api·pipeline 파드 | 인터넷 게이트웨이 라우팅, 공인 IP, NodePort·LoadBalancer 타입 Service(진입은 Ingress 로만) | 없음(아웃바운드는 NAT Gateway 경유 목적지 한정) | 노드 ACG(LB 서브넷·배스천 출발지만), NetworkPolicy 기본 거부, PSA `restricted` |
| 내부 - DB(데이터 영역) | 이용 기관 데이터·사고 기록·감사 기록이 저장되는 계층 | Cloud DB for PostgreSQL, Object Storage 사설 엔드포인트 접점, 백업(`backups/`) | 인터넷 게이트웨이 라우팅, 공인 IP·공인 도메인 접속, 진입 영역에서의 직접 접속 경로 | 없음 | DB ACG(워커 노드 서브넷·5432 만), NetworkPolicy egress(api·pipeline 만), TLS `require`, 서버측 암호화 |
| 관리망 | 운영 인력 진입·관리 시스템 영역 | 배스천(접근통제솔루션), 로그 저장소 접점, 모니터링, 배포용 self-hosted runner | 서비스 트래픽 처리 자산 | 없음(SSL VPN 경유) | SSL VPN 허용 계정 제한, TOTP 다중 인증, 접속 기록 |
| 개발·시험 | 개발·시험·스테이징 환경 | 사내 `dev0` 워크로드(네임스페이스 `dev`, PSA restricted), 로컬 compose·k3d, 개발용 스토리지(SeaweedFS·MinIO) | 운영 데이터 원본, 운영 자격증명 | 없음(dev0 은 사내 프록시 IP 허용 목록 뒤, 시험 엔드포인트 인터넷 비노출) | 운영과 물리·계정 분리, 상호 접속 차단 |

- 새 자산은 위 기준에 따라 배치 영역을 먼저 정한 뒤 생성한다. 어느 영역에도 해당하지 않으면 정보보호 관리자가 영역 신설 여부를 검토하여 본 기준에 반영한다.
- 사무 업무망(사무실 PC·내부 업무 시스템)은 운영 VPC 와 연결하지 않으며, 운영 인력은 SSL VPN을 통해 관리망으로만 진입한다.

## 3. 분리 구현 수단 기준

분리 대상의 신뢰 수준 차이에 따라 다음 수단 이상을 적용한다. 하위 수단(서브넷·ACG)만으로 상위 수준의 분리를 갈음하지 않는다.

| 분리 대상 | 최소 분리 수단 | 비고 |
| --- | --- | --- |
| 운영 환경 ↔ 개발·시험 환경 | 계정(프로젝트) 분리, 최소 VPC 분리 | 당사는 운영(NCP 공공 계정)과 개발·시험(사내 `dev0`·로컬)을 물리적으로 분리. 동일 VPC 내 서브넷 구분만으로 분리 금지 |
| 운영 VPC 내 영역(DMZ, 내부 - 앱, 내부 - DB, 관리망) | 서브넷 분리 + 라우팅 구분 + ACG·Network ACL | Public(LB)·Private(노드·DB·관리) 서브넷은 라우팅 테이블로 구분 |
| 동일 영역 내 자산 간 | ACG(역할별) | 예: acg-lb, acg-node, acg-db, acg-bastion |
| 컨테이너 워크로드 간 | 네임스페이스 분리 + NetworkPolicy | 인·아웃 기본 거부, DNS·DB·스토리지·허용 외부만 개방. api ↔ pipeline 직접 통신 없음(DB `jobs` 표로만 연계) |
| 이용자(이용 기관) 간 | 이용 기관별 전용 배포(5항) | 같은 기관 안의 조직 구분은 응용 계층 권한 |
| 서비스 네트워크 ↔ 사무 업무망 | 물리·논리 네트워크 분리, SSL VPN 접점만 허용 | |

- ACG 규칙의 출발지는 가능하면 IP 대역 대신 출발지 ACG 로 한정하는 것을 기본으로 한다. Cloud DB 처럼 ACG 참조가 안 되는 관리형 서비스는 워커 노드 서브넷 대역으로 한정하고 파드 단위 통제는 NetworkPolicy egress 로 보완한다.
- 라우팅 테이블은 영역별로 두고, Private 서브넷의 라우팅에 인터넷 게이트웨이 경로를 추가하지 않는다.

## 4. 환경(개발·시험·운영) 분리 기준

1. 개발(dev), 시험·스테이징(staging), 운영(prod) 환경은 별도 계정 또는 별도 네트워크로 구성한다. 당사는 운영을 NCP 공공기관용 계정에, 개발·스테이징을 사내 `dev0`(통합 검증과 스테이징 겸용)에, 개인 개발을 로컬에 둔다. 세 환경을 동일 VPC 안의 서브넷으로만 구분하는 구성을 금지한다.
2. 개발·시험 환경과 운영 환경 간에는 VPC 피어링, 라우팅, VPN 연결, 공유 스토리지 마운트 등 네트워크 상호 접속 경로를 두지 않는다. 개발 서버에서 운영 DB로 접속할 수 없어야 하며, 운영 DB ACG 의 인바운드에 개발·시험 출발지(사내 대역 포함)를 등록하지 않는다.
3. 배포는 네트워크 상호 접속 대신 승인된 배포 경로(CI 가 커밋 SHA 태그 이미지를 레지스트리에 게시 → 관리망의 self-hosted runner 가 운영 클러스터에 push 배포, 운영은 `vX.Y.Z` 태그 + 수동 승인)를 통해서만 수행하고, 배포 파이프라인의 운영 환경 자격증명은 개발 환경과 분리하여 관리한다.
4. 개발·시험 환경의 엔드포인트는 인터넷에 노출하지 않는다. 외부 시험이 필요하면 기간을 정해 접근 IP를 한정하고 종료 후 즉시 회수한다.
5. 운영 데이터는 개발·시험 환경으로 복제하지 않는다(JAS-11.1.5-01 네트워크 분리 관리 지침 8항).

## 5. 이용자(이용 기관) 간 분리 기준

서비스는 공공기관 전용 SaaS 로, 이용 기관 간 서비스 영역은 다음과 같이 분리한다. 공공 고객용 운영 인스턴스는 민간 고객과 공유하지 않는다(gis-sass ADR 2026-09-26.02 운영 원칙, 14.3.5 영역분리).

| 계층 | 분리 방식 | 확인 방법 |
| --- | --- | --- |
| 응용 | 이용 기관별 전용 배포(전용 네임스페이스·Ingress 호스트·세션 서명키). 한 배포 안에서는 모든 요청에 역할(`admin`·`service`·`user`)과 레이어 권한(`role_permissions`)을 서버가 검사하고, 조직 슬러그는 패턴(`^[a-z0-9][a-z0-9-]{0,62}$`)으로 검증 | 코드 리뷰, 권한 시험(레이어 권한 외 파일 요청 403) |
| DB | 테넌트별 DB 분리 — 이용 기관마다 전용 데이터베이스와 전용 DB 계정. 앱 DB 계정은 자기 데이터베이스에만 권한을 갖는다 | DB 계정 권한 목록, 다른 기관 데이터베이스 접속 실패 시험 |
| 스토리지·캐시 | 이용 기관별 전용 버킷(또는 전용 접두어 + 그 접두어만 허용한 접근키). 객체 키는 `orgs/{org}/…` 규칙을 따르고 경로 탐색(`..`·숨은 파일)을 차단 | 접근키 정책, `safeFilePath` 시험 |
| 계약상 강화 분리 요구 시 | 전용 NKS 클러스터 또는 전용 VPC 구성 | 해당 이용 기관 계약·구성도 |

1. 이용 기관 간 격리는 릴리스 전 시험 항목에 포함하고, 연 1회 이상 취약점 점검 시 다른 이용 기관 데이터 접근 시도(권한 상승·식별자 변조)를 점검한다.
2. 이용 기관이 계약으로 강화된 분리(전용 클러스터·VPC)를 요구하면 별도 구성으로 제공하고 JAS-11.1.5-03 네트워크 분리 구성도에 반영한다.
3. 현재 이용 기관은 제주특별자치도(발주처) 1곳이며, 산하 기관을 추가할 때 위 기준으로 전용 배포를 만든다.

## 6. 영역 간 연계 기준

1. 영역 간 통신은 JAS-11.1.5-03 네트워크 분리 구성도 4항의 접근통제 요약에 등록된 경로만 허용한다. 등록되지 않은 통신은 기본 거부한다.
2. VPC 피어링, 전용 연결, 사설 엔드포인트 등 연계 구성은 다음 조건을 모두 충족할 때만 신설한다.
   - 업무 목적과 통신 범위(출발지·목적지·포트)가 문서화되어 있다.
   - 신뢰 수준이 다른 환경 간(개발 ↔ 운영) 연계가 아니다.
   - 정보보호 최고책임자의 승인을 받았다.
3. 연계 구성은 JAS-11.1.5-03 네트워크 분리 구성도 3항에 등록하고, 분기 준수 검토에서 사용 여부와 필요성을 재확인하여 불필요한 연계를 해지한다.
4. 클라우드 관리형 서비스(Object Storage, Container Registry, 키 관리 등) 접근은 인터넷 경유 대신 사설 엔드포인트를 우선 사용한다.

## 7. 관리자 접근 경로 기준

1. 운영 인력의 서버·클러스터·DB·관리 시스템 접근은 SSL VPN → 배스천(접근통제솔루션) 경로로만 허용하고, TOTP 다중 인증과 접속 기록을 적용한다. 상세 기준은 JAS-9.1.5-01 공개서버 보안 관리 지침 8항과 동일하게 적용한다.
2. SSL VPN은 허용된 계정에만 발급하고, 관리망 외 영역으로의 직접 라우팅을 제공하지 않는다.
3. 클라우드 콘솔 접근은 TOTP 다중 인증을 적용하고, 네트워크 구성 변경 권한은 네트워크 관리자(2.1.2 주요 직무자)로 한정한다.

## 8. 신설·변경 시 설계 검토 체크리스트

네트워크 영역·서브넷·연계·허용 규칙을 신설하거나 변경할 때 적용 전에 확인한다. 변경 건마다 이 표를 복사해 기록하며, 아래는 운영 네트워크 최초 설계(목표 구조, JAS-11.1.5-03 1.0)의 검토 결과다.
