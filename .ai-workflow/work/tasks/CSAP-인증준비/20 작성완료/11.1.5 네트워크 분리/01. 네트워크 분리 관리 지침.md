# 네트워크 분리 관리 지침

> [!info] 법령 기준
> 개인정보의 안전성 확보조치 기준 제6조(접근통제)·제6조의2(인터넷망의 차단 조치 등)(개인정보보호위원회고시 제2026-9호, 2026. 7. 1. 시행)를 기준으로 작성했다. 당사가 개인정보처리자로서 개인정보처리시스템을 운영하는 경우에 적용하며, 고시가 개정되면 국가법령정보센터에서 조문을 다시 확인한다.

> [!note] 현 구현과 차이
> 본 지침은 운영 타깃(NCP 공공기관용 VPC·NKS·Cloud DB for PostgreSQL·Object Storage)의 목표 상태 기준이다. 2026-10-20 현재 운영 네트워크는 구축 전이며, 서비스는 인증 대상이 아닌 사내 `dev0`·로컬에서만 돈다. 실제 구성과 차이는 JAS-11.1.5-03 구성도와 JAS-11.1.5-04 검토서에 적는다.

## 1. 목적

㈜이노팸은 클라우드컴퓨팅서비스 지반침하 스마트관리 시스템(제주 GEO-AI 지반침하 SaaS, 이하 "서비스")을 제공하는 네트워크를 서비스, 사용자 그룹, 정보자산의 중요도, 법적 요구사항에 따라 물리적 또는 논리적으로 분리하고 영역 간 접근을 통제하여, 한 영역의 침해가 다른 영역(특히 이용 기관 데이터가 저장된 DB와 운영 관리 영역)으로 확산되지 않도록 한다. 당사의 관리 영역과 이용자의 서비스 영역, 이용자 간 서비스 영역의 네트워크 접근 분리를 포함한다.

## 2. 적용 범위

- 서비스 인증 범위 내 모든 클라우드 네트워크 자원(VPC, 서브넷, 라우팅, ACG, Network ACL, Load Balancer, NAT Gateway, SSL VPN, NKS 클러스터 네트워크와 NetworkPolicy, 관리형 서비스 사설 엔드포인트)
- 인증 범위 내 컨테이너(web·api·pipeline)·DB·관리 시스템이 사용하는 모든 통신 경로
- 네트워크를 설계·운영·변경하는 임직원과 외부인력
- 당사 사무실 업무망은 서비스 네트워크와의 접점(SSL VPN 관리자 진입 경로)에 한하여 적용한다. 사내 개발·스테이지 클러스터 `dev0` 는 운영과의 분리 대상(개발·시험 영역)으로만 다룬다.

## 3. 용어 정의

| 용어 | 정의 |
| --- | --- |
| 네트워크 영역 | 동일한 신뢰 수준과 용도를 가진 자산을 묶어 다른 영역과 분리하여 운영하는 네트워크 단위. 당사 영역 구분은 JAS-11.1.5-02 네트워크 영역별 분리 기준을 따른다. |
| 물리적 분리 | 별도의 물리 회선·장비로 네트워크를 나누는 방식. 클라우드 환경에서는 IaaS/PaaS 제공자의 물리 인프라 격리로 제공된다. 당사 개발·시험 환경(사내 `dev0`)은 운영(NCP)과 물리적으로 분리되어 있다. |
| 논리적 분리 | 계정(프로젝트), VPC, 서브넷, ACG, Network ACL, 쿠버네티스 네임스페이스·NetworkPolicy 등으로 하나의 물리 인프라 위에서 네트워크를 나누는 방식 |
| DMZ | 인터넷과 내부 네트워크 사이의 완충 영역. 당사 운영 환경에서는 공인 IP 가 붙는 Load Balancer 와 TLS 종단·경로 라우팅을 수행하는 Ingress 컨트롤러로 이루어진 진입 영역 |
| 내부 네트워크 | 인터넷에서 직접 접근할 수 없는 Private 서브넷 영역(서비스 영역 = 내부 - 앱, 데이터 영역 = 내부 - DB) |
| 관리망 | 클라우드 시스템을 운영하는 인력의 접속(SSL VPN·배스천)과 로그·모니터링 시스템이 위치한 영역 |
| 망간 자료전송 | 신뢰 수준이 다른 영역 간(예: 운영 ↔ 개발·시험)에 데이터·파일을 옮기는 행위 |
| 우회 경로 | 정해진 진입점(Load Balancer, SSL VPN·배스천)과 허용 규칙을 거치지 않고 영역에 접근할 수 있는 경로(공인 IP 직접 할당, `kubectl port-forward` 상시 개방, 임시 터널, 미등록 피어링, NodePort·LoadBalancer 타입 Service 임의 생성 등) |

## 4. 책임공유모델에 따른 책임 구분

당사는 IaaS/PaaS 제공자(네이버클라우드플랫폼 NCP 공공기관용)의 인프라 위에서 서비스를 운영한다. 네트워크 분리에 대한 책임은 다음과 같이 구분하며, 제공자 책임 영역은 제공자의 CSAP 인증서·서비스 계약으로 확인하고 사본을 보관한다.

| 분리 계층 | IaaS/PaaS 제공자 | 당사(SaaS 제공자) | 확인 방법 |
| --- | --- | --- | --- |
| 물리 네트워크·회선, 데이터센터 | 책임 | 제공자 인증·계약으로 확인 | 제공자 CSAP 인증서, 계약서 |
| 하이퍼바이저·가상 네트워크 기반의 이용자(계정) 간 격리, 공공기관용 영역과 민간 영역의 분리 | 책임 | 제공자 인증·계약으로 확인 | 제공자 CSAP 인증서, 책임공유 안내 문서 |
| 계정·VPC·서브넷 설계와 라우팅 구성 | 기능 제공 | 설계·설정 책임 | JAS-11.1.5-03 네트워크 분리 구성도 |
| ACG·Network ACL·NetworkPolicy 등 영역 간 접근통제 정책 | 기능 제공 | 정책 설정·검토 책임 | JAS-11.1.5-03 구성도 4항, JAS-11.1.5-04 준수 검토서 |
| 개발·시험 환경과 운영 환경의 분리 | 기능 제공 | 분리 책임(운영은 NCP 공공, 개발·시험은 사내 `dev0`·로컬) | JAS-11.1.5-02 분리 기준 4항, JAS-11.1.5-03 구성도 |
| 서비스 이용자(이용 기관) 간 서비스 영역 분리 | 해당 없음 | 이용 기관별 전용 배포 책임 | JAS-11.1.5-02 분리 기준 5항 |

## 5. 네트워크 분리 원칙

1. 네트워크 영역은 다음 기준에 따라 구분하고, 서로 다른 신뢰 수준의 영역을 같은 네트워크에 두지 않는다.
   - 클라우드서비스 구성 요소의 역할(진입, 서비스 워크로드, DB·스토리지, 관리)
   - 사용자 그룹(인터넷 이용자, 이용 기관 서비스 관리자, 당사 운영 인력, 개발 인력)
   - 정보자산의 중요도(이용 기관 데이터·민감 레이어(관로·굴착)·사고 기록·감사 기록 저장 여부)
   - 법적 요구사항(개인정보처리시스템 접근통제, 공공기관 요건 — 공공 고객용 운영 인스턴스를 민간 고객과 공유하지 않는다)
2. 분리는 물리적 또는 논리적 방식으로 하되, 당사는 클라우드 환경 특성상 계정·VPC·서브넷·ACG·NetworkPolicy 를 이용한 논리적 분리를 기본으로 한다. 물리적 분리 수준은 제공자의 인프라 격리로 충족됨을 확인한다.
3. 영역 간 통신은 기본 거부(deny by default)로 하고, 업무상 필요한 통신만 출발지·목적지·포트를 한정하여 허용한다. 전체 허용(any) 규칙을 두지 않는다. 쿠버네티스 워크로드는 NetworkPolicy 로 인·아웃 기본 거부를 적용한다.
4. 신뢰 수준이 다른 환경(개발, 시험·스테이징, 운영) 간 분리는 계정 또는 VPC 단위 이상으로 하며, 동일 VPC 안의 서브넷 구분만으로 갈음하지 않는다. 당사는 운영을 NCP 공공 계정에, 개발·스테이징을 사내 `dev0` 에 두어 물리적으로 분리한다.
5. 업무 특성과 중요도에 따라 새 영역이 필요하면 JAS-11.1.5-02 네트워크 영역별 분리 기준에 영역과 분리 기준을 먼저 정의한 뒤 구성한다.

## 6. 영역 구분과 영역 간 접근통제

당사 네트워크는 다음 영역으로 구분한다. 영역별 상세 정의·배치 기준은 JAS-11.1.5-02 네트워크 영역별 분리 기준을, 실제 구성과 연계 방법은 JAS-11.1.5-03 네트워크 분리 구성도를 따른다.

| 영역 | 용도 | 핵심 통제 |
| --- | --- | --- |
| DMZ(진입 영역) | 인터넷에 공개되는 진입점(Load Balancer, Ingress 컨트롤러) | 공인 IP 는 Load Balancer 에만, 443 만 수신, 공개 워크로드(web·api)로만 전달 |
| 내부 - 앱(서비스 영역) | NKS 워커 노드 Private 서브넷의 web·api·pipeline 파드 | 인터넷 비노출, Ingress 컨트롤러 파드에서만 web·api 수신, pipeline 은 인바운드 없음 |
| 내부 - DB(데이터 영역) | Cloud DB for PostgreSQL, Object Storage 사설 엔드포인트, 백업 | 별도 Private 서브넷, api·pipeline 만 접근(NetworkPolicy egress + DB ACG), 진입 영역·인터넷 직접 경로 차단 |
| 관리망 | 운영 인력 진입점(SSL VPN·배스천), 로그 저장소·모니터링, 배포용 self-hosted runner | SSL VPN·TOTP 경유, 다른 영역과 분리 |
| 개발·시험 | 사내 `dev0`(개발·스테이지), 로컬 | 운영과 물리적으로 분리, 운영 영역과 상호 접속 차단, 운영 데이터 반입 금지 |
| 이용자 간 서비스 영역 | 이용 기관별 서비스 영역 | 이용 기관별 전용 배포(네임스페이스·DB·버킷 분리) |

1. DMZ의 공개 진입점을 경유하여 내부 네트워크로 접근이 이루어지지 않도록, 진입 영역에서 내부 영역으로 향하는 통신은 기본 거부하고 승인된 최소 규칙(Ingress 컨트롤러 → web 8080·api 8787)만 허용한다. 진입 영역에서 데이터 영역으로 직접 향하는 경로는 두지 않는다.
2. 이용자의 중요정보가 저장된 DB는 데이터 영역에만 배치하고, Public 서브넷 배치와 공인 IP 할당(Cloud DB 공인 도메인 사용 포함)을 금지한다.
3. 클라우드 시스템을 운영하는 인력이 사용하는 접속 경로와 관리 시스템은 관리망으로 분리하고, 운영 인력은 SSL VPN과 배스천(접근통제솔루션)을 경유해서만 각 영역에 접근한다. NKS API 엔드포인트는 배스천 출발지만 허용한다.
4. 개발·시험 환경은 운영 환경과 별도 계정·네트워크로 구성하고, 두 환경 간 네트워크 상호 접속(피어링, 라우팅, VPN 연결)을 두지 않는다.
5. 이용자 간 서비스 영역은 이용 기관별 전용 배포로 분리하고, 분리 방식과 검증 방법은 JAS-11.1.5-02 네트워크 영역별 분리 기준 5항을 따른다.
6. 외부 네트워크에서 접근할 필요가 없는 운영자용 서비스 관리 기능(`admin` 역할 화면·관리자 API)은 이용자 기능과 분리하여 인터넷에 노출하지 않는다. 관리 기능은 Ingress 에서 사내 VPN 대역만 허용하고, 서버 측 역할 검사와 TOTP 다중 인증을 적용한다.

## 7. 내부 서버의 인터넷 접근 제한

1. 내부 네트워크(서비스 영역, 데이터 영역)와 관리망의 서버·파드에서 인터넷으로 직접 나가는 통신은 기본 차단한다.
2. 이미지 pull, 외부 API 호출(브이월드 WMTS) 등 업무상 필요한 아웃바운드 통신은 NAT Gateway 를 경유하게 하고, 목적지(도메인·IP·포트)를 한정하여 허용 목록으로 관리한다. 파드 단위로는 NetworkPolicy egress 로 사설·루프백·링크로컬 대역을 제외한 외부 443 만 허용하며, 외부 호출이 필요 없는 web·pipeline 파드에는 외부 egress 를 열지 않는다. 지수 산정 격리 컨테이너는 네트워크 없이 실행한다.
3. 데이터 영역에서 인터넷으로 향하는 아웃바운드는 원칙적으로 두지 않는다. 불가피하면 목적지를 한정하고 사유·승인을 JAS-11.1.5-03 네트워크 분리 구성도 4항에 기록한다.
4. 개인정보처리시스템에 대한 접속 권한은 IP 주소 등으로 제한하여 인가받지 않은 접근을 차단하고, 접속한 IP를 분석하여 유출 시도를 탐지·대응한다(안전성 확보조치 기준 제6조제1항).
5. 전년도 말 기준 직전 3개월간 일일평균 이용자 수 100만명 이상에 해당하면 접근 권한 설정·다운로드·파기가 가능한 개인정보취급자 컴퓨터에 인터넷망 차단 조치를 적용한다. 클라우드컴퓨팅서비스로 개인정보처리시스템을 구성·운영하는 당사는 해당 서비스 접속 외의 인터넷을 차단하는 방식으로 적용한다(같은 기준 제6조의2제1항). 대상 여부 판단: 해당 없음 — 서비스는 개인정보를 수집하지 않도록 설계했고(개인정보처리시스템 해당 여부는 발주처 확인 전), 이용자는 제주특별자치도와 산하 기관의 업무 담당자로 일일평균 이용자 수가 100만명에 크게 못 미친다. 판단 기준일 2026-10-20. 발주처 확인 결과 개인정보처리시스템에 해당하면 다시 판단한다.

## 8. 망간 자료전송 통제

1. 신뢰 수준이 다른 영역 간(운영 ↔ 개발·시험, 서비스 네트워크 ↔ 사무 업무망) 자료전송은 승인된 전송 수단을 통해서만 수행한다. 승인된 수단: (1) 운영 서비스의 데이터셋 업로드 기능(관리자 인증·감사 기록, Object Storage `raw/` 저장), (2) 운영 서비스의 내보내기 기능(권한 검사·감사 기록), (3) 코드·이미지는 CI/CD 와 컨테이너 레지스트리, (4) 그 밖의 파일은 SSL VPN 을 경유한 배스천 전송(건별 승인).
2. 자료전송은 건별로 부서장 신청과 정보보호 관리자 승인을 거치고, 전송 일시·대상 자료·사유·승인자를 기록하여 3년 이상 보관한다. 서비스 기능(1)·(2)를 통한 전송은 감사 이벤트(`audit_events`)로 기록하며, 정기·반복 전송은 범위와 주기를 정해 일괄 승인할 수 있다.
3. 운영 데이터(이용 기관 데이터, 사고 기록, 감사 기록, 개인정보가 섞일 수 있는 자료)는 개발·시험 환경으로 복제하지 않는다. 시험에는 합성 자료(`scripts/fixtures.ts`)와 공개 공공데이터만 사용하고, 불가피하게 운영 원본이 필요하면 정보보호 최고책임자 승인과 사용 후 삭제 확인을 기록한다.
4. 영역 간 직접 공유 스토리지 마운트, 운영 버킷 자격증명의 개발 환경 사용, 임의 파일 서버 개설 등 승인되지 않은 전송 경로를 만들지 않는다.

## 9. 우회 경로 차단

1. 각 영역의 진입점은 JAS-11.1.5-03 네트워크 분리 구성도에 정의된 경로(인터넷 → (웹 방화벽)·Load Balancer → Ingress, 운영자 → SSL VPN·배스천)로 한정한다.
2. 다음 우회 경로를 금지하고, 발견 시 즉시 차단한 뒤 경위를 조사한다.
   - 워커 노드·DB·배스천에 대한 공인 IP 직접 할당, Private 서브넷에 인터넷 게이트웨이 라우팅 추가
   - 배스천을 경유하지 않는 관리 포트(SSH·쿠버네티스 API·DB 포트) 직접 개방
   - 승인되지 않은 VPC 피어링·VPN 터널·포트 포워딩·릴레이 구성, NodePort·LoadBalancer 타입 Service 임의 생성(서비스 chart 는 ClusterIP 만 허용)
   - 개발·시험 환경(`dev0`·로컬)에서 운영 영역으로의 접속 경로, 운영 자격증명의 개발 환경 반입
3. 정보보호 담당자는 흐름 로그·클라우드 감사 로그·NKS 감사 로그로 우회 경로 생성·사용 여부를 모니터링하고, 발견 사항과 조치 결과를 JAS-11.1.5-04 네트워크 분리 정책 준수 검토서에 기록한다.

## 10. 분리 정책 준수 검토

1. 정보보호 관리자는 네트워크 분리 정책 준수 여부를 **분기 1회 이상** 정기 검토하고, 네트워크 구조 변경(영역·서브넷 신설, 연계 구성 변경, 진입점 변경) 시 수시 검토한다.
2. 검토는 JAS-11.1.5-04 네트워크 분리 정책 준수 검토서로 수행하며, 실제 클라우드 구성(서브넷·라우팅·ACG·Network ACL·피어링·NetworkPolicy 내보내기 자료)과 JAS-11.1.5-03 네트워크 분리 구성도를 대조한다.
3. 검토 결과 부적합 사항은 조치 기한을 정해 조치하고, 구성도·기준 문서를 현행화한다.
