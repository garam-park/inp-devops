# 제주 AI 실제 배포와 HTTPS 관리자 로그인 복구

- 날짜: 2026-11-05
- 요청: 개발 URL 로그인 실패를 확인한 뒤 실제 배포까지 진행.
- 이전 기록: [로컬 통합](03.dev-deploy-local-develop-merge.md)

## 배경

기존 FE는 로그인 화면을 제공했지만 API `357cf24`에는 로그인 경로가 없어 404였다.
사용자가 DB 전용 네임스페이스(A)를 선택한 뒤 실제 배포를 요청했다.

## 변경 내용

- dev0: CNPG 연산자, 전용 DB namespace·3인스턴스·영속 저장·TLS·네트워크 제한·GitOps 구성 배포.
- BE: SHP 검증 Python 의존성을 API·파이프라인 테스트보다 먼저 설치해 깨끗한 CI 환경의 실패 수정.
- API 이미지 `357cf24` → `b869b72`, FE `9ef57e6` 유지. Image Updater가 dev0 main `222837b`에 자동 반영.
- 초기 admin 계정과 제주 조직 owner 권한 생성. 초기 비밀번호는 로컬 dev0의
  `secrets/jeju-ai-saas-admin.password`(0600, git 제외)에만 보관한다.
- 제품 작업 공간은 BE `b869b72` 고정과 배포 결과를 커밋해 develop `f2f89f1`로 게시.
- 이 우산 `projects/jeju-ai`: `d35f5d8` → `f2f89f1`, `ops/dev0`: `8fd1842` → `222837b`로 고정.

## 결정과 이유

로컬 커밋·머지 이후 사용자가 별도로 실제 배포를 승인했다.
BE develop → CI·GHCR → Image Updater → dev0 main → Argo CD의 기존 경로를 사용했다.
DB 데이터·PVC의 자동 삭제를 방지하고 기존 S3 자료는 보존했다.
CI 리스너의 기존 장애 파드와 같은 제품의 오래된 야간 검사만 정리해 배포 검증을 재개했다.

## 검증

- 최종 CI 41949753479: checks·integration·pipeline·build-push 전부 success.
- 로컬 API 213/213·제외 0, Python 27/27, OpenAPI·감사·SAST·SBOM·라이선스 통과.
- API 런타임 deploy-check: 실제 DB·공간 확장·주요 테이블·S3 통과.
- 실제 HTTPS Chromium: 로그인 200·Secure/HttpOnly·계정/자료 조회·새로고침 세션 유지,
  로그아웃 204와 후속 me 401. 지도 화면 표시 확인. 분석값의 정확성을 검증한 것은 아니다.
- 앱·DB Application Synced/Healthy, DB 3/3 Ready. 앱 DB 계정 비슈퍼유저와 TLS 인증·호스트 검증 성공.
- 하위 저장소를 먼저 게시하고 우산 고정 커밋을 연결했다. 비밀번호를 문서·로그·Git에 출력하지 않았다.

## 되돌리는 방법

앱 이미지·API 설정의 이전 Git 커밋으로 복귀한다. DB·PVC·Secret은 삭제하지 않는다.
초기 계정 비밀번호 변경은 별도 계정 관리 절차를 사용하며 기존 비밀번호를 자동 덮어쓰지 않는다.
