# 루트 develop과 origin/develop을 병합해 같은 이력으로 동기화

- 날짜: 2026-11-12
- 요청: 루트의 develop과 origin/develop 차이를 머지로 해결하고 하나의 develop 이력으로 유지한다.
- 이전 기록: [의미별 커밋 후속 정리](02.pm6f-semantic-commits.md), [앞선 프로젝트 Git 동기화](../05/01.project-git-sync.md)

## 배경

로컬 `develop`은 `3785381`, 원격 `origin/develop`은 `38d9d8d`였다.
로컬에만 8개, 원격에만 2개 커밋이 있었고, 원격 최신 fetch 후에도 같았다.
미커밋 상태는 dev0 체크아웃 `3b870cb`와 우산에 등록하지 않은 독립 저장소 `ops/pm6f/`였다.

## 변경 내용

- 루트 `develop`: `3785381` → 병합 커밋 `34864a5`.
  부모는 `3785381`, `38d9d8d`이며 로컬 8개·원격 2개 커밋을 모두 보존했다.
- `ops/dev0` 고정 값: `76bfc9f` → `3b870cb`. 현재 체크아웃 및 원격의 최신 배포 기록과 일치한다.
- `projects/jeju-ai`: 원격의 `58f9b55`가 로컬 고정 값 `a584b37`의 조상임을 확인하고 `a584b37`을 유지했다.
- 나머지 우산 문서·고정 커밋은 로컬의 기존 변경을 보존했다. 원격과 중복된 배포 기록 3개는 같은 내용으로 합쳐졌다.
- 루트 `origin/develop`: `38d9d8d` → `34864a5` 일반 push 성공. 강제 push나 기존 이력 재작성은 하지 않았다.
- 이 기록은 병합 이후 별도 문서 커밋으로 추가하고 같은 원격 develop에 반영한다.

## 결정과 이유

사용자가 지정한 머지 방식으로 두 이력을 통합했다. 작업 파일을 임시 보관하거나 제거하지 않고 병합했다.
서브모듈 고정 값은 조상 관계를 검사해 양쪽을 포함하는 최신 커밋을 선택했다.

루트가 고정한 고양 UAM의 `a3066bc`는 원격 develop `e0c4bef`보다 3개 앞서 있었다.
우산보다 하위 저장소를 먼저 게시하는 규칙과 고양 UAM의 산출물 PR 규칙을 함께 지키기 위해,
기존 3개 커밋을 `codex/lx-baseline-a3066bc`에 먼저 push하고
[초안 PR #168](https://github.com/innopam/ws-goyang-uam/pull/168)을 만들었다.
고양 UAM 원격 develop은 변경하지 않았고 제품 파일도 수정하지 않았다.

## 검증

- 사전 `merge-tree` 결과와 실제 병합 커밋의 트리가 `2fd94174020bf868f096f81809bab11e4b5adee3`으로 일치했다. 충돌은 없었다.
- 실제 병합 트리에서 기존 로컬 대비 변경은 dev0 고정 값 하나였고, 미추적 pm6f 문서 4개의 SHA-256이 모두 같았다.
- 고양 UAM 기존 3개 커밋의 gitleaks 검사, 변경 Markdown 19개와 `git diff --check`가 통과했다.
- 고양 UAM LFS 2개 업로드 성공. PR이 draft·OPEN, base `develop`, head `a3066bc`임을 확인했다.
- 루트는 `push --recurse-submodules=check`로 하위 고정 커밋의 원격 게시 여부를 검사한 뒤 게시했다.
- 병합본 `34864a5`에서 로컬·원격 HEAD 일치와 ahead/behind `0/0`을 확인했다.
- 루트 병합 커밋은 정상 lefthook으로 생성했다. 이 기록도 루트 Markdown 검사와 커밋 훅으로 검사한다.
- 최초 `merge-tree`는 `invalid commit position. commit-graph is likely corrupt`로 실패했다.
  해당 Git 명령에 `core.commitGraph=false`를 적용해 캐시를 우회했다. 캐시 파일의 영구 복구는 수행하지 않았다.
- 별도 `write-tree` 확인은 보호된 `index.lock` 쓰기 권한으로 실패했다. 권한이 있는 실제 병합·커밋으로 트리를 확인했다.
- GitHub 연결 앱의 비공개 저장소 조회가 404·422로 실패해, 정상 접근 가능한 SSH Git·GitHub CLI 인증을 사용했다.
- 이번 작업에서 DB 실행·산출물 재생성·실제 서비스 배포는 하지 않았다.

## 되돌리는 방법

병합 변경을 취소해야 하면 공유 이력을 보존하며 `git revert -m 1 34864a5`를 검토한다.
작업 기록은 별도 문서 커밋으로 되돌릴 수 있다. 미추적 pm6f 저장소와 다른 worktree는 삭제하지 않는다.

- Git commit-graph 캐시의 영구 복구는 필요할 때 별도로 진단한다.
