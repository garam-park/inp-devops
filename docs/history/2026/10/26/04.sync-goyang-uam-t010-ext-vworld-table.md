# 고양 UAM 저장소의 합사 DB 반영 커밋을 우산 저장소 포인터에 반영

- 날짜: 2026-10-26
- 요청: 종료단계 DB 감리 지적사항 가운데 UAM 1번(`ext_vworld_layer_features` 구현 누락)을 합사 개발 DB 에 반영한다.
- 이전 기록: [고양 UAM T010 DB UAM 추출본 커밋 포인터 반영](./03.sync-goyang-uam-t010-db-uam-report.md)

## 배경

`projects/goyang-uam`(ws-goyang-uam) 의 T010 작업이 DB 지적사항 확인 단계에 있었다. 감리 도표 3-1-10 이 지적한
`ext_vworld_layer_features` 구현 누락은 "설계에서 빼는" 문제가 아니라 "합사 개발 DB 에 반영하는" 문제였다.
설계 · 스키마 원본 · 백엔드 구현이 이미 준비돼 있었고, 합사 개발 DB 에만 테이블이 없었다.

프로젝트 저장소 커밋이 원격에 먼저 올라간 것을 확인한 뒤 우산 저장소 포인터를 갱신한다.

## 변경 내용

- `projects/goyang-uam`: `2942cb1b` → `e1fa7c62` 로 gitlink를 갱신한다.
- `projects/goyang-uam/apps/gygo-database`(별도 저장소 `innopam/gygo-database`): 커밋 `c77ce61` → `260d924`.
  `deploy/gis/dev/HISTORY.md` 에 lxegisdev DB 적용 기록 1호(`ext_vworld_layer_features` 생성)를 추가했다.
- `projects/goyang-uam/docs/history/2026/10/26/04.t010-ext-vworld-layer-features-create.md` (신규) — 프로젝트 저장소 쪽 기록.

한 DB 밖의 상태 변화가 있었다. 합사 개발 DB(`lxegisdev`, 스키마 `"GYGO_UAM"`)에 `ext_vworld_layer_features` 테이블을 만들고
VWorld 공역 11개 레이어 435건을 적재했다.

## 결정과 이유

- **설계에서 제거하지 않고 DB 에 만들었다.** 설계 · 스키마 원본(`database/schema/05-batch.sql`) · 백엔드 구현(BATCHREQ022)이
  이미 일관된 상태였다. 지우면 그 일관성이 깨지고 감리 지적도 해소되지 않는다.
- **배포 SQL 전체 재적용 대신 해당 블록만 적용했다.** 저장소 배포 규칙("테이블만 추가 → `01-tables.sql` 재적용,
  인덱스·주석은 따로 적용")을 좁게 수행한 것이고, 다른 서비스 스키마에는 손대지 않았다.
- **SQL 을 새로 쓰지 않았다.** 배포본에서 그대로 추출해 적용했다.
- **배치까지 돌려 확인했다.** 감리 도표는 구현 컬럼 수만 판정하지만, API 가 실제로 이 테이블을 읽는지까지 보려면
  수집이 필요했다. 쓰기는 이 테이블 1개에 한정된다.
- **기록은 서브모듈에 남겼다.** `gygo-database` 저장소 규칙상 LX DB 배포 기록은 그 저장소의 `deploy/*/HISTORY.md` 가
  기준이며, 우산 저장소는 포인터 반영만 한다.

### 실패한 시도 · 미검증

- **`ENC(...)` 복호화는 못 했다.** jasypt 1.9.3 에 `PBEWITHHMACSHA512ANDAES_256` 구현이 없고 BouncyCastle 런타임도 없어
  `no such algorithm` 이 났다. 암호화 이전 커밋 이력에 남아 있던 평문으로 접속했다(값은 기록하지 않는다).
- **미검증: LX 운영(lxprod) DB 반영.** 합사 개발 DB 만 손댔다.

## 되돌리는 방법

이 기록과 gitlink만 담은 커밋을 되돌리면 우산 저장소가 이전 `2942cb1b` 프로젝트 커밋을 가리킨다.
프로젝트 저장소의 커밋과 `gygo-database` 커밋은 유지된다. DB 쪽은 `DROP TABLE "GYGO_UAM".ext_vworld_layer_features;` 로 되돌린다.
