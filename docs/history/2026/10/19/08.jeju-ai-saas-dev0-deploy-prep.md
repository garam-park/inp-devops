# jeju-ai-saas FE·BE 를 dev0 에 배포할 준비 (CI 워크플로 + dev 매니페스트)

- 날짜: 2026-10-19
- 요청: 프로토타입 Jeju-subsidence-AI 대신 jeju-ai-saas-be, jeju-ai-saas-fe 를 dev0 에 배포하려 한다.
- 이전 기록: [02.jeju-subsidence-ai-dev0-deploy-prep.md](02.jeju-subsidence-ai-dev0-deploy-prep.md), [07.move-jeju-ai-saas-fe-under-jeju-ai.md](07.move-jeju-ai-saas-fe-under-jeju-ai.md)

## 배경

저장소 세 개가 함께 바뀐다. 두 제품 저장소에는 Dockerfile 이 있지만 이미지를 올리는 길이 없었고, dev0 에는 띄울 설정이 없었다.

## 변경 내용

- `projects/jeju-ai/jeju-ai-saas-fe` (develop, 커밋 전): `.github/workflows/image.yml` 추가
  - develop push·수동 실행 → `runs-on: dev0` 에서 typecheck·vitest → `ghcr.io/innopam/jeju-ai-saas-fe:<SHA>` 빌드·push. 빌드 인자 `VITE_VWORLD_KEY` 는 저장소 시크릿 `VWORLD_KEY`.
- `projects/jeju-ai/jeju-ai-saas-be` (develop, 커밋 전): `.github/workflows/image.yml` 추가
  - `api/**` 가 바뀐 develop push·수동 실행 → `api/` 에서 typecheck·테스트 → `ghcr.io/innopam/jeju-ai-saas-api:<SHA>`(컨텍스트 `api/`).
- `ops/dev0` (main, 커밋 전): `apps/jeju-ai-saas/` 추가. 자세한 것은 dev0 의 `docs/history/2026/10/19/10.jeju-ai-saas-dev-manifests.md`

## 결정과 이유

- 사용자 결정 3개: 스토리지는 dev 의 SeaweedFS, 주소 `jeju-ai.dev.innopam.net` 을 넘겨받고 옛 앱을 내림, 이미지는 ARC 러너 CI.
- 태그는 40자 커밋 SHA, latest 없음(gis-sass 규칙). 워크플로는 배포하지 않는다. dev0 의 newTag 를 손으로 바꾼다.
- 테스트를 통과한 커밋만 이미지를 올린다. FE 의 e2e(puppeteer)는 브라우저가 필요해 넣지 않았다.

## 검증

- 두 이미지를 로컬에서 빌드해 SeaweedFS 와 함께 띄워 fe → api → 스토리지 경로를 확인했다(dev0 기록).
- 미검증: 워크플로 실행 자체. 러너 그룹 `dev0` 이 지금 두 저장소를 허용하지 않아 push 해도 잡이 대기한다.

## 되돌리는 방법

세 저장소 모두 커밋 전이다. 새 파일을 지우면 된다.

## 남은 일

- FE 로컬 develop 이 origin 보다 5커밋 앞서 있다(`06725ac`). 워크플로 커밋과 함께 push 해야 한다.
- 사용자: 러너 그룹에 두 저장소 추가, FE 시크릿 `VWORLD_KEY`.
- 세 저장소 커밋·push 뒤 ws 의 서브모듈 고정 커밋을 올린다.
