# 현장방문 대비 개발 담당 산출물을 독립 검증하고 틀린 곳을 고침

- 날짜: 2026-10-17
- 요청: 별도 요청 없이 직전 작업(산출물 21종 작성)의 연장으로 진행했다. 작성한 산출물의 사실 주장을 작성자와 다른 검증자가 저장소·GitHub·CI 기록과 다시 대조하게 하고, 확인된 오류를 문서에 반영한다.
- 이전 기록: [../16/03.site-visit-dev-deliverables.md](../16/03.site-visit-dev-deliverables.md)

## 배경

- 이전 기록의 산출물 21종은 작성자가 직접 대조했지만 날짜·수치·상태·"없다" 주장이 많아 작성자 혼자 확인한 것으로는 부족하다고 보았다.
- 현장방문은 평가자가 문서의 한 문장을 저장소와 맞춰 볼 수 있는 자리라서, 확인된 것보다 확실하게 쓴 문장과 범위 단서가 빠진 문장을 미리 걸러 내는 것이 목적이다.

## 변경 내용

### 1차 검증

- 14개 묶음(문서 1~4종씩)으로 나눠 검증자가 사실 주장 3,180건을 1차 자료와 대조했다. 지적 197건(모순 27, 불일치 65, 과장 71, 근거 없음 19, 낡음 15)마다 다른 검증자가 처음부터 다시 확인해 반박을 시도했다.
- 반박 검토 결과: 확정 157건, 해석이 갈려 문구를 완화해야 하는 건 35건, 반박 3건, 검토를 끝내지 못한 건 2건(이 중 1건은 다른 지적의 수정에 포함됐다).
- 확정·완화 건을 `30 관리 산출물/개발/` 의 21종과 README 에 반영했다. 검증자가 낸 수정문이 틀린 경우(예: 오래된 측정값, 근거 없는 날짜)는 쓰지 않고 1차 자료를 다시 확인해 고쳐 썼다.

### 반영한 오류의 유형과 대표 사례

- 범위·시점 단서가 빠진 서술(가장 많음)
  - 배포 런북·롤백 계획·릴리스 노트(JSA-PF-RL-002·RL-003·RL-004, JSA-CM-RL-002): 런북이 설명하는 chart 동작은 `v0.1.0` 태그가 아니라 `develop` 의 것이다. `v0.1.0` chart 는 마이그레이션 Job 이름이 고정이고 시드가 항상 실행된다. 이를 고친 T105 는 2026-09-27(KST)에 병합됐고 아직 릴리스되지 않았다. 문서를 `develop` 기준으로 쓰고 차이를 밝혔다.
  - 같은 문서들: 로그인 왕복·smoke 3종·제품 간 격리 검증은 시드 계정을 전제로 해 시드를 켠 로컬 k3s 에서만 가능하다. 시드를 끈 사내 개발·운영에는 첫 관리자 계정을 만드는 절차가 없다(T105 남은 일). 검증 기준값 38·42 PASS 는 compose 스택 실측이다.
  - 로컬 k3s "배포·검증 완료"는 T105 이전 chart 의 첫 설치만 해당한다. 현재 chart 의 설치·업그레이드·롤백은 실행 기록이 없다.
  - 장애 포스트모템(JSA-PF-OP-006): 시각은 UTC(`Z`), 날짜만 적은 값은 KST 라고 밝혔고, CI 가 처음 전부 통과한 시점(2026-09-26 14:35Z)과 T097 완료 근거의 통과 확인(09-27)을 구분했다. 미시작 사유는 처음부터 잡 안내 문구에 있었으나 진단이 그것을 쓰지 못한 것으로 원인 서술을 고쳤다.
- 틀린 사실
  - JSA-PF-IM-002: `v0.1.0` 이후 병합 PR 은 37건이 아니라 38건이다(#36 이 태그 2분 뒤에 병합됨). ETL 길이 상한 검증은 T091(#46)이 아니라 T074(#49), 헬름 결함 3건은 #24 가 아니라 #12 의 변경이다. e2e 시나리오는 PR #69 가 아니라 PR 없이 반영된 커밋이다.
  - JSA-PF-DS-002·DS-003: 마이그레이션 이미지는 PHP 8.2 가 아니라 8.4 다(`composer.json` 하한 선언이 `^8.2`). 공유 패키지는 `api-core` 하나가 아니라 `web-core` 를 더한 둘이다.
  - JSA-PF-ST-001: 코드는 명명 규칙(변수·매개변수 `snake_case`, 내부 멤버 `_` 접두사)을 따르지 않는다. 이를 검사하는 테스트·린터도 없다. 로그 비밀 비노출 테스트 목록에 로그가 아닌 DTO 테스트가 들어 있었다.
  - JSA-PF-ST-005: 테스트 스택은 `AUTH_JWT_SIGNING_KEY` 가 없으면 `down -v` 와 단계별 명령까지 모두 실패한다. 개발 스택 상태 확인은 `docker compose ps -a` 가 맞다. 헬스 응답 본문은 `groups` 가 포함된다.
- 확실하게 쓴 서술(과장)
  - JSA-PF-ST-002·ST-003: 머지 조건·PR 경유·직접 push 금지는 규칙일 뿐 시스템이 강제하지 않는다(브랜치 보호 불가). `main` 은 `v0.1.0` 보다 56커밋 앞서 있고 그 first-parent 28건이 모두 PR 병합이 아니다. squash 병합 1건(PR #7)이 이력에 남아 있다.
  - JSA-PF-DS-003: Ingress 의 rate limit·요청 크기 제한은 값이 없고, 동작하는 rate limit 은 앱의 로그인·refresh 경로 제한뿐이다. "실패 주입 4개 시나리오 통과"는 실제로 주입한 3개와 `--dry-run` 만 한 노드 드레인을 구분했다.
  - JSA-PF-TS-001·JSA-CM-CT-002: Gradle 의존성 점검은 "잡이 쉬고 있는" 것이 아니라 CI 에 없고(PR #20 미병합) 실제 NVD 스캔을 한 번도 돌리지 못했다. 성능·부하 시험은 WBS ID 12(담당 AI)·8월 월간보고와의 관계를 밝혔다.
  - JSA-CM-RL-001(파일럿 계획): "저장소와 WBS 에서 파일럿 계획을 찾지 못했다"는 틀렸다. WBS 세세부4 에 파일럿 후보지 선정 과업이 있다(개발팀 범위 밖, 기획 담당).
- README: CI 실패 이력(마지막 성공 뒤 6회 연속 실패, 원인이 린트 MD029 와 링크 11건으로 갈림), e2e 건수(기준 커밋에서 19건), 4절 공백 목록의 누락(담당 확인 필요 10건 등), ADR·문서 인용 표기, 새로 확인한 문제 3건(5절 10~12번)을 보완했다.

### 2차 검증

- 1차에서 고친 문장이 맞는지 다시 확인하려고 같은 방식으로 한 번 더 돌렸다. 산출물 21종과 README 의 사실 주장 4,323건을 대조해 68건이 지적됐고(1차의 6.2% 에서 1.6% 로 줄었다), 반박 검토 결과 확정 62건·해석이 갈린 3건·반박 3건이다. 확정·완화한 건을 반영했다.
- 1차 반영이 문서 한 곳만 고쳐 같은 사실이 다른 곳에 남은 경우(전파 누락)가 많았다.
  - 이미지 푸시: "모든 잡 통과 뒤에만"은 자동 경로(develop push·`v*` 태그)에만 맞고 수동 실행(`workflow_dispatch`)은 테스트를 거치지 않는다. JSA-PF-TS-001·OP-001·IM-002·OP-006 에서 같은 단서를 맞췄다.
  - 시드 전제: smoke 3종의 38·42 PASS 를 시드 없는 사내 개발·운영의 점검 기준처럼 적은 JSA-PF-OP-001, 로그인 왕복을 기대 결과에 둔 JSA-PF-TS-005 TC-060 을 고쳤다.
  - DB TLS: `sslMode` 를 낮추면 `DB_REQUIRE_TLS` 도 함께 꺼져 기동 검증이 사라진다. "미만이면 기동에 실패한다"는 chart 경로에서 틀리다(JSA-PF-RL-002).
  - 사내 불성립 기록: 설계서·`deploy/README.md` 의 "사내 k8s 물리 노드 1대, Multi-AZ 불성립"은 `dev0` 가 아니라 별도 Proxmox 호스트의 보안 실습 클러스터 기준이다. "`dev0` 확장 이전 기준"이라는 표현을 바로잡았다(JSA-PF-DS-002·DS-003, README).
  - 자원 기준선: "로컬 k3s 에서 측정한 기준선"은 측정 근거가 저장소에 없고 chart 기본값일 뿐이다(JSA-PF-DS-001·DS-002·TS-001).
- 1차 반영이 새로 만든 오류도 있었다.
  - JSA-PF-OP-006: 14:35Z 는 run 의 종료 시각이고 시작은 12:16Z 다. build-push 는 이 run 이 처음 통과한 것이 아니라 09-26 05:37Z 부터 통과하고 있었다. 미시작 사유는 develop push 뿐 아니라 PR 에도 해당하고, PR 8건(#33–#39, #41)이 검사 11개 실패인 채 병합됐다.
  - JSA-PF-RL-002: `v0.1.0` chart 가 "시드가 매 배포 실행"이라는 서술은 같은 문장의 "두 번째 업그레이드가 실패"와 부딪친다. 시드는 Job 이 만들어질 때(설치, Job 을 지우고 다시 배포)만 돈다. api 파드의 대기·`maxUnavailable: 0`·`backoffLimit: 0` 은 `v0.1.0` 에도 있다.
- 새로 드러난 사실: WBS 가중치 6.5% 는 ID 2 전체값이고 개발팀 범위(ID 3~8)는 3.5% 다(JSA-PF-DS-001). 프로토타입은 지도 레이어가 6종이고 관리자 화면(역할별 권한 설정·사고 이력 관리·작업 기록, 모두 브라우저 저장)이 있다(JSA-PF-DS-003·DS-004·DS-001). JSA-PF-OP-001 의 "감사 로그의 ip"는 인증 로그의 ip 다(JSA-PF-TS-005 TC-012 포함). CT-002 의 smoke-auth 38 PASS 는 나열한 항목 전체를 확인한 것이 아니다.
- 반박되어 고치지 않은 것: JSA-PF-OP-001 의 `dev0` 쿼터 값(2026-10-16 W65 이후 값이라 맞다), README 4.4 의 인용 범위, 폴더의 Word 잠금 파일(운영 점검 사안이라 문서에 적지 않는다).

### 3차 검증

- 2차에서 새로 쓴 문장 99개와 같은 사실이 반복되는 곳을 한 번 더 대조했다(1,310건 대조). 지적은 19건이고 모두 영향이 낮거나 중간이다. 반박 검토 결과 확정 16건·해석이 갈린 2건이며, 반박 검토 한 건은 에이전트가 사용량 한도로 실패해 그 건은 1차 자료를 직접 확인해 반영했다. 한도가 풀린 뒤 반박 검토를 다시 돌렸다. 이 재실행은 이미 고친 문장을 읽은 판정이라 결과가 확정 14건·해석이 갈린 1건·'이미 반영돼 해소' 4건이었고, 앞의 반영을 뒤집은 것은 없었다.
- 고친 것의 성격: 2차에서 쓴 "차이 전체는 1절", "Job 이 끝날 때까지 대기" 같은 완결·포괄 표현의 과장, KMS 를 서비스 간 TLS 와 함께 "Task 범위에 없다"고 묶은 서술(설계서 9장은 KMS 를 T078·T079 소관으로 둔다), e2e 09-27 건에 "trace 확인 기록이 없다"고 쓴 것(저장소 검증 기록에 trace 대조가 있다), `prefer`·`allow` 를 "평문으로 기동"이라 단정한 것, OP-006 의 시각 범례(Z 값은 시작·종료·병합 시각이 섞여 있다)·병합 시각(#38·#39·#41 은 검사 결과가 나오기 전에 병합)·T097 완료 근거의 run 번호(test·build-push·lint-git 가 서로 다른 run)·build-push 의 "이미 통과"(이후 3회 실패), JSA-PF-TS-005 TC-055 의 기대 결과(검증기는 플래그가 켜진 때만 기동을 막는다).
- 재실행에서 나온 문구 다듬기 4건을 반영했다. JSA-PF-RL-004 는 새 마이그레이션이 없는 배포는 두 버전이 같고 롤백만 갈린다고 나눠 적었다. JSA-PF-RL-002 의 인증 smoke 행은 '연속 2회 동일'이 2026-08-18 관측이고 2026-09-27 은 1회 재확인임을 밝혔다. JSA-PF-TS-001 은 e2e 09-27 건 대조 기록의 절 이름(`.ai-workflow/M012-1-verify.md` 의 '추가 1 · T107 e2e')을 정확히 적었다. JSA-PF-OP-006 12:16Z 행은 이후 실패를 워크플로별로 나눴다(test: 외부 다운로드 시간 초과·이미지 pull 연결 끊김, build-push 3회: Docker 데몬 연결 실패·컨테이너 생성 중 runc 권한 오류·BuildKit 오류). build-push 3회의 원인은 실패 잡 로그의 오류 문구로 직접 확인했고 원인의 뿌리는 조사하지 않았다.
- 설계서 3.1.4 가 옛 동작(같아질 때까지 대기·시드 알려진 결함)을 적고 있어 JSA-PF-DS-003 에 develop 기준과의 차이를 따로 적었다. JSA-PF-OP-006 6절의 담당 칸은 다른 산출물의 관행대로 "개발팀(담당자 확인 필요)"로 맞췄다(담당자를 정한 기록이 없다).
- 3차의 지적률은 1.5% 로 2차(1.6%)와 비슷했고 새로 지적된 것은 대부분 문장 단위의 단서·범위 문제여서 검증은 여기서 멈췄다.

### CT-001 교체

- `JSA-CM-CT-001_인증 범위 정의서.docx` 는 사용자의 Word 가 열어 둔 상태(잠금 파일 `~$A-CM-CT-001_…docx` 존재)라서 처음에는 덮어쓰지 않고, 고친 파일을 스크래치패드 `staging/` 에 만들어 검증까지 마쳐 두었다. 사용자가 Word 를 닫은 것(프로세스·파일 점유·잠금 파일 없음)을 확인한 2026-10-17 04:12 에 반영본으로 교체했다. 임시 파일에 복사한 뒤 이름을 바꾸는 방식으로 바꿨고, 반영 전 파일은 스크래치패드에 백업했다. 교체본은 반영본과 바이트가 같고(39,782 B) 폴더에 임시·잠금 파일이 남지 않았다. 교체 전에는 3절 '네트워크' 행이 '충족'이라 적고 WBS 담당 조직 열(ID 32~35 가 '운영(DevSecOps)') 단서가 없었으며, 그 때문에 README 에 임시 단서를 두었다가 교체 뒤 지웠다.

## 결정과 이유

- 사실이 갈리거나 확인하지 못한 문장은 단정을 낮추고 "확인 필요"로 표시했다(예: 재현하지 않은 `helm upgrade` 실패, GHCR 이미지 게시 여부).
- 직접 push 건수 같은 이력 통계는 문서에 싣지 않았다. 규칙 위반 이력을 문서에 어디까지 적을지는 문서 주인의 결정이라서 "예외가 있다"와 근거 Task(T096)만 적었다.
- 수정은 문서 파일에 직접 했고 수정 전 사본은 따로 두지 않았다(커밋 전이고 산출물 폴더가 아직 추적되지 않는다). 사용자가 열어 두었던 `JSA-CM-CT-001` 만 교체 전 파일을 스크래치패드에 백업했다.
- 사용자 개인 정보(Word 가 잠금 파일에 남기는 OS 계정명)와 비밀값은 문서에 넣지 않았다.

## 검증

- 문서 반영마다 Markdown 은 `mise exec -- markdownlint-cli2` 로, Word·Excel 은 `xmllint` 와 ISO/IEC 29500 스키마(`wml.xsd`·`sml.xsd`)로 다시 검증했고 모두 통과했다. 재빌드한 Word 4종과 Excel 2종은 macOS `textutil`·Quick Look 으로도 열렸다.
- 산출물 사이의 문서번호·절 인용은 스크립트로 전수 점검했다(없는 문서번호·절 인용 0건). 비밀값·내부 IP·이메일·전화번호 스캔도 통과했다(`MAP_SECRET_KEY` 기본값 포함).
- 1·2차 검증 모두 읽기 전용 에이전트가 수행했고, 같은 지적에 대해 다른 에이전트가 1차 자료에서 다시 확인했다. 그래도 클러스터 실동작과 저장소 밖 사실은 확인하지 못했다(남은 일 참조).
