# jeju-ai 화면(App.tsx)을 계산 규칙·상태·정책으로 쪼갠다

- 날짜: 2026-10-24
- 요청: "결정이 필요 없는 것만 우선 진행해. 각자 worktree 로 작업하고 커밋 푸시 PR 만들고 리뷰하고 머지까지 다 해."
- 이전 기록: [03.jeju-ai-prototype-parity.md](03.jeju-ai-prototype-parity.md)

## 배경

`jeju-ai-saas-fe` 의 `src/App.tsx` 가 787줄이고 한 함수에 `useState` 27개 · `useMemo` 14개가
섞여 있었다. 문제가 세 가지였다.

1. **계산 규칙을 시험할 수 없었다.** '직전 조회 대비'의 신규 판정, 알림 임계(CSI 상위 5%),
   목록의 정렬 · 쪽나누기 같은 규칙이 화면 안에 박혀 있어서 규칙만 따로 시험할 수 없었다.
2. **상태의 용도가 섞여 있었다.** 조회 결과 · 화면 표시 · 지도 상태가 한 블록에 흩어져 있어
   어떤 상태가 무엇을 바꾸는지 읽기 어려웠다.
3. **권한 정책이 코드 안에 파묻혀 있었다.** `DEFAULT_PERMS` 가 역할별 레이어 목록 세 벌로
   적혀 있어 '누가 무엇을 보는가'가 한눈에 보이지 않았다. 서버가 같은 정책을 집행해야 하는데
   그 기준이 없었다.

### `innopam/jeju-ai-saas-fe` — PR: `refactor/permission-policy-and-sso-seams`

브랜치 `refactor/permission-policy-and-sso-seams` → base `develop`.

- `src/data/constants.ts`: 역할별 레이어 목록 세 벌(`DEFAULT_PERMS`)을 **정책표**로 바꾼다.
  - `LAYER_ACCESS` — 레이어 id → 그 레이어를 볼 수 있는 역할
  - `EXPORT_ACCESS` — 반출 형식 → 그 형식을 반출할 수 있는 역할
  - `DEFAULT_PERMS` 는 표에서 만들어지는 **파생값**이 된다.
  - **값은 이전과 완전히 같다**(역할별 목록과 순서까지). 파생값을 테스트로 고정했다.
- 정책에 쓰는 역할 집합(`ALL_ROLES` · `STAFF_ROLES`)은 `ADMIN_ROLES`(관리자 메뉴 권한)와
  **분리**했다. '관리자 화면에 들어갈 수 있다' 와 '지하시설물을 볼 수 있다' 는 다른 결정이다 —
  하나를 묶으면 나중에 한쪽을 고칠 때 다른 쪽이 딸려간다.
- `src/data/permission-policy.test.ts` **신규** (6건) — 표가 진짜 기준인지, 파생값이 표와
  어긋나지 않는지 고정한다.

## 결정과 이유

- **훅을 5개로 나눴다.** 14개 `useMemo` 를 하나씩 훅으로 만들면 화면이 14개의 이름을 갖게
  된다. 계산 흐름(점수 → 조회 결과 → 목록 → 알림) 단위로 묶는 편이 읽힌다.
- **`Db` 를 `types.ts` 로 옮겼다.** 훅이 `Db` 를 받는데 `Db` 가 App.tsx 에 있으면 순환 참조가
  된다. `types.ts` 가 아래쪽 모듈이라 거기가 자리다.
- **정책표를 역할×레이어 행렬로 뒤집지 않고 '레이어 → 역할' 로 두었다.** 행렬로 세우면
  레이어가 늘어날 때 표가 넓어지고, 지금처럼 '레이어 하나가 누군지' 한 줄로 읽힌다.
- **역할 집합을 `ADMIN_ROLES` 과 분리했다.** 위와 같은 이유 — 두 결정이 같은 상수를 쓰면
  하나를 고칠 때 다른 쪽이 딸려간다.
- **기존 테스트 192건에 훅 테스트 14건을 더했다.** 리팩터는 '같은 동작'을 증명해야 하는데,
  App.test.tsx 만으로는 '훅으로 뺀 계산이 원래와 같다' 를 직접 보이지 않는다. 훅 테스트가 그
  자리를 메운다.
