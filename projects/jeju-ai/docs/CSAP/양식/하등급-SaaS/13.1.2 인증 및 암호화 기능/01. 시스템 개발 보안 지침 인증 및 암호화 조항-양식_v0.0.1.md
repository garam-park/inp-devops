> [!info] 법령 기준
> 개인정보 보호법 제29조(법률 제20897호, 2025. 10. 2. 시행)와 개인정보의 안전성 확보조치 기준 제6조·제7조(개인정보보호위원회고시 제2026-9호, 2026. 7. 1. 시행)를 기준으로 작성했다. 법령·고시가 개정되면 국가법령정보센터에서 조문을 다시 확인한다.

## 1. 목적

{{회사명}}은(는) {{서비스명}}(하등급 SaaS)의 설계·개발·변경 시 사용자 인증과 중요정보 암호화에 대한 보안 요구사항을 본 조항으로 정의하고, 모든 설계·개발 산출물에 반영하여 인증 우회, 중요정보 유출, 취약한 암호화 사용을 예방한다. 본 문서는 시스템개발보안지침 중 13.1.2 인증 및 암호화 기능에 해당하는 조항이며, 정보보호 정책서의 하위 지침으로 시행한다.

## 2. 적용 범위

- {{서비스명}} 인증 범위 내 응용 프로그램(이용자 웹 포털, 관리자 콘솔, API), 관리서버, 개인정보 수집·과금 기능의 설계·개발·변경 업무 전체
- 당사 임직원과 개발 업무를 수행하는 외부인력
- 책임공유모델에 따라 애플리케이션 계층의 인증·암호화 설계는 당사 책임이다. 하이퍼바이저·물리 인프라 등 IaaS/PaaS 제공자 책임 영역의 인증은 제공자 인증(CSAP 등)·계약으로 확인하고, 당사가 사용하는 클라우드 콘솔·관리 스택 계정의 인증 설정은 당사 책임으로 본 조항을 적용한다.

## 3. 용어 정의

| 용어 | 정의 |
| --- | --- |
| 중요정보 | 개인정보, 인증정보, 이용 기관 데이터 등 유출·변조 시 서비스와 이용 기관에 중대한 영향을 주는 정보. 암호화 대상 분류는 5항을 따른다. |
| 인증정보 | 비밀번호, 생체인식정보, 인증 토큰, API 키, 인증서 등 사용자·시스템 인증에 사용되는 정보 |
| 안전한 암호 알고리즘 | 12.3.1 암호 정책에서 정한 안전성이 입증된 알고리즘과 키 길이(보안강도 112비트(2^112) 이상, KISA 암호이용 안내서 권고 준용) |
| 보안 요구사항 ID | 본 조항 4~7항의 요구사항 식별자. 설계 반영표(양식 03)와 시험 결과에서 추적에 사용한다. |

## 4. 사용자 인증 보안 요구사항

클라우드 시스템 설계 시 다음 요구사항을 정의하여 반영한다. 세부 수치는 당사 기준값이며, 조정하더라도 요구사항 자체를 삭제하지 않는다.

### 4.1 인증 시기와 대상

| ID | 요구사항 | 적용 대상 |
| --- | --- | --- |
| AUTH-01 | 서비스 기능·데이터에 접근하기 전에 사용자를 인증하며, 인증 없이 접근 가능한 기능은 공개 대상(로그인, 안내 페이지 등)으로 한정하여 명세한다. | 이용자 웹 포털, 애플리케이션 |
| AUTH-02 | 관리서버, 개인정보 수집서버, 과금 기능, API 관련 서버 등 내부 관리 기능도 사용자 인증을 거쳐 접근한다. | 관리서버, 내부 관리 기능 |
| AUTH-03 | 관리자 기능은 일반 사용자 기능과 분리(별도 URL·화면·권한)하고, 접근 시 추가 인증을 요구한다. | 관리자 콘솔 |
| AUTH-04 | 개인정보처리시스템 등 중요한 시스템은 OTP, 생체인증, 인증서 등 추가 인증을 적용하고, 정보통신망을 통한 외부 접속에는 안전한 인증수단을 적용한다(안전성 확보조치 기준 제6조제2항). | 개인정보처리시스템, 클라우드 콘솔 |

### 4.2 패스워드

| ID | 요구사항 | 기준값 |
| --- | --- | --- |
| AUTH-05 | 패스워드 길이·조합 규칙을 정의하여 강제한다. | {{예: 10자리 이상, 문자 종류 2종 이상 조합}} |
| AUTH-06 | 로그인 실패가 임계치를 초과하면 계정을 잠그거나 추가 검증(CAPTCHA 등)을 요구한다. | 연속 {{5}}회 실패 시 {{계정 잠금 / n분 잠금}} |
| AUTH-07 | 패스워드는 복호화되지 않도록 일방향 암호화(솔트 적용 해시)하여 저장한다(안전성 확보조치 기준 제7조제1항). | {{예: SHA-256 이상 기반 검증된 해시}} |
| AUTH-08 | 패스워드 변경 주기와 초기 패스워드 강제 변경을 적용한다. | {{예: 관리자 90일, 초기 패스워드 최초 로그인 시 변경}} |
| AUTH-09 | 로그인 오류 메시지는 아이디 존재 여부와 패스워드 오류를 구분하여 표시하지 않는다. | 일반화된 메시지 |

- 패스워드 세부 기준(생성 규칙, 변경 절차 등)은 10.3.4 패스워드 관리 절차와 일치시킨다.

### 4.3 접근 권한과 세션

| ID | 요구사항 | 기준값 |
| --- | --- | --- |
| AUTH-10 | 동일 사용자·동일 권한의 동시 접근 제한을 설계에 정의한다(관리자 계정은 필수). | {{예: 관리자 동시 세션 1개}} |
| AUTH-11 | 관리자 등 필요 시 접근 IP 또는 MAC 제한을 적용할 수 있게 설계한다. | {{예: 관리자 콘솔 허용 IP 목록}} |
| AUTH-12 | 접근 후 관리 활동을 수행하지 않으면 세션이 자동 만료되도록 타임아웃을 설정한다(안전성 확보조치 기준 제6조제4항). | 유휴 {{n}}분 |
| AUTH-13 | SaaS 애플리케이션 사용을 위한 접근 권한 정책을 수립하고, 그에 따라 사용 권한과 관리 권한을 구분하여 부여하도록 설계한다. 이용 기관·이용자 데이터에 대한 접근 권한도 정책에 따라 부여한다. | 권한 정책 문서 |

### 4.4 API 및 연동 서비스

| ID | 요구사항 | 기준값 |
| --- | --- | --- |
| AUTH-14 | API 등을 통한 연동 서비스 호출에 안전한 인증 방안(토큰, 상호 TLS, 서명 등)을 적용한다. 인증 없는 API 엔드포인트를 두지 않는다. | {{예: OAuth 2.0, API 키 + TLS}} |
| AUTH-15 | 인증에 사용되는 인증키(API 키, 토큰 서명키, 인증서 개인키)는 비밀정보 저장소 등으로 보호하고, 소스코드·설정 파일에 평문으로 저장하지 않는다. | {{예: 키 관리 서비스, 비밀정보 저장소}} |

## 5. 저장 암호화 보안 요구사항

중요정보로 분류된 데이터는 저장 시 암호화·복호화를 적용하도록 설계한다. 암호 알고리즘과 키 길이는 12.3.1 암호 정책의 안전성이 입증된 알고리즘을 사용한다.

| ID | 대상 | 요구사항 | 근거 |
| --- | --- | --- | --- |
| ENC-S-01 | 비밀번호, 생체인식정보 등 인증정보 | 저장 시 암호화하며, 비밀번호는 일방향 암호화 | 안전성 확보조치 기준 제7조제1항 |
| ENC-S-02 | 이용자의 주민등록번호·여권번호·운전면허번호·외국인등록번호·신용카드번호·계좌번호·생체인식정보 | 안전한 암호 알고리즘으로 암호화하여 저장 | 안전성 확보조치 기준 제7조제2항 |
| ENC-S-03 | 그 밖의 중요정보(이용 기관 데이터 중 기밀 분류, 인증키 등) | 데이터 분류 기준에 따라 저장 암호화 적용 여부를 설계 단계에서 결정하고 근거를 기록 | 내부 데이터 분류 기준 |
| ENC-S-04 | 개인정보취급자 컴퓨터·모바일 기기·보조저장매체에 저장하는 이용자 개인정보 | 안전한 암호 알고리즘으로 암호화 후 저장 | 안전성 확보조치 기준 제7조제5항 |
| ENC-S-05 | 암호키 | 키 생성·보관·교체·폐기는 12.3.1 암호 정책의 키 관리 기준을 따르고, 암호화 대상 데이터와 분리하여 보관 | 12.3.1 암호 정책 |

## 6. 전송 암호화 보안 요구사항

중요정보를 송·수신하는 경우 기밀성과 무결성을 지원하는 안전한 채널을 사용하도록 설계한다.

| ID | 요구사항 | 기준값 |
| --- | --- | --- |
| ENC-T-01 | 웹 포털·관리자 콘솔·API의 중요정보 송·수신 구간에 TLS 1.2 이상을 적용한다. | TLS {{1.2 / 1.3}} 이상 |
| ENC-T-02 | SSL(전 버전), TLS 1.0, TLS 1.1 등 취약한 암호화 프로토콜은 지원하지 않도록 설정하고, 설계·구축 시 비활성화를 확인한다. | 금지 목록 고정 |
| ENC-T-03 | 서버 원격 접근·데이터 이관 등 관리 목적 통신에는 VPN, SSH 등 암호화된 통신수단을 사용한다. | {{VPN / SSH}} |
| ENC-T-04 | 개인정보·인증정보를 정보통신망(인터넷망 구간)으로 송·수신하는 경우 안전한 암호 알고리즘으로 암호화한다. | 안전성 확보조치 기준 제7조제1항·제4항 |
| ENC-T-05 | 지원 암호 스위트의 보안강도는 112비트(2^112) 이상으로 구성한다(11.1.4 네트워크 암호화 지침과 일치). | {{예: RSA 2048bit 이상, SHA-256 이상}} |

## 7. 시큐어 코딩 보안 요구사항

| ID | 요구사항 | 기준값 |
| --- | --- | --- |
| SEC-C-01 | 사용자 입력값은 서버 측에서 검증한 뒤 사용하고, 검증 없이 SQL 쿼리·명령어·경로에 직접 연결(문자열 연결)하지 않는다. | 입력값 검증 공통 모듈 |
| SEC-C-02 | DB 질의는 Prepared Statement(매개변수화된 쿼리) 또는 검증된 ORM을 사용하여 SQL Injection을 차단한다. 검색 기능 등 동적 조건이 필요한 경우에도 문자열 연결 방식을 사용하지 않는다. | 코드 리뷰 필수 확인 항목 |
| SEC-C-03 | 인증·세션·암호화 기능은 검증된 표준 라이브러리·프레임워크 기능을 사용하고 자체 구현하지 않는다. | {{사용 프레임워크}} |
| SEC-C-04 | 오류 발생 시 내부 정보(스택 트레이스, 쿼리문, 서버 정보)를 사용자 화면에 노출하지 않는다. | 공통 오류 처리 |

## 8. 단계별 적용

| 단계 | 적용 내용 | 기록 |
| --- | --- | --- |
| 설계 | 4~7항의 요구사항을 설계서에 반영하고 양식 03. 시스템 설계서 보안 요구사항 반영표를 작성한다. | 양식 03 |
| 구현 | 시큐어 코딩 요구사항을 준수하고 코드 리뷰에서 SEC-C 항목을 확인한다. | 코드 리뷰 기록 |
| 시험 | 요구사항 ID별로 동작을 시험한다(잠금 동작, 취약 프로토콜 비활성, SQL Injection 등). 시험 계획·결과는 13.2.1 시험 계획 및 결과 산출물을 따른다. | 시험 결과서 |
| 변경 | 인증·암호화에 영향을 주는 변경은 양식 04. 시스템 변경 내역서로 영향을 검토하고 반영·시험을 확인한다. | 양식 04 |
| 운영 | 구현 상태의 증적을 양식 05. 증적 수집 점검표로 수집·보관한다. | 양식 05 |

- 요구사항 정의부터 반영 확인까지의 상세 절차는 양식 02. 보안요구사항 정의 및 반영 절차를 따른다.

## 9. 역할과 책임

| 역할 | 책임 |
| --- | --- |
| 정보보호 최고책임자 | 본 조항 승인, 예외 승인 |
| 정보보호 관리자 | 본 조항 관리·개정, 설계 반영표·변경 내역서의 보안 검토, 시험 결과 확인 |
| 개발 부서장 | 설계·구현 단계의 요구사항 반영 책임, 코드 리뷰 시행 |

| 인프라 운영 담당 | TLS·VPN 등 전송 구간 설정, 암호화 설정 적용과 증적 수집 |

## 10. 예외 관리

1. 기술적 제약으로 요구사항을 적용할 수 없으면 대체 통제와 적용 기한을 적어 정보보호 최고책임자의 승인을 받는다.
2. 예외는 양식 03의 반영 확인표에 예외 승인 번호와 함께 기록하고, {{반기}}마다 지속 필요성을 재검토한다.
3. 취약 프로토콜 허용(ENC-T-02 위반)과 인증 없는 중요 기능 접근(AUTH-01·02 위반)은 예외로 승인하지 않는다.
