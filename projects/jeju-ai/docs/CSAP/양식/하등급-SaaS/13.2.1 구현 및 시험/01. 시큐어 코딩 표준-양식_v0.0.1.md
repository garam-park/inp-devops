> [!info] 법령 기준
> 개인정보를 처리하는 기능의 접근통제·암호화 요구는 개인정보의 안전성 확보조치 기준 제6조·제7조(개인정보보호위원회고시 제2026-9호, 2026. 7. 1. 시행)를 기준으로 식별했다. 법령·고시가 개정되면 국가법령정보센터에서 조문을 다시 확인한다.

## 1. 목적

{{회사명}}은(는) 클라우드컴퓨팅서비스 {{서비스명}}을 안전하게 구현하기 위하여 개발 전 과정에 적용하는 시큐어 코딩 표준을 정하고, 모든 개발자가 이 표준에 따라 구현하도록 한다.

## 2. 적용 범위

- {{서비스명}}(하등급 SaaS) 인증 범위의 응용 프로그램: 웹 애플리케이션, API, 관리자 기능, 배치 프로그램, 배포 스크립트·인프라 코드(IaC)
- 당사 임직원과 개발 업무를 수행하는 외부인력이 작성하는 모든 소스코드
- 책임공유모델에 따라 물리 시설, 하이퍼바이저, 관리형 플랫폼 등 IaaS/PaaS 제공자 책임 영역의 소프트웨어는 제공자 인증·계약으로 확인하고, 당사는 제공자 위에서 당사가 개발·운영하는 애플리케이션 계층에 본 표준을 적용한다.

## 4. 코딩표준

각 규칙의 준수 여부는 코드 리뷰와 정적 분석 도구로 확인하며, 확인 방법은 5항을 따른다.

### 4.1 입력 데이터 검증

| No | 규칙 |
| --- | --- |
| 1 | 사용자·외부 시스템이 입력한 모든 데이터는 서버 측에서 검증한다. 클라이언트 측 검증은 편의 목적으로만 사용하고 신뢰하지 않는다. |
| 2 | 보안 기능(인증, 권한, 금액·수량 등)을 결정하는 입력값은 반드시 서버 측에서 재검증한다. |
| 3 | 입력값은 허용 목록(형식, 길이, 범위, 허용 문자) 방식으로 검증하고, 검증에 실패하면 요청을 거부한다. |
| 4 | 파일 업로드는 확장자·MIME 타입·크기를 서버 측에서 검증하고, 업로드 파일은 실행 권한 없이 웹 루트 밖 또는 별도 스토리지에 저장한다. |

### 4.2 SQL 삽입 방지

| No | 규칙 |
| --- | --- |
| 1 | 데이터베이스 질의는 Prepared Statement(파라미터 바인딩) 또는 검증된 ORM으로 작성한다. |
| 2 | 사용자 입력값을 문자열 연결로 SQL 쿼리에 직접 결합하지 않는다. |
| 3 | 동적으로 구성할 수밖에 없는 식별자(테이블·컬럼명, 정렬 기준)는 허용 목록과 대조하여 사용한다. |
| 4 | 애플리케이션의 DB 계정은 업무에 필요한 최소 권한만 가지며 DDL·관리자 권한을 부여하지 않는다. |

### 4.3 출력값 처리(XSS 방지)

| No | 규칙 |
| --- | --- |
| 1 | 사용자 입력값을 화면에 출력할 때는 출력 위치(HTML, 속성, 스크립트, URL)에 맞게 이스케이프 처리한다. |
| 2 | 템플릿 엔진·프레임워크의 자동 이스케이프 기능을 사용하고, 이를 우회하는 함수({{예: innerHTML, dangerouslySetInnerHTML}})는 검토 승인 없이 사용하지 않는다. |

### 4.4 URL 리다이렉션

| No | 규칙 |
| --- | --- |
| 1 | 사용자 입력값을 리다이렉션 대상 URL로 직접 사용하지 않는다. |
| 2 | 리다이렉션이 필요한 경우 허용된 URL 목록 또는 내부 경로 식별자와 대조한 뒤 이동시킨다. |

### 4.5 세션 관리

| No | 규칙 |
| --- | --- |
| 1 | 세션 ID는 프레임워크가 제공하는 안전한 난수 기반 값을 사용하고 URL에 노출하지 않는다. |
| 2 | 로그인 성공 시 세션 ID를 재발급하고, 로그아웃·권한 변경 시 기존 세션을 무효화한다. |
| 3 | 세션 쿠키에 Secure, HttpOnly 속성을 설정하고, SameSite 속성을 {{Lax 이상}}으로 설정한다. |
| 4 | 일정 시간({{n}}분) 활동이 없으면 세션을 만료하고, 관리자 기능은 더 짧은 타임아웃({{n}}분)을 적용한다. |

### 4.6 오류 처리

| No | 규칙 |
| --- | --- |
| 1 | 오류 발생 시 스택 트레이스, 내부 경로, DB 오류 메시지 등 내부 정보를 이용자 화면에 노출하지 않고, 정의된 오류 페이지·응답 코드를 반환한다. |
| 2 | 오류 처리 후 시스템은 안전한 상태(거부 기본값)로 동작한다. 오류를 무시하고 처리를 계속하지 않는다. |
| 3 | 상세 오류 내용은 서버 로그에만 기록하고, 로그에 개인정보·인증정보를 남기지 않는다. |

### 4.7 인증·접근권한

| No | 규칙 |
| --- | --- |
| 1 | 모든 보호 대상 기능·API는 서버 측에서 인증과 권한을 검증한다. 화면 숨김만으로 접근을 통제하지 않는다. |
| 2 | 데이터 조회·변경 시 요청자가 해당 데이터의 소유자(이용 기관·이용자)인지 서버 측에서 확인하여 다른 이용 기관의 데이터에 접근할 수 없게 한다. |
| 3 | 관리자 기능은 일반 이용자 기능과 분리된 경로·권한으로 구현한다. 인증·패스워드·추가 인증 구현 기준은 10.3.2, 10.3.3, 10.3.4를 따른다. |
| 4 | 로그인 연속 실패 제한, 계정 잠금 등 인증 보호 기능은 13.1.2에서 정의한 보안 요구사항대로 구현한다. |

### 4.8 암호화

| No | 규칙 |
| --- | --- |
| 1 | 중요정보·개인정보·인증정보의 저장·전송 암호화는 12.3.1 암호 정책에서 정한 안전성이 입증된 알고리즘과 키 길이를 사용한다. |
| 2 | 자체 구현한 암호 알고리즘을 사용하지 않고, 검증된 라이브러리를 사용한다. |
| 3 | 패스워드는 일방향 암호화(해시)로 저장한다. |
| 4 | 중요정보 전송 구간에는 TLS 1.2 이상을 적용하고, 취약한 프로토콜(SSL v3, TLS 1.0·1.1)을 허용하지 않는다(11.1.4 참조). |

### 4.9 비밀정보·설정 관리

| No | 규칙 |
| --- | --- |
| 1 | 패스워드, API 키, 인증서, 접속 문자열 등 비밀정보를 소스코드·형상관리 저장소에 하드코딩하지 않는다. |
| 2 | 비밀정보는 비밀정보 저장소({{예: 클라우드 Secret 관리 서비스}}) 또는 암호화된 설정으로 관리한다. |
| 3 | 주석·테스트 코드·로그에 비밀정보와 개인정보를 남기지 않고, 운영 반영 전에 디버그 코드를 제거한다. |

### 4.10 외부 구성요소

| No | 규칙 |
| --- | --- |
| 1 | 오픈소스·외부 라이브러리는 승인된 목록에서 사용하고, 알려진 취약점(CVE) 여부를 도입 시와 주기적으로 확인한다. |
| 2 | 지원이 종료되었거나 취약점이 조치되지 않은 버전은 사용하지 않는다. |

## 7. 교육 및 주지

- 개발자(외부인력 포함)는 배치 후 {{n}}개월 이내와 이후 연 1회 이상 시큐어 코딩 교육을 이수한다(2.3.2 교육 시행과 연계).
- 본 표준은 형상관리 저장소·사내 위키 등 개발자가 상시 참조할 수 있는 위치({{ }})에 게시하고, 제·개정 시 전 개발자에게 공지한다.
