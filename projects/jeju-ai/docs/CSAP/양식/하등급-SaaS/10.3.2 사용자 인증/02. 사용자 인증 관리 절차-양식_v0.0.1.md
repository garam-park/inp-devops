## 1. 목적

{{회사명}}이(가) 클라우드컴퓨팅서비스 {{서비스명}}을 제공하기 위해 운영하는 클라우드 시스템에 대한 접근을 사용자 인증, 로그인 횟수 제한, 세션 관리, 불법 로그인 시도 경고 등 안전한 사용자 인증절차로 통제하고, 싱글사인온 등 계정 연동 방식의 인증에 별도 보호대책을 적용하는 기준과 절차를 정한다.

## 2. 적용 범위

### 2.3 제공자 책임 영역

물리 시설, 하이퍼바이저, 제공자 내부 관리 시스템에 대한 인증 통제는 IaaS/PaaS 제공자의 책임이며, 제공자의 CSAP 인증서와 계약서 보안 조항으로 확인한다. 당사는 제공자가 제공하는 인증 기능(다중 인증, 비밀번호 정책, 세션 설정, 접속 조건)을 당사 계정에 실제로 설정할 책임을 진다.

## 3. 용어 정의

| 용어 | 정의 |
| --- | --- |
| 사용자 인증 | 시스템에 접근을 요청하는 자가 정당한 계정의 소유자임을 인증정보로 검증하는 절차 |
| 인증정보 | 비밀번호, 일회용 비밀번호(OTP), 인증서, 보안토큰, 생체정보, 액세스 키 등 신원 검증에 사용되는 정보 |
| 다중 인증(MFA) | 지식(비밀번호), 소유(OTP 기기·인증서·보안토큰), 속성(생체) 중 서로 다른 두 가지 이상의 요소를 결합한 인증 |
| 강화된 인증수단 | 아이디·비밀번호 외에 추가로 적용하는 인증수단(OTP, 인증서, 보안토큰, 생체 등)과 접속 조건 통제(IP·단말 제한 등) |
| 로그인 횟수 제한 | 일정 횟수 이상 인증에 실패하면 계정 잠금, CAPTCHA, 지연 등으로 추가 시도를 제한하는 통제 |
| 세션 | 인증 성공 후 재인증 없이 시스템을 사용할 수 있는 상태. 유휴 시간 제한과 최대 유지 시간으로 관리한다. |
| 재인증 | 유효한 세션이 있어도 중요 기능 접근 전이나 일정 시간 경과 후 인증을 다시 요구하는 것 |
| 불법 로그인 시도 | 정당한 사용자가 아닌 자가 시도한 것으로 의심되는 로그인 실패·성공 이벤트(반복 실패, 비정상 위치·단말, 다수 계정 대상 시도 등) |
| 싱글사인온(SSO) | 한 번의 인증으로 여러 시스템에 접근할 수 있게 하는 인증 방식. IdP와 SAML·OIDC·OAuth 등 프로토콜로 구성한다. |

## 4. 기본 원칙

1. 클라우드 시스템의 모든 접근 경로(웹 UI, API, CLI, 원격 접속)는 인증을 거쳐야 하며, 인증 없이 접근 가능한 기능은 공개가 승인된 정보에 한정한다.
2. 계정은 개인별로 발급하고 공용 계정 사용을 금지한다. 시스템 기본 계정(admin, root 등)은 비활성화하거나 직접 로그인을 차단하고, 불가피하게 사용하면 봉인·2인 관리한다.
3. 시스템 유형과 위험도에 따라 6항의 최소 기준 이상으로 인증 방식, 로그인 실패 제한, 세션 관리, 경고를 설정한다. 제공자·제품 기본값이 기준보다 약하면 기준에 맞게 변경한다.
4. 인증 실패 시 실패 사유(계정 존재 여부, 비밀번호 오류, 잠금 상태 등)를 화면·응답에 상세히 노출하지 않는다.
5. 위험도가 높은 접근에는 다중 인증을 적용하고, 개인정보처리시스템에 대한 외부 접속에는 법정 안전한 인증수단을 적용한다.
6. 인증 통제 기준을 충족하지 못하는 시스템은 14항의 예외 절차로 승인·보완하지 않는 한 운영하지 않는다.
7. 인증 통제 설정과 불법 로그인 시도 경고는 정기적으로 점검·검토하고 결과를 기록한다.

## 5. 책임공유모델에 따른 책임 구분

| 인증 통제 영역 | IaaS/PaaS 제공자 | 당사(SaaS 제공자) | 이용 기관 |
| --- | --- | --- | --- |
| 물리 시설·하이퍼바이저 접근 인증 | 책임 | 제공자 인증·계약으로 확인 | 해당 없음 |
| 제공자 콘솔·API 인증 기능 | 기능 제공(다중 인증, 비밀번호 정책, 세션, 접속 조건) | 당사 계정에 기능 설정·유지, 루트 계정 봉인 | 해당 없음 |
| 운영 서버·DB·네트워크·정보보호시스템 계정 인증 | 해당 없음(PaaS 관리형 서비스는 기능 제공) | 설정·운영 | 해당 없음 |

| 불법 로그인 시도 경고·대응 | 인프라 계층 이상 통지 | 서비스·관리 계층 탐지·경고·대응 | 이용자 알림 확인·신고 |

## 8. 로그인 실패 처리 및 오류 메시지 기준

### 8.1 로그인 실패 제한

| 단계 | 조건(내부 기준) | 조치 | 해제 |
| --- | --- | --- | --- |
| 1단계 | 연속 {{3}}회 실패 | CAPTCHA 요구 또는 {{n}}초 지연 | 성공 시 초기화 |
| 2단계 | 연속 {{5}}회 실패 | 계정 잠금 {{30}}분(자동 해제) 또는 관리자 해제 | 시간 경과 또는 본인 확인 후 담당자 해제 |
| 3단계 | 잠금 반복 {{3}}회 이상 또는 다수 계정 대상 시도 | 출발지 IP 차단, 정보보호 담당자 경고, 사용자 알림 | 정보보호 담당자 확인 후 해제 |

- 실패 횟수는 계정 단위로 집계하고, 출발지 IP 단위 집계를 병행하여 다수 계정을 대상으로 한 시도(무차별 대입·크리덴셜 스터핑)를 탐지한다.
- 관리자 포털·관리시스템의 잠금은 자동 해제 대신 관리자 확인 해제를 우선 적용한다. 자동 해제를 쓰면 해제 시간과 실패 임계치를 양식 03에 기록한다.
- 잠금 해제 요청은 본인 확인(등록된 연락처, 소속 부서장 확인 등)을 거치고 처리 기록을 남긴다.
- 개인정보처리시스템은 일정 횟수 이상 인증 실패 시 접근을 제한하는 조치가 법정 의무이므로(안전성 확보조치 기준 제5조제6항) 예외를 허용하지 않는다.

3. 확인: 정보보호 담당자는 경고 수신 후 {{1}}시간 이내(업무 시간 외 다음 업무일 시작 후 {{1}}시간 이내)에 접근기록을 확인하고, 사용자 또는 부서장에게 사실을 확인한다.
4. 조치: 불법 시도로 판단하면 출발지 차단, 해당 계정 비밀번호 초기화와 세션 강제 종료, 다중 인증 재등록을 수행하고 이용 기관 계정이면 이용 기관 관리자에게 통지한다.
5. 전환: 로그인 성공 흔적, 권한 변경, 데이터 접근이 확인되면 침해사고 대응 절차(5.1.1)로 전환하고 보고한다.
6. 기록: 모든 경고와 조치는 양식 05. 사용자 인증 통제 점검 기록 4항에 월별로 집계하고, 원본 이벤트는 접근기록(10.1.2)으로 보관한다.

## 12. 설계·도입·변경 시 인증 통제 검토

## 14. 예외 관리

| 단계 | 담당 | 내용 |

| 5. 재검토 | 정보보호 관리자 | 만료 전 재검토, 정기 점검(양식 05) 시 이행 확인 |
