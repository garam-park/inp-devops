> [!info] 법령 기준
> 개인정보의 안전성 확보조치 기준 제7조(개인정보보호위원회고시 제2026-9호, 2026. 7. 1. 시행)는 비밀번호·생체인식정보 등 인증정보를 정보통신망을 통하여 송·수신하는 경우(제1항)와 개인정보를 정보통신망을 통하여 인터넷망 구간으로 송·수신하는 경우(제4항) 안전한 암호 알고리즘으로 암호화하도록 정한다. 법령·고시가 개정되면 국가법령정보센터에서 조문을 다시 확인한다.

## 1. 목적

본 지침은 {{회사명}}이 제공하는 {{서비스명}}(하등급 SaaS)의 클라우드 시스템에서 중요정보가 이동하는 모든 구간에 암호화된 통신 채널을 적용하기 위하여, 암호화 대상, 요구 암호 강도, 전송 시 암호화 방법, 담당자의 역할과 책임을 정한다. 본 지침은 정보보호 정책서 {{문서번호}} 제{{n}}장(암호 통제)과 네트워크보안지침 {{문서번호}} 중 네트워크 암호화에 해당하는 절을 이루며, 저장 데이터 암호화와 암호키 관리의 상세 절차는 12.3.1 암호 정책 수립 산출물을 따른다.

| 구분 | 범위 | 책임 |

| 제공자 책임 구간 | 데이터센터 내 물리 네트워크, 하이퍼바이저 내부 통신, 제공자 관리 영역의 전송 보호 | IaaS/PaaS 제공자({{제공자명}})의 책임이며, 제공자의 CSAP 인증과 이용 계약·공개 문서로 보호 수준을 확인한다. 확인 결과는 양식 02. 암호화 통신 채널 사용 현황 4항에 기록한다. |

| 용어 | 정의 |

## 5. 암호화 대상 구간

다음 구간에서 중요정보를 송·수신하는 경우 암호화 통신 채널을 필수로 적용한다. 구간별 실제 적용 내역은 양식 02. 암호화 통신 채널 사용 현황으로 관리한다.

| No | 구간 | 예시 | 적용 채널 | 적용 |
| --- | --- | --- | --- | --- |
| 1 | 이용자·이용 기관 ↔ 서비스 | 웹·모바일 접속, 로그인, 개인정보 처리 화면, 공개 API 호출 | HTTPS(TLS) | 필수 |
| 2 | 관리자 원격 접근 | 운영 서버 SSH 접속, 클라우드 콘솔·관리 포털 접속 | VPN, SSH, HTTPS | 필수 |
| 3 | 서비스 내부 구간 | 응용 ↔ DB·스토리지, 서버 간 중요정보 전송 | TLS, SSH 터널 | 필수(중요정보 이동 시) |
| 4 | 외부 서비스 연계 | 외부 API, 알림·메일 발송, 결제 연동 | HTTPS(TLS) | 필수 |
| 5 | 데이터 이관·백업 전송 | 이용자 데이터 이관, 리전·가용영역 간 복제, 외부 백업 전송 | VPN, TLS(SFTP 등) | 필수 |

- 인증정보는 중요정보 취급 여부와 관계없이 모든 구간에서 암호화하여 송·수신한다(안전성 확보조치 기준 제7조제1항).
- DaaS 형태로 가상 데스크톱을 제공하는 경우 내부망(업무환경)에서 가상PC 접근 시 VPN 또는 전용회선을 필수 적용한다. 해당 서비스가 없으면 이 항은 적용하지 않는다.

## 6. 통신 프로토콜 기준

| 구분 | 허용 | 사용 금지 |
| --- | --- | --- |
| 웹·API(TLS) | TLS 1.2 이상(TLS 1.3 권장) | SSL 2.0, SSL 3.0, TLS 1.0, TLS 1.1 |
| 원격 셸·파일 전송 | SSH-2(OpenSSH 등), SFTP, SCP, FTPS, HTTPS | SSH-1, Telnet, FTP, TFTP |
| VPN | IPsec(IKEv2), SSL VPN(TLS 1.2 이상) | PPTP |

- 신규 시스템·구간은 오픈 전에 허용 프로토콜만 활성화되어 있는지 확인한다.
- 운영 중 취약 프로토콜이 발견되면 {{n}}영업일 이내에 비활성화하고, 즉시 조치가 어려우면 10항의 예외 절차를 따른다.
- 로드밸런서·웹서버의 TLS 정책은 취약 버전을 포함하지 않는 정책({{예: 클라우드 제공자의 TLS 1.2 이상 보안 정책}})으로 지정하고, 정책 이름을 양식 02 현황에 기록한다.

## 7. 암호 알고리즘·보안강도 기준

암호화 통신 채널이 지원하는 암호의 보안강도는 2^112 이상이어야 한다. KISA 암호이용 안내서의 권고를 참고하여 다음 기준을 적용한다.

| 구분 | 허용(예) | 사용 금지(예) |
| --- | --- | --- |
| 블록 암호 | SEED, ARIA, AES 등 키 길이 128bit 이상 | DES, RC4 |
| 공개키 암호 | RSA 키 길이 2048bit 이상, ECDSA P-256 이상 | RSA 1024bit 이하 |
| 해시 | SHA-256 이상 | MD5, SHA-1(인증서 서명·무결성 용도) |
| 키 교환 | ECDHE, DHE(2048bit 이상) | 익명(anonymous) 키 교환, EXPORT 급 암호 스위트 |

- 공공기관에 검증필 암호화 기술을 제공해야 하는 경우 국가정보원 검증필 암호모듈·검증 대상 알고리즘 기준을 함께 적용한다. 상세 요구는 14.3.1 검증필 암호화 기술 제공 산출물을 따른다.

## 8. 구간별 적용 방법

| 구간 | 적용 방법 |
| --- | --- |
| 웹 서비스·공개 API | 로드밸런서 또는 웹서버에 TLS 인증서를 설치하고 6항의 TLS 정책을 적용한다. HTTP 접속은 HTTPS로 리다이렉트하고 HSTS 적용을 권장한다. |
| 클라우드 콘솔·관리 포털 | HTTPS로만 접속하고 다중 인증을 적용한다(10.3.3 강화된 인증 수단 제공). |
| 운영 서버 원격 접근 | VPN 접속 후 SSH-2로 접근한다. SSH는 키 기반 인증을 원칙으로 하고, sshd 설정에서 취약 알고리즘을 제거한다. |
| 응용 ↔ DB·스토리지 | DB 연결 문자열과 서버 파라미터에서 TLS 옵션을 활성화한다({{예: require_secure_transport, ssl=on}}). |
| 외부 서비스 연계 | HTTPS를 사용하고 상대 인증서 검증을 활성화한다. 개발·시험 편의를 위한 인증서 검증 생략 설정을 운영 환경에 반영하지 않는다. |
| 데이터 이관·백업 전송 | VPN 터널 또는 TLS 기반 전송(SFTP, HTTPS)을 사용하고, 필요 시 파일 단위 암호화를 병행한다. 이관 작업 기록에 사용 채널을 남긴다. |

## 9. 인증서 관리

1. TLS 인증서는 신뢰된 인증기관(CA)에서 발급받는다. 내부 시스템 간 통신에 사설 인증서를 쓰는 경우 내부 CA 운영 기준을 따르고 신뢰 저장소를 관리한다.
2. 인증서 만료 {{30}}일 전에 갱신을 완료하도록 만료 알림을 설정하고, 만료일은 양식 02 현황에서 관리한다.
3. 개인키와 비밀정보는 암호키·인증정보 관리자만 접근할 수 있는 저장소({{예: 키 관리 서비스, 비밀정보 저장소}})에 보관하고, 소스코드·문서에 평문으로 저장하지 않는다.
4. 암호키 생성·배포·교체·폐기의 상세 절차는 12.3.1 암호 정책 수립 산출물을 따른다.

## 10. 예외 관리

1. 기술적 제약(레거시 연동, 상대 시스템 미지원 등)으로 본 지침의 기준을 적용할 수 없는 구간은 담당 부서장이 예외를 신청하고, 정보보호 관리자 검토를 거쳐 정보보호 최고책임자가 승인한다.
2. 예외 승인 시 보완 통제(망 분리, 접근 IP 제한, 파일 단위 암호화, 모니터링 강화 등)와 적용 기한(최대 {{n}}개월)을 함께 정한다.
3. 예외 구간은 양식 02. 암호화 통신 채널 사용 현황 3항에 기록하고, 기한 도래 시 재검토한다.

## 11. 점검 및 현행화

1. 신규 통신 구간 오픈, 구성 변경, 인증서 교체 시 담당자는 6~8항의 기준 충족을 확인하고 양식 02 현황을 갱신한다.
2. 정보보호 관리자는 {{반기}} 1회 이상 양식 03. 암호화 통신 채널 점검 결과서로 전 구간의 프로토콜·알고리즘·인증서를 점검한다.
3. 프로토콜·알고리즘의 신규 취약점이 공개되면 수시 점검을 수행하고 필요 시 본 지침의 허용·금지 기준을 개정한다.
4. 심사 대비 증적은 양식 04. 증적 수집 점검표에 따라 수집·보관한다.
